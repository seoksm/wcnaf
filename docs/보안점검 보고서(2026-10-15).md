## Critical

### C1. `CommonQueryController` — 인증/인가 우회 가능한 범용 MyBatis 쿼리 실행 브릿지
- **분류**: OWASP A01 Broken Access Control / A03 Injection 인접
- **위치**: `services/common/.../interfaces/inboundAdapter/web/CommonQueryController.java:36-98`, `AbstractSqlSessionDao.java:30-90`, `CommonAuthorizationRequestInterceptor.java:111-126`(queryId 단위 인가 로직이 주석처리되어 비활성), `CommonAuthorizationUtilServiceImpl.java:60-90`
- **설명**: `/api/v1/{serviceName}/crud/{mapperName}/{queryId}`가 서비스명/매퍼명/쿼리ID를 그대로 조립해 MyBatis statement를 호출. `system`, `smart-asset` 양쪽 모두 `winitech.mybatis.enabled=true`로 실제 활성화됨. 인가는 queryId 단위 정확매칭이 아니라 URL 패턴 와일드카드 매칭(`AntPathMatcher`)이라, "crud/**" 류 권한이 하나라도 등록되면 의도치 않은 쿼리까지 호출 가능.
- **공격 시나리오**: `GET /api/v1/system/crud/user/UserMapper/findByUsernameAndStatus?username=admin` 호출로 관리자 계정의 해시 비밀번호 포함 레코드 획득, `PATCH .../updateUser`로 임의 사용자 레코드 직접 수정(정상 컨트롤러의 검증/권한체크 전부 우회).
- **권고안**: 엔드포인트 제거 권장. 유지 시 호출 가능한 `mapperName.queryId` 화이트리스트 강제 + 정확매칭 인가로 재설계, Map 기반 바인딩을 DTO로 전환.
- **상태**: ✅ 수정완료 — 사용처 없음 확인 후 `CommonQueryController`/`CommonQueryDto` 완전 삭제(`aa5833b`)

### C2. PostgreSQL 계정 하드코딩(`postgres/postgres`) + DB 포트 호스트 노출
- **분류**: OWASP A07 / 행안부 "하드코드된 비밀번호"
- **위치**: `docker/docker-compose.yml:113,115-116`(`25432:5432` 포트 퍼블리시, `POSTGRES_PASSWORD: postgres`), `services/{api-gateway,system,smart-asset}/src/main/resources/application-docker.properties:6-7`(`username=postgres`/`password=postgres`)
- **설명**: JWT/MFA/매직헤더/엑셀서명 키는 전부 환경변수+fail-fast 패턴으로 잘 분리했는데, DB 계정만 이 원칙에서 빠져 가장 흔한 기본값이 git에 커밋된 설정파일에 평문 노출되고 동시에 포트도 호스트에 열려 있음.
- **공격 시나리오**: 호스트 25432 포트 접근 가능한 공격자가 자격증명 추측 없이 `psql`로 즉시 전체 DB 접근.
- **권고안**: `${POSTGRES_PASSWORD}` 환경변수 주입으로 전환, 서비스별 최소권한 계정 분리, 포트 매핑 제거 또는 `127.0.0.1` 바인딩.
- **상태**: ✅ 수정완료(`aa5833b`) — 환경변수 주입 구조로 전환, 포트 `127.0.0.1` 바인딩. 단 **실제 비밀번호 값 자체는 사용자 요청("DB 암호는 그대로 두고")에 따라 "postgres"로 유지** — 구조적 하드코딩(git에 평문 노출)만 제거됐고, 자격증명 강도 자체를 올리려면 `docker/.env`의 `POSTGRES_PASSWORD`를 교체 후 `ALTER USER`로 별도 로테이션 필요

### C3. MFA 2차 인증(`secondAuth`) Rate Limit 전무 — TOTP/백업코드 무제한 시도
- **분류**: OWASP A07 / 행안부 "무차별 대입 공격 대응 미흡"
- **위치**: `services/system/.../domain/userMfa/UserMfaServiceImpl.java:78-120`, `services/mfa/.../TotpService.java:23-37`
- **설명**: 코드 실패해도 챌린지가 소비되지 않아 TTL(180초) 내 재시도 횟수 제한이 전혀 없음. 코드 전체에 rate limiter 자체가 존재하지 않음(전수 검색 결과 0건). 2차인증 실패는 로그인 잠금 카운트에도 반영 안 되는 것이 "의도된 정책"으로 주석에 명시되어 있음.
- **공격 시나리오**: 비밀번호가 유출된 계정에 대해 자동화 스크립트로 초당 수백~수천 회 TOTP/백업코드 대입 — MFA가 막으려는 바로 그 시나리오(비밀번호 유출 후 2차인증 우회)가 그대로 뚫림.
- **권고안**: `UserMfaChallenge`에 실패횟수 컬럼 추가해 N회 실패 시 챌린지 즉시 폐기, challengeId/사용자/IP 단위 rate limiter(Bucket4j 등) 도입.
- **상태**: ✅ 수정완료(`aa5833b`) — `UserMfaChallenge.failCount` + `registerFailure()`/`isFailureLimitExceeded()` 추가(기본 5회 초과 시 챌린지 즉시 폐기), 마이그레이션 `V5__add_mfa_challenge_fail_count.sql`. 2차 재점검에서 파일 간 연결(엔티티↔서비스↔레포지토리)까지 전부 정상 동작 확인

### C4. docker/local 프로파일에서 refreshToken API가 세션 상태·로그아웃·만료 검증 전부 우회
- **분류**: OWASP A07, A05 / 행안부 "세션 관리 미흡"
- **위치**: `UserApiController.java:274-276`, `UserFacade.java:230-241`(`devRefreshAccessToken`), `WiniSecurity.java:231-239`(만료검증 skipValidation), `docker-compose.yml:161`(`ACTIVE: "docker"`)
- **설명**: `activeProfile`이 "docker" 또는 "local"이면 `user_session` 조회, 로그인상태, 세션차단 확인 없이 **만료검증조차 스킵된** Authorization 헤더만으로 새 액세스 토큰을 재발급. 그런데 "docker"는 이 저장소의 유일한 컨테이너 배포 구성 자체 — prod 전용 프로파일은 존재하지 않음. 즉 이 우회가 실제 운영에서 상시 활성.
- **공격 시나리오**: 과거 발급된 토큰을 한 번이라도 확보하면(세션 하이재킹, XSS, 로그 유출, 퇴사자 토큰 등), 만료/로그아웃/강제차단과 무관하게 `GET /refreshToken` 반복 호출로 영구히 새 토큰 획득 가능.
- **권고안**: 분기 제거 또는 검증된 `winitech.devmode` 플래그와 결합, `devRefreshAccessToken`에도 세션 상태/차단 체크 추가.
- **상태**: ✅ 수정완료(`aa5833b`) — docker/local 분기에 `existLoginSessionBySessionIdAndUserId` 세션 LOGIN 상태 재검증 + `accessTokenRefreshTimeout` 체크 추가

### C5. API Gateway `AuthorizationFilter`의 `matchStart` 오용 — 인가 검사 전체 우회
- **분류**: OWASP A01 Broken Access Control
- **위치**: `AuthorizationFilter.java:86-94`(`matchStart` 사용) vs `AuthenticationFilter.java:67`(올바르게 `match` 사용 — 두 필터 간 불일치)
- **설명**: `matchStart`는 "접두사 일치"를 판단하므로, `EXCLUDE_PATHS`의 `/api/v1/system/user/login` 등과 공통 접두사인 `/api/v1/system/user`로 요청하면 인가 필터 자체가 완전히 스킵됨. 이 경로는 `UserApiController`의 전체 사용자 조회(`searchAllUser`)/신규계정 생성(`registerUser`) 베이스 경로.
- **공격 시나리오**: 유효한 JWT만 있으면(메뉴 권한 전혀 없는 말단 계정이라도) `GET /api/v1/system/user` 직접 호출로 전 직원 PII(username/email/phoneNumber/employeeNo/부서) 열람, `POST`로 임의 계정 생성 가능.
- **권고안**: `matchStart`를 `match`로 교체(한 줄 수정), 교체 후 EXCLUDE_PATHS 회귀 테스트.
- **상태**: ✅ 수정완료(`aa5833b`) — `match`로 교체, `AuthenticationFilter`와 일관성 확보. 2차 재점검에서 재확인 완료

## 운영 중 발견된 버그 (2026-10-16, `c7af80c`)

**증상**: MFA 해제 시 확인 코드를 틀리면 "세션이 만료되었습니다, 다시 로그인해주세요"가 뜨며 강제로 로그인 화면으로 튕겨나감(사용자 직접 테스트로 발견).

**원인**: R7에서 추가한 재인증 검증(`UserMfaServiceImpl.disable`)이 코드 검증 실패 시 `UnauthenticatedException`(HTTP 401 + `COMMON_UNAUTHENTICATED`)을 던지도록 구현했는데, 이 조합은 프론트엔드 전역 인터셉터(`httpAdapter.js`의 `AUTH_ERROR_CODE_NAMES`/`statusCode === 401` 체크)가 "세션 무효"로 해석해 강제 재로그인시키는 트리거였다. 로그인 2단계(`verifyChallenge`, 아직 미인증 상태)에서 쓰던 예외 타입을 "이미 로그인된 사용자가 현재 세션에서 재확인하는" 전혀 다른 상황(`disable`)에 그대로 복붙해서 생긴 실수.
