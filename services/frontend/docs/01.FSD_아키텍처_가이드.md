## 1. 핵심 원칙

### 1-1) Feature 중심 개발

- 새 요구사항(유즈케이스)은 **일단 `features/<domain>/<usecase>`에서 시작**합니다.
- `pages`는 가능하면 얇게 유지(조립/배치 중심)합니다.

추가 설명

- **왜 features부터 시작하나?**
  - 요구사항(유즈케이스)의 경계를 먼저 고정하면, 이후에 재사용/분리(entities/shared/widgets)로 이동할 때 기준이 명확해집니다.
  - 반대로 `pages`에 로직이 쌓이면 “다른 화면에서 재사용” 시점에 분리 비용이 급증합니다.

실무 팁

- 처음부터 완벽한 구조를 만들기보다, **일단 features에 두고** 2회 재사용 시점에 올리는 방식이 안정적입니다.

### 1-2) 2번째 재사용 시점에 "공통으로 분리"

- 동일/유사 코드가 **2곳에서** 쓰이기 시작하면 공통화 후보로 보고 분리합니다.
  - 도메인 규칙/표현/계산/selector → `entities/<entity>`
  - 도메인 비의존 공통 → `shared/*`
  - 여러 조합(UI 블록) 반복 → `widgets/*`

추가 설명(판단 기준)

- **entities**: 도메인(업무) 의미가 있는 규칙/표현/상태(예: 사용자 상태 표시, 메뉴 트리 빌더)
- **shared**: 도메인과 무관한 범용 유틸/컴포넌트(예: 날짜 포맷터, debounce, 공용 버튼 스타일)
- **widgets**: “조합된 블록”이 반복될 때(예: 검색바+그리드+페이지네이션 세트)

### 1-3) 외부는 Public API만

- 슬라이스 외부(상위 레이어)에서는 **슬라이스 루트 `index.js`(Public API)로만** import 합니다.
- 내부(같은 슬라이스)는 상대경로 import를 허용합니다.

추가 설명

- Public API를 강제하면 내부 폴더 구조(`ui/model/api`)를 리팩터링해도 사용처 영향이 최소화됩니다.
- deep import를 허용하면 “사용처가 내부 구현에 종속”되어 구조 변경이 어려워집니다.

## 2. 레이어 구조

```txt
app -> pages -> widgets -> features -> entities -> shared
```

- **app**: 앱 초기화/전역 프로바이더/전역 설정
- **pages**: 라우트 단위 화면
- **widgets**: 여러 페이지에서 재사용되는 "블록 단위 조립 UI"
- **features**: 유저 도메인/유즈케이스 단위
- **entities**: 도메인 엔티티 단위
- **shared**: 도메인 비의존 유틸/컴포넌트/설정

추가 설명

- 레이어는 “의존성 방향”을 강제하기 위한 장치입니다. 상위 레이어는 하위 레이어를 자유롭게 조합할 수 있고, 하위 레이어는 상위를 모르게 만들어 **순환 의존/결합**을 방지합니다.

---

## 3. 디렉토리 규칙

기본 구조

```txt
src/<layer>/<slice>/<segment>/...
```

- layers: `app | pages | widgets | features | entities | shared`
- segments(공통): `ui | model | api`

`shared`에서 자주 쓰는 segment 예시

```txt
shared/ui | shared/lib | shared/model | shared/api | shared/config | shared/assets
```

추가 예시(슬라이스 기본 형태)

```txt
features/menu/manage/
  ui/Section.jsx
  ui/Editor.jsx
  model/useSection.js
  api/api.js
  index.js
```

## 4. 네이밍 규칙

- 폴더명: `kebab-case`
- JS 파일: `camelCase.js`
- React 컴포넌트: `PascalCase.jsx`
- 커스텀 훅: `useSomething.js`
- 슬라이스 루트 엔트리: `index.js`

슬라이스 내부 파일명은 "폴더 문맥을 신뢰"합니다.

```txt
features/user/create/
  ui/Form.jsx
  model/useSubmit.js
  api/api.js
  index.js
```

추가 설명

- 파일명이 너무 구체적으로 길어지기보다, “폴더가 문맥을 제공”하도록 설계합니다.
  - 예: `features/user/create/ui/Form.jsx`는 `UserCreateForm`으로 export

## 5. 의존성 규칙

### 5-1) 레이어 의존
```txt
shared → entities → features → widgets → pages → app
```
- **하위 레이어는 상위 레이어를 import 하면 안 됩니다.**
- 상위 → 하위 방향만 허용됩니다.

예)

- `pages`는 `widgets/features/entities/shared` 사용 가능
- `entities`는 `features/widgets/pages/app` import 불가

### 5-2) 슬라이스 의존(Cross-slice)

- **같은 레이어 내 다른 슬라이스 import 금지**
- 조립이 필요하면 상위 레이어에서 조립합니다.
- 공통이 필요하면 `shared`(또는 `entities`)로 분리합니다.

자주 하는 실수와 해결

- 실수: `features/a`에서 `features/b`를 import해서 재사용하려고 함 ❌  
  해결: 상위 레이어(`pages`/`widgets`)에서 조립하거나, 공통 부분을 `shared`/`entities`로 올립니다.

### 5-3) 세그먼트 의존

- `ui -> model, api` (가능)
- `model -> api` (가능)
- `api -> ui, model` (금지)

추가 설명

- `api`는 “순수 통신/데이터 접근” 레이어라 UI/상태에 의존하면 테스트/재사용이 어려워집니다.
- UI에서 필요한 변환/검증은 `model`에서 수행하고, `api`는 요청/응답만 담당합니다.

#### 예시 (pages는 features/shared 사용 가능)

> 실제 예시: `src/pages/menu-management/ui/MenuManagementPage.jsx`

```jsx
import { WiniGridItem, WiniGridLayout } from '@/shared/ui/wini';
import { WiniFormNormal } from '@/shared/ui/blocks/form-layout';
import { MenuManagementSection } from '@/features/menu/manage';
import { ProgramManagementSection } from '@/features/program/manage';
import { MenuProgramMapper } from '@/features/menu/program-mapping';
import { useMenuManagementPage } from '../model/useMenuManagementPage';

export const MenuManagementPage = (props) => {
  const {
    isSmallScreen,
    onSuccess,
    menuSection,
    programSection,
    handleRemovePrograms,
    handleAddPrograms,
  } = useMenuManagementPage(props);

  return (
    <WiniFormNormal>
      <WiniGridLayout container>
        <WiniGridItem item size={{ md: 5, xs: 12 }}>
          <MenuManagementSection onSuccess={onSuccess} menuSection={menuSection} />
        </WiniGridItem>

        <MenuProgramMapper
          isSmallScreen={isSmallScreen}
          onRemovePrograms={handleRemovePrograms}
          onAddPrograms={handleAddPrograms}
        />

        <WiniGridItem item size={{ md: 6, xs: 12 }}>
          <ProgramManagementSection onSuccess={onSuccess} programSection={programSection} />
        </WiniGridItem>
      </WiniGridLayout>
    </WiniFormNormal>
  );
};
```

## 6. Import / Export 규칙

### 6-1) 경로 규칙

- `@/`는 `src/`를 가리킵니다.
- **슬라이스 외부**: `@/` 절대경로 사용
- **슬라이스 내부**: `../model/*` 같은 상대경로 사용

#### 예시

```js
// ✅ 외부 import (features/shared)
import { WiniFormNormal } from '@/shared/ui/blocks/form-layout';
import { ManageGroupUsersSection } from '@/features/authorization/manage-group-users';

// ✅ 슬라이스 내부 import (pages 내부 model)
import { usePermissionGroupUserPage } from '../model/usePermissionGroupUserPage';
```

### 6-2) Public API 규칙

- `pages`를 제외한 모든 레이어는 **Named export만 허용**합니다. (default export 금지)
- **슬라이스 외부에서는 슬라이스 루트 `index.js`로만 import**합니다. (deep import 지양)

#### ✅ 허용 (Public API)

```js
import { UserCreateForm, useUserCreate } from '@/features/user/create';
import { UserStatusChip } from '@/entities/user';
```

#### ❌ 금지 (deep import)

```js
import { Form } from '@/features/user/create/ui/Form.jsx';
import { useSubmit } from '@/features/user/create/model/useSubmit.js';
```

> 현재는 ESLint 등으로 강제하지 않고, **문서/리뷰로만** 운영합니다.

추가 가이드(권장)

- `index.js`에서 export 이름은 **사용처 관점**에서 명확하게(충돌 방지 위해 prefix 권장)
  - 예: `Editor` → `MenuManagementEditor`, `Section` → `MenuManagementSection`
- export는 **UI / Model / API** 순서로 묶어두면 찾기 쉽습니다.

#### `index.js` 작성 예시 (UI/Model export를 한곳으로)

> 실제 예시: `src/features/menu/manage-actions/index.js`

```js
// Model - Hooks
export { useProgramList as useMenuProgramList } from './model/useProgramList';
export { useActionList as useMenuActionList } from './model/useActionList';
export { useEditor as useMenuActionEditor } from './model/useEditor';
export { useSourceLoader as useMenuSourceLoader } from './model/useSourceLoader';

// UI
export { SearchBar as MenuProgramSearchBar } from './ui/SearchBar';
export { ProgramGrid as MenuProgramGrid } from './ui/ProgramGrid';
export { ProgramInfo as MenuSelectedProgramInfo } from './ui/ProgramInfo';
export { TypeFilter as MenuActionTypeFilter } from './ui/TypeFilter';
export { ActionGrid as MenuActionGrid } from './ui/ActionGrid';
export { Editor as MenuActionEditor } from './ui/Editor';
export { Buttons as MenuActionButtons } from './ui/Buttons';
```

### 6-3) pages 예외 규칙

- `pages`는 동적 라우팅 로더 요구사항 때문에 **default export만** 사용합니다.

```js
// pages/users/index.js
export { UsersPage as default } from './ui/Page.jsx';
```

## 7. 작업 패턴

### 7-1) 새 페이지 만들기(개발 관점)

> 라우팅/메뉴/권한 등록은 별도 가이드에서 진행합니다.

1. `pages/<route>/ui/<route>Page.jsx` 생성 (컴포넌트)
2. `pages/<route>/index.js`에서 **default export**
3. 페이지는 가능한 한 "조립"만 담당합니다.
   - 반복되는 블록은 widgets로 올립니다.
   - 유즈케이스 로직은 features로 내립니다.

추가 팁

- 페이지에서 로직이 커지면 먼저 `pages/<route>/model/*`로 내리고, 같은 로직이 다른 페이지에서도 필요해지면 `features`로 이동합니다.

---

### 7-2) 새 기능 만들기(Feature-first)

1. `features/<domain>/<usecase>/` 생성
2. `ui/`, `model/`, `api/`에서 필요한 파일만 작성
3. `index.js`에서 외부에 노출할 것만 Named export

예시

```txt
features/user/create/
  ui/Form.jsx
  model/useSubmit.js
  api/api.js
  index.js
```

```js
// features/user/create/index.js
export { Form as UserCreateForm } from './ui/Form.jsx';
export { useSubmit as useUserCreate } from './model/useSubmit.js';
```

---

### 7-3) "2곳 재사용"이 보이면 분리하기

#### A) 도메인 공통 → entities로 분리

- 예: 사용자 상태 뱃지, 사용자 표시 이름 규칙, 공용 selector, 공용 API

```txt
entities/user/
  ui/StatusChip.jsx
  model/getDisplayName.js
  api/userApi.js
  index.js
```

#### B) 도메인 비의존 공통 → shared로 분리

- 예: `useDisclosure`, `debounce`, `Modal`, `Table`, `formatDate` 등

#### C) 조합 블록 반복 → widgets로 분리

- 예: "사용자 테이블 + 툴바 + 필터 UI"가 여러 페이지에서 반복된다면 `widgets/user-table` 고려

#### D) API 중복 → entities로 분리
- API는 필요에 따라 어느 레이어에도 둘 수 있지만, 보통 **features**에 먼저 작성합니다.
- `features`에서 만든 API 호출 로직이 **2곳에서 재사용**되면 `entities/<entity>/api/<entity>Api.js`로 분리하여 공용화합니다.

## 8) pages는 “조립”만 하고, 로직은 `model` 훅으로 분리

### 규칙

- `pages/*/ui/*Page.jsx`는 레이아웃/섹션 조합만 담당합니다.
- 데이터 조회/변환/이벤트 묶음은 `pages/*/model/*` 또는 `features/*/model/*`로 이동합니다.

추가 설명(어디로 둘지 기준)

- **페이지 전용**(해당 라우트에서만 쓰는 상태/핸들러) → `pages/<route>/model/*`
- **유즈케이스 재사용 가능**(다른 화면에서도 쓰일 가능성 높음) → `features/<domain>/<usecase>/model/*`

### 예시 (form + grid 조합 / hooks는 feature에서 제공)

> 실제 예시: `src/pages/menu-request-permission/ui/MenuRequestPermissionPage.jsx`

```jsx
import { WiniFormNormal } from '@/shared/ui/blocks/form-layout';
import { WiniGridLayout, WiniGridItem } from '@/shared/ui/wini';
import { winiCom } from '@/shared/lib';
import {
  MenuProgramSearchBar,
  MenuProgramGrid,
  MenuSelectedProgramInfo,
  MenuActionTypeFilter,
  MenuActionGrid,
  MenuActionEditor,
  MenuActionButtons,
  useMenuProgramList,
  useMenuActionList,
  useMenuActionEditor,
  useMenuSourceLoader,
} from '@/features/menu/manage-actions';

export const MenuRequestPermissionPage = (props) => {

  const { listView, searchPg, selectedData, handleSearchChange, handleSearch, handleProgramSelect } =
    useMenuProgramList();

  const { refActionGrid, actionAllList, actionList, actionTypeFilter, setReloadId, handleFilterChange, loadActionList } =
    useMenuActionList(selectedData.id);

  const { formRef, selectedActionData, handleActionSelect, handleChange, handleReset, handleSave, handleDelete } =
    useMenuActionEditor(selectedData, (reloadId) => {
      loadActionList();
      if (reloadId) setReloadId(reloadId);
    });

  const { loadFromSource } = useMenuSourceLoader(selectedData, actionAllList, () => {
    loadActionList();
  });
  return (
    <WiniFormNormal id={props.formid}>
      <WiniGridLayout container columnSpacing={2}>
        <WiniGridItem>
          <MenuProgramSearchBar searchValue={searchPg} onSearchChange={handleSearchChange} onSearch={handleSearch} />
          <MenuProgramGrid rowData={listView} onSelectionChanged={handleProgramSelect} />
        </WiniGridItem>

        <WiniGridItem ratio={1.5}>
          <MenuSelectedProgramInfo programCode={selectedData.code} programName={selectedData.name} />
          <MenuActionTypeFilter value={actionTypeFilter} onChange={handleFilterChange} />
          <MenuActionGrid ref={refActionGrid} rowData={actionList} onSelectionChanged={handleActionSelect} />
          <MenuActionEditor
            ref={formRef}
            actionData={selectedActionData}
            selectedProgramData={selectedData}
            actionAllList={actionAllList}
            onChange={handleChange}
            onReset={handleReset}
            onSave={handleSave}
            onDelete={handleDelete}
            onLoadFromSource={loadFromSource}
          />
          <MenuActionButtons
            selectedProgramId={selectedData.id}
            selectedActionId={selectedActionData.programActionId}
            onReset={handleReset}
            onSave={handleSave}
            onDelete={handleDelete}
          />
        </WiniGridItem>
      </WiniGridLayout>
    </WiniFormNormal>
  );
};
```

```txt
    model/getDisplayName.js
    index.js

```

### 9-2) 페이지는 조립만

- `pages/users/ui/Page.jsx`는 다음을 조립합니다.
  - `widgets/user-table` (테이블 블록)
  - `features/user/create` (생성 폼)
  - `features/user/edit` (수정 폼)
  - `features/user/delete` (삭제 버튼/동작)

> "목록 조회 로직을 어디에 둘지(페이지/위젯/feature)"는 팀 상황에 따라 열어둡니다.  
> 본 예시에서는 `features/user/list`를 만들어 위젯이나 페이지가 호출하도록 구성합니다.

## 10. 개발/리뷰 체크리스트

- [ ] 새 요구사항은 features에서 시작했는가?

- [ ] `api`에서 `ui/model`을 import하지 않았는가?
- [ ] deep import(`.../ui/*`, `.../model/*`) 대신 Public API를 사용했는가?
