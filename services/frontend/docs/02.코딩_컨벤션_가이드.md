## 1) 주석 규칙

### ❌ 금지

- 의미 없는 주석
- 코드를 그대로 반복하는 주석
- 임시/디버깅 목적 주석

### ✅ 허용

- 비즈니스 의도/제약/예외 케이스 설명
- "왜(why)"를 설명 (무엇(what)은 코드로 표현)

### ✅ 소스 기준 예시 (페이지/훅 주석 스타일)

> 페이지는 “조립/레이아웃” 의도를 짧게 남깁니다.

```jsx
/**
 * 메뉴 관리 페이지
 * 섹션들을 조합하여 레이아웃만 구성
 */
export const MenuManagementPage = (props) => {
  // ...
};
```

> 훅은 “무엇을 책임지는지” + 주요 핸들러 블록에 주석을 둡니다.

```js
/**
 * 사용자 목록 조회 및 검색 로직
 */
export const useList = () => {
  /**
   * 사용자 목록 조회
   */
  const handleSelect = async () => {
    // ...
  };

  /**
   * 검색어 입력 시 엔터키 처리
   */
  const handleKeyUpSearch = (e) => {
    // ...
  };
};
```

## 2) 로깅 규칙

### ❌ 금지

- 테스트/디버깅용 임시 로그
- 반복적으로 찍히는 noisy 로그

### ✅ 권장

- 운영에 필요한 핵심 이벤트만 로깅
- 최소 포함 정보: action, entity/id, result, reason

### ✅ 프로젝트 기준(현 상태)

- **업무 코드(`features/`, `pages/` 등)에는 `console.log` 금지** (샘플/실험용 페이지 제외)
- 현재 프론트에서 공용 `logger`가 강제되어 있지 않으므로, “운영 로그”가 필요하면
  - **백엔드 로그/감사 로그**로 남기거나
  - 프론트는 **사용자 피드백(`winiMsg`) + 에러 재throw/상태관리**로 처리합니다.

### ❌ 금지 예시 (디버깅 로그)

> 실제 예시 형태: `console.log(...)`는 커밋 전에 제거

```js
const selectNode = (node) => {
  console.log('Selected node:', node);
};
```

## 3) HTTP 클라이언트 규칙

### 필수 사항

- **신규 코드는 공용 HTTP 클라이언트만 사용** (직접 `fetch/axios` 호출 금지)
- 원소스 위치: `shared/api/http/client.js`
- 타임아웃/헤더/인증/에러 처리는 클라이언트에서 통합 관리
- features(`features/*/api`)는 요청 함수만 선언
- 반환/에러 형태는 프로젝트 표준 준수
- **URL은 항상 리터럴 전체 문자열로 작성** (공용 `BASE_PATH` 상수로 조합 금지). 이유는 아래 "URL을 리터럴로 써야 하는 이유" 참고

### ✅ 소스 기준 예시

#### 예시 A) 일반 조회/저장 -> `winiCom.getFormInfo()`에서 `connector`를 받아 API에 주입

> 실제 예시: `src/features/menu/manage/model/useTree.js`

```js
import { winiCom } from '@/shared/lib';

export const useTree = () => {
  const { connector } = winiCom.getFormInfo();

  const handleSelect = async () => {
    const response = await getMenuTree(connector);
    // ...
  };
};
```

#### 예시 B) 로그인처럼 헤더를 건드려야 하는 케이스 -> 매 호출마다 connector 생성

> 실제 예시: `src/features/auth/login/api/api.js`

```js
import { Communicator } from '@/shared/api';

export const login = async (username, password, organizationId = null) => {
  const connector = new Communicator();
  connector.client.defaults.headers.common['Authorization'] = null;

  const response = await connector.client.post(
    '/api/v1/system/user/login/admin',
    { ipSecurityStatus: 'DISABLE', username, password, organizationId },
  );

  return response.data;
};
```

### URL을 리터럴로 써야 하는 이유

- 시스템관리 > 메뉴관리 > **프로그램별 액션관리**의 "소스에서 가져오기" 기능(`features/menu/manage-actions/model/useSourceLoader.js`)이 각 feature의 `api.js`를 정적 스캔해서 `connector.client.get/post/patch/delete('...')` 같은 **리터럴 문자열 호출**만 정규식으로 찾아 `program_action`(권한 단위)을 자동 등록합니다.
- `const BASE_PATH = '/api/v1/...'` 처럼 상수로 접두사를 조합하면, 정규식이 URL을 통째로 못 읽어(`${BASE_PATH}`가 그대로 캡처됨) 액션 자동탐지가 깨집니다. path param만 `${id}` 형태로 보간하고, 접두사는 항상 각 호출부에 그대로 풀어 씁니다.

```js
// ✅ 올바른 예 — 리터럴 URL, path param만 보간
export const updateDictionaryTerm = async (connector, termId, params) => {
  const response = await connector.client.patch(
    `/api/v1/analysis-design/dictionary-term/${termId}`,
    params,
  );
  return response.data.data;
};

// ❌ 금지 — 공용 상수로 URL을 조합하면 "소스에서 가져오기"가 인식 못함
const BASE_PATH = '/api/v1/analysis-design/dictionary-term';
export const updateDictionaryTerm = async (connector, termId, params) => {
  const response = await connector.client.patch(`${BASE_PATH}/${termId}`, params);
  return response.data.data;
};
```

### 예외) 분석/설계(AD) 도메인 페이지 — connector 선택 기준

`pages/ad-*`(분석/설계 워크스페이스) 화면은 **캔버스 에디터인지 여부**에 따라 connector를 다르게 고릅니다.

- **순수 CRUD 화면**(예: 도메인사전 목록) → **예시 A와 동일**하게 `useEditorTabContext()`(내부적으로 `winiCom.getFormInfo().connector`)로 받은 **탭 전용 connector**를 그대로 씁니다. 실제 예시: `src/features/analysis-design/dictionary-list/api/api.js`.
- **캔버스 에디터 화면**(다이어그램/이벤트스토밍처럼 원본 `infra-designer`에서 그대로 이식된 화면)만 예외적으로 `shared/lib/analysis-design/api.ts`의 전용 싱글턴 래퍼(`apiRequest`/`apiRequestWithMeta`)를 씁니다.

이 둘을 구분하는 이유: AD 워크스페이스는 탭을 keep-alive로 여러 개 동시에 띄워둘 수 있는데, 이식된 캔버스 훅은 탭/Context 개념을 몰라(원본이 단일 에디터 SPA였음) 탭별 connector를 주입받을 수 없습니다. 그래서 이 훅들만 예외적으로 앱 전체에 하나뿐인 모듈 싱글턴 connector를 쓰고, 매 요청 시점에 `workspaceStore`에서 활성 탭을 다시 조회해 `X-Menu-Id`를 직접 실어 보냅니다(그렇지 않으면 숨겨진 다른 탭이 헤더를 덮어씀). 캔버스 상태를 갖지 않는 화면은 이 문제 자체가 없으므로, 굳이 이 전용 래퍼를 쓰지 말고 다른 시스템 화면들과 동일한 방식(예시 A)을 따릅니다.

> 새 AD 화면을 만들 때 판단 기준: "이 화면이 모듈 싱글턴 스토어를 가진 이식 코드인가?" → 아니면(대부분의 신규 화면) 예시 A를 따르세요.

### 예외) OpenCommunicator 사용 기준

- 내부 API 호출은 기본적으로 `connector`(= `Communicator`)를 사용합니다.
- 외부 API 호출 등으로 인해 기본 헤더(`Authorization`, `X-Org-Id`, `X-Menu-Id`)가 방해되는 경우에만 `OpenCommunicator` 사용을 허용합니다.

```js
import { OpenCommunicator } from '@/shared/api';

export const fetchExternal = async () => {
  const openConnector = new OpenCommunicator();
  const response = await openConnector.client.get(
    'https://jsonplaceholder.typicode.com/posts/1',
  );
  return response.data?.data ?? response.data;
};
```

## 4) 에러 처리 & 사용자 피드백

- 에러 표시: **snackbar** 또는 **alert** 중 선택
- 에러 타입 구분: 네트워크/권한/유효성
- 사용자 액션(저장/삭제/제출)에 대한 피드백 필수

**가이드:**

- 전역 에러: 토스트
- 폼 필드 에러: 인라인 메시지

### ✅ 메시지 창(`winiMsg`) 사용 규칙

- **금지**: `window.alert`, `window.confirm` 사용 금지
- **원칙**: 메시지 창은 `@/shared/model`의 `winiMsg`를 사용합니다.
- **순차 처리**가 필요하면 `async/await`로 작성합니다.

#### Alert

- 확인 클릭 시 리턴 값 `"Y"`가 넘어옵니다.

```js
import { winiMsg } from '@/shared/model';

const ans = await winiMsg.showAlert('메세지 내용을 작성해주세요.');
// ans === 'Y'
```

#### Confirm

- 예/아니오 클릭 시 각각 `"Y"` / `"N"`이 넘어옵니다.
- 줄바꿈이 필요하면 `\n`을 사용합니다.

```js
import { winiMsg } from '@/shared/model';

const ans = await winiMsg.showConfirm('메세지 내용을 작성해주세요.\n줄바꿈도 가능합니다.');
// ans === 'Y' | 'N'
```

#### Snackbar

- 짧은 안내/완료 메시지 등 **간단한 표시용**으로 사용합니다.

```js
import { winiMsg } from '@/shared/model';

winiMsg.showSnackbar('잠깐 띄우는 메세지에 사용하세요.');
```

### ✅ 소스 기준 예시 (snackbar/alert)

> 조회/비차단성 에러는 `showSnackbar`

```js
try {
  const data = await fetchUsers(connector);
  // ...
} catch (error) {
  winiMsg.showSnackbar(winiCom.getErrorMessage(error.response?.data?.message));
}
```

> 사용자가 즉시 인지해야 하는 차단성 에러는 `showAlert`

```js
try {
  const data = await fetchUser(connector, userId);
  // ...
} catch (error) {
  winiMsg.showAlert(winiCom.getErrorMessage(error.response?.data?.message));
}
```

## 5) 비동기 상태 관리

네트워크 요청 시 아래와 같은 상태 처리 권장

- **Loading**: 로딩 중
- **Error**: 에러 발생
- **Empty**: 데이터 없음

**권장:** 동일한 상태명과 패턴 사용 (컴포넌트마다 다르게 구현 금지)

### ✅ 소스 기준 예시 (isLoading/error를 훅에서 표준화)

```js
const [isLoading, setIsLoading] = useState(false);
const [error, setError] = useState(null);

const handleSelect = async () => {
  setIsLoading(true);
  setError(null);
  try {
    const data = await fetchUsers(connector);
    // ...
  } catch (error) {
    setError(error);
    winiMsg.showSnackbar(winiCom.getErrorMessage(error.response?.data?.message));
  } finally {
    setIsLoading(false);
  }
};
```

> UI에서는 `isLoading/error/list.length` 조합으로 동일 패턴을 유지합니다.

- 전역 의존 최소화

### ✅ 소스 기준 예시 (Section 컴포넌트는 “UI + props” 중심)

```jsx
      </WiniBox>
    </WiniGridLayout>
```

## 7) Custom Hook

- 네이밍: `useSomething`
- 단일 책임 원칙 준수
- UI 직접 조작 금지 (DOM 조작 등)

### ✅ 권장 구성(소스에서 실제로 쓰는 스타일)

- 상단: `connector`, `useState` 선언
- 중단: handler 함수들 (`handleSelect`, `handleSearchChange` 등) + 필요한 유틸 처리
- 하단: `useEffect`로 초기 로드/의존 변화 처리
- return: UI가 필요로 하는 값/핸들러를 **명확한 이름으로** 반환

```js
export const useList = () => {
  const { connector } = winiCom.getFormInfo();

  const [isLoading, setIsLoading] = useState(false);
  const [error, setError] = useState(null);

  const handleSelect = async () => {
    // ...
  };

  useEffect(() => {
    handleSelect();
  }, []);

  return { isLoading, error, handleSelect };
};
```

## 8. 상태관리 규칙(useState + Zustand)

### 8-1) 기본은 useState

- 대부분의 화면/컴포넌트 상태는 `useState`로 관리합니다.

### 8-2) Zustand는 전역 공유

- 현재는 사용자/메뉴 정보만 전역으로 사용합니다.
- 위치: `shared/model/userStore.js` (예시)

```jsx
import { userStore } from '@/shared/model';

const userId = userStore((s) => s.userId);
const readOnceWithGetState = () => {
  const s = userStore.getState();
  alert(
      ["getState()로 읽기", `userId: ${s.userId}`, `userName: ${s.userName}`, `orgId: ${s.organizationId}`].join(
          "\n"
      )
  );
};
```

> 전역 라이브러리 사용은 팀 단위 검토하에 사용합니다.

## 9) 권한 처리 (필수)

### ✅ 원칙

- 권한 값은 `"ALLOW"` 또는 `"NONE"` 입니다.
- 화면(메뉴) 단위 권한은 `winiCom.getFormInfo()` 또는 `winiCom.getFormAut()`로 가져옵니다.
- **권한에 따라 버튼/기능이 노출/동작**해야 하는 경우 반드시 권한 체크를 적용합니다.

### 예시 A) 현재 화면 권한(`winiAut`) 가져오기

```jsx
import { winiCom } from '@/shared/lib';

const { winiAut } = winiCom.getFormInfo();
```

## 11) 날짜/시간 규칙 (`winiDate`) + UTC 주의사항

### ✅ 원칙

- **`new Date()` 남발을 피하고 `winiDate` 사용**을 우선합니다.
- 백엔드에서 내려오는 시간은 UTC 기반일 수 있어, **표시/비교/검색 전에 변환이 필요**할 수 있습니다.
- 그리드(AG Grid) 날짜 표시는 `valueFormatter`로 변환을 적용하는 것을 권장합니다.

### ✅ `winiDate` 함수 목록 (소스 기준)

> 구현 위치: `src/shared/lib/date.js`  
> `winiDate(value)`는 `dayjs` 객체를 반환하는 래퍼입니다.

- **`winiDate(value)`**: 날짜 값(문자열/Date 등)을 `dayjs`로 변환
- **`winiDate.now()`**: 현재 시각(`dayjs`)
- **`winiDate.dateFormat(dayjsDate, format?)`**: 포맷 문자열로 변환 (format 미지정 시 기본 `YYYY-MM-DD`)
- **`winiDate.addDate(date, amount, opt = 'd')`**: 날짜 더하기/빼기 (`d`=일, `m`=월, `y`=년) → `dayjs`
- **`winiDate.getBetweenDay(fromDate, toDate)`**: 두 날짜 차이를 “일”로 계산(정수)
- **`winiDate.getLastDateofMonth(date)`**: 해당 월의 마지막 날(`dayjs`)
- **`winiDate.getFirstDateofMonth(date)`**: 해당 월의 1일(`dayjs`)
- **`winiDate.dateParse(date)`**: 로케일/타임존 설정 기반 파싱(`dayjs`)
- **`winiDate.dateParseStartOf(date)`**: 해당 일자 00:00:00으로 세팅(`dayjs`)
- **`winiDate.dateParseEndOf(date)`**: 해당 일자 23:59:59로 세팅(`dayjs`)

> 참고: `winiDate.format(...)`는 현재 구현에 없습니다. 포맷팅은 `dateFormat(...)`을 사용합니다.

### ✅ `dateFormat` 포맷 토큰 참고

| Token | 설명 | Token | 설명 | Token | 설명 | Token | 설명 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Y | 01 | D | 1-31 | H | 0-23 | s | 0-59 |
| YYYY | 2001 | DD | 01-31 | HH | 00-23 | ss | 00-59 |
| M | 1-12 | Do | 1st... 31st | h | 1-12 | S | 0-9 |
| MM | 01-12 | A | AM PM | hh | 01-12 | SS | 00-99 |
| MMM | Jan-Dec | a | am pm | m | 0-59 | SSS | 000-999 |
| MMMM | January-December |  |  | mm | 00-59 |  |  |

자주 쓰는 예시:

- **날짜**: `YYYY-MM-DD`
- **날짜+시간**: `YYYY-MM-DD HH:mm:ss`
- **한글 포맷**: `YYYY년도 MM월 DD일 HH시 mm분 ss초`

### 예시 (그리드 날짜 표시 변환)

```jsx
import { winiDate } from '@/shared/lib';

const columnDefs = [
  {
    field: 'startedAt',
    headerName: '시작일시',
    width: 200,
    cellStyle: { textAlign: 'center' },
    valueFormatter: (data) =>
      data.value
        ? winiDate.dateFormat(winiDate(data.value), 'YYYY-MM-DD HH:mm:ss')
        : '',
  },
];
```

### 예시 (자주 쓰는 패턴)

```jsx

// 2) 현재 시각
```

## 15) 통신 암호화

통신 암호화는 **전역 통신 암호화**와 **개별 통신 암호화** 두 가지 방식으로 사용합니다.

- 전역 통신 암호화: `.env`의 `VITE_ENCRYPTION` 값으로 공용 HTTP 클라이언트에 일괄 적용
- 개별 통신 암호화: 특정 요청에서 `requestWithEncryption` 함수를 직접 사용

### 15-1) 전역 통신 암호화

#### ✅ 설정 위치

`.env`에서 설정합니다.

```env
# 암호화 여부 : parameter로 넘어가는 데이터를 암호화합니다.
# true : 암호화 사용
# false : 암호화 사용 안함
VITE_ENCRYPTION=false
```

#### ✅ 적용 기준

- `VITE_ENCRYPTION=true`이면 `Communicator` 내부 HTTP 클라이언트와 전역 `apiClient`에 암호화 interceptor가 설치됩니다.
- `/api/v1/`로 시작하는 요청 중 `data`가 plain object인 경우 암호화 대상입니다.
- 공개키 조회 URL(`/api/v1/system/commonSecurity/generateKeyPair`)은 암호화 대상에서 제외됩니다.
- URL path 또는 query string으로 전달되는 값은 암호화되지 않습니다. 암호화가 필요한 값은 `data` 객체에 담습니다.
- 암호화 적용 시 요청 body는 `{ Enc: '...' }` 형태로 변환되고, 암호화 키/IV는 `X-Enc-Key`, `X-Enc-Iv` 헤더로 전달됩니다.

#### ✅ 사용 예시

전역 암호화가 켜진 상태에서는 기존 공용 HTTP 클라이언트 사용 방식을 유지합니다.

```js
// 소스 위치: `src/entities/user/api/userApi.js`
export const createUser = async (connector, params) => {
  const response = await connector.client.post('/api/v1/system/user', params);
  return response.data;
};
```

#### ✅ 주의사항

- 신규 코드에서 직접 `fetch`/`axios`를 호출하지 않고, 기존 규칙대로 `Communicator` 또는 화면에서 받은 `connector`를 사용합니다.
- 전역 암호화는 `.env` 설정에 따라 한 번에 적용되므로, 개별 API 함수에서 별도 암호화 처리를 중복 작성하지 않습니다.
- path parameter나 query parameter에 민감 정보가 들어가지 않도록 API 설계 단계에서 확인합니다.

### 15-2) 개별 통신 암호화

전역 암호화 설정과 별개로, 로그인/비밀번호 변경처럼 특정 요청만 암호화 흐름을 명시해야 하는 경우 `requestWithEncryption`을 사용합니다.

#### ✅ import

```js
import { requestWithEncryption } from '@/shared/api';
```

#### ✅ 함수 시그니처

```js
requestWithEncryption(connectorOrClient, requestConfig);
```

- `connectorOrClient`: `new Communicator()` 인스턴스
- `requestConfig`: axios request config 형식
  - `method`: 문자열로 작성 (`'get' | 'post' | 'patch' | 'delete'` 등)
  - `url`: 문자열로 작성
  - `data`: 암호화할 plain object payload

#### ✅ 사용 예시 A) 로그인

```js
// 소스 위치: `src/features/auth/login/api/api.js`
import { Communicator, requestWithEncryption } from '@/shared/api';

export const login = async (username, password) => {
  const connector = new Communicator();
  connector.client.defaults.headers.common['Authorization'] = null;

  const response = await requestWithEncryption(connector, {
    method: 'post',
    url: '/api/v1/system/user/login',
    data: {
      ipSecurityStatus: 'DISABLE',
      username,
      password,
    },
  });

  return response.data;
};
```

#### ✅ 사용 예시 B) 비밀번호 변경

```js
// src/entities/user/api/userApi.js
import { requestWithEncryption } from '@/shared/api';

export const changeUserPassword = async (connector, params) => {
  const response = await requestWithEncryption(connector, {
    method: 'patch',
    url: '/api/v1/system/user/changeUserPassword',
    data: {
      oldPassword: params.oldPassword,
      newPassword: params.newPassword,
    },
  });

  return response.data;
};
```

#### ✅ 자동 액션 등록 주의사항

`소스에서 가져오기` 기능은 `requestWithEncryption(connector, { method: '...', url: '...' })` 형태를 인식합니다.

- `method`와 `url`은 옵션 객체에 문자열로 작성합니다.
- URL 안에서 함수 호출을 넣지 않습니다.
- path parameter는 템플릿 리터럴 보간을 사용합니다.

```js
// 추천
await requestWithEncryption(connector, {
  method: 'patch',
  url: `/api/v1/system/user/${id}`,
  data: params,
});

// 비추천: URL 구문 내 함수 호출
await requestWithEncryption(connector, {
  method: 'patch',
  url: `/api/v1/system/user/${user.getId()}`,
  data: params,
});
```

#### ✅ 주의사항

- `data`가 plain object가 아니면 암호화하지 않고 일반 요청으로 처리됩니다.
- 로컬 개발 환경(`localhost`) 또는 `http:` 프로토콜에서는 개별 암호화 함수가 일반 요청으로 처리됩니다.
- `requestWithEncryption`은 내부적으로 전역 암호화 interceptor를 우회하므로, 같은 요청이 중복 암호화되지 않습니다.
