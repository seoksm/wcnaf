## 개요

이 문서는 **백엔드 응답 형식과 프론트엔드 내부 형식 사이를 맞추는 adapter** 수정·연동 방법을 정리합니다.

- **공통 backend**를 쓰는 경우: 파일 받은 그대로 사용이 가능합니다.
- **공통 backend 없이 프론트만** 개발하는 경우: mock JSON과 adapter 변환만 연결해도 로그인·메뉴·화면 권한 흐름을 그대로 사용할 수 있습니다. (4장 참고)
- **다른 backend**를 쓰는 경우: 훅의 API 호출부와 해당 adapter의 변환 로직만 수정하면, UI·페이지 코드는 최대한 유지할 수 있습니다.

## 1. 분류

### 1-1) `authAdapter`, `menuAdapter`

- 인증/인가에 대한 **데이터 형식(interface)** 을 정의합니다.
- 인증/인가 관련 백엔드 응답을 공통 프론트엔드가 쓰는 내부 형식으로 맞춥니다.
- 로그인/로그아웃, 메뉴/권한 어댑터로 나뉩니다.

### 1-2) `httpAdapter`

- 개별 화면 개발 시 각 API 요청에 공통으로 붙는 **요청/응답 규약**을 정의합니다.
- axios 요청 전에 어떤 헤더를 실을지, 응답과 에러를 어떤 공통 구조로 받을지 정리합니다.
- `auth/menu` 처럼 도메인 데이터를 정해진 형식으로 바꾸는 adapter가 아니라, API 호출 자체의 공통 규약을 맞추는 adapter입니다.

## 2. `authAdapter`, `menuAdapter`

### 2-1) 역할

- `authAdapter`는 로그인, 로그아웃, 인증 상태 확인에서 사용하는 데이터 형식을 정의합니다.
- `menuAdapter`는 메뉴 트리와 메뉴 권한 화면에서 사용하는 데이터 형식을 정의합니다.
- 둘 다 이미 우리가 쓰기로 한 내부 interface를 코드로 만든 것입니다.
- `raw response -> 내부 표준 shape` 변환만 담당합니다.

### 2-2) 사용할 수 있는 메서드

`authAdapter`

- `toLoginResult`: 로그인 응답 또는 mock 데이터를 로그인용 표준 형식으로 변환합니다.
- `toLogoutResult`: 로그아웃 응답 또는 mock 데이터를 로그아웃용 형식으로 감쌉니다.
- `toAuthState`: 정규화된 로그인 결과를 기준으로 현재 인증 상태를 계산합니다.
- `getAuthStateFromStorage`: 저장된 `localStorage` 값을 기준으로 현재 인증 상태를 추론합니다.
- `isSessionValid`: 서버에 세션(또는 로그인) 유효 여부를 확인하고 `true` / `false`를 반환합니다. (2-7절 참고)

`menuAdapter`

- `toMenuTreeResult`: 메뉴 목록 응답을 화면에서 사용할 메뉴 트리 데이터 형식으로 변환합니다.
- `toMenuPermissionResult`: 메뉴 권한 응답을 권한 기본값이 보정된 형식으로 변환합니다.

### 2-3) 수정해야 하는 경우

- 백엔드 응답 구조가 달라졌다.
- 동일 의미의 다른 필드명을 내부 표준 필드로 맞춰야 한다.
- 권한 응답에서 일부 status가 누락될 수 있어 기본값 보정이 필요하다.

### 2-4) 수정 방식

1. **훅에서 api 호출 부분을 백엔드에 따라 변경합니다.**
    ```js
    // useMenuTree.js
    const data = menuAdapter.toMenuTreeResult(
        await fetchMenuTree(connector, userId), <-- 이부분을 새롭게 바뀐 백엔드 api로 변경
        firstloadingOpen,
    );
    ```
2. 변경된 백엔드 구조에 맞춰 데이터 변환 로직을 수정하여 adapter에 정의된 고정 shape로 만듭니다.
    ```js
    // menuAdapter.js
    /**
     * @type {{
        * 	toMenuTreeResult: (response: unknown, firstloadingOpen?: boolean) => MenuTreeResult, <-- 고정 res shape
        * 	toMenuPermissionResult: (permission: unknown, menuId?: string | null) => MenuPermissionResult,
     * }}
    */

    export const menuAdapter = {
        // 메뉴 구조 트리
        toMenuTreeResult(response, firstloadingOpen = true) { <-- 변환로직 (이 부분을 수정해야함)
            return {
                data: buildMenuTreeData(normalizeMenuTreeItems(response), firstloadingOpen),
                raw: response,
            };
        },
    };
    ```
    - 누락될 수 있는 필드나 기본값은 adapter 안에서 보정합니다.
    - private helper는 adapter 내부에서만 사용합니다.

### 2-5) 훅과의 관계

- 기존 `useLogin`, `useLogout`, `useMenuTree`, `useMenuPermission` 흐름은 유지합니다.
- 훅은 API를 호출한 뒤 바로 adapter를 호출합니다.
- adapter는 형식만 맞추고, 훅은 상태 저장, 라우팅, 사용자 피드백을 담당합니다.

기본 패턴:

```js
const data = authAdapter.toLoginResult(
  await login(id, password, organizationId),
);
```

mock 패턴:

```js
const data = authAdapter.toLoginResult(
  // await login(id, password, organizationId),
  loginData,
);
```



### 2-6) 개발 mock data
 #### 현재 로그인 및 메뉴 조회 는 mock data로 하고있습니다.
- `src/shared/adapters/data` 아래의 JSON은 최종 반환값이 아니라 **adapter 테스트용 데이터**입니다.
- 테스트를 할 때는 실 API 호출 줄을 삭제하지 말고 주석 처리한 뒤 JSON을 adapter에 넣습니다.

예시:

```js
const data = menuAdapter.toMenuPermissionResult(
  // await fetchMenuPermission(connector, userId, menuId),
  menuPermissionData,
  menuId,
);
```

### 2-7) `isSessionValid` (세션 유효성 확인)

**파일:** `src/shared/adapters/authAdapter.js`

공통 backend의 JWT/세션 흐름이 아닌 경우, `localStorage`에 값만 있어도 실제 로그인이 만료되었을 수 있습니다.  
이때 **서버 기준 세션 유효 여부**를 확인하는 진입점으로 `isSessionValid`를 둡니다.

#### 역할

- 세션 check API(또는 동일 목적 API) 호출 결과를 **`boolean`** 으로 정리합니다.
- `getAuthStateFromStorage`는 **저장값만** 보고 인증 여부를 추론합니다.
- `isSessionValid`는 **서버 응답**을 기준으로 유효 여부를 판별합니다.

#### 현재 구현 (스텁)

```js
// authAdapter.js
isSessionValid() {
  // 세션 check api 호출
  return true;
},
```

- 아직 API 연동 전이며, 항상 `true`를 반환합니다.
- 백엔드 연동 시 이 메서드 안에서 API 호출·응답 판별만 추가하면 됩니다.

#### 연동 시 수정 방식

1. 세션 확인 API를 `features/auth` 등에 추가합니다. (예: `GET /api/v1/system/user/session` — 실제 URL은 백엔드 규약에 맞게 변경)
2. `isSessionValid`를 **async** 로 바꾸고, API 성공/실패에 따라 `true` / `false`를 반환합니다.

```js
// 연동 예시 (형태만 참고)
async isSessionValid() {
  try {
    const connector = new Communicator();
    const response = await connector.client.get('/api/v1/system/user/sessionCheck');
    const payload = response?.data ?? response;
    return payload?.result === 'SUCCESS'; // 백엔드 규약에 맞게 조정
  } catch {
    return false;
  }
},
```

3. 호출 위치는 요구사항에 따라 선택합니다.
   - **앱 진입 시 1회:** `useUserInit`, `AppProvider` 등
   - **API 요청마다:** `src/shared/api/http/client.js` request interceptor
   - **메인 레이아웃 진입 전:** `useAuthenticatedLayout` 마운트 시

```js
// 호출 예시
const isValid = await authAdapter.isSessionValid();
if (!isValid) {
  // 로그인 페이지 이동, localStorage 정리 등
}
```

#### `getAuthStateFromStorage`와의 차이

| 구분 | `getAuthStateFromStorage` | `isSessionValid` |
|------|---------------------------|----------------|
| 기준 | `localStorage` 저장값 | 서버 API 응답 |
| 용도 | 새로고침·직접 URL 진입 시 빠른 추론 | 실제 세션 만료 여부 확인 |
| 반환 | `{ authMode, isAuthenticated, accessToken }` | `boolean` |

> 공통 backend를 그대로 쓰는 경우에는 JWT 갱신·401 처리(`httpAdapter`, `client.js`)만으로 충분할 수 있습니다.  
> **다른 backend**이거나 JSESSION 등 **서버 세션**을 쓰는 경우 `isSessionValid` 연동을 검토합니다.

## 3. `httpAdapter`

### 3-1) 역할

- `httpAdapter`는 화면의 각 API 요청에 공통으로 붙는 요청/응답 규약을 정의합니다.
- axios 요청 전에 어떤 인증 헤더를 실을지, 응답과 에러를 어떤 공통 형식으로 정리할지 담당합니다.
- `authAdapter`, `menuAdapter`처럼 도메인 데이터를 화면 형식으로 변환하는 adapter가 아니라, API 호출 자체의 공통 규약을 맞추는 adapter입니다.

### 3-2) 사용할 수 있는 메서드

- `getAuthHeaders`: 현재 저장된 토큰, 조직, 메뉴 정보를 읽어 공통 인증 헤더 값을 만듭니다.
- `applyRequestAuthHeaders`: 개별 요청의 `config.headers`에 인증 헤더를 주입합니다.
- `applyDefaultAuthHeaders`: axios 인스턴스의 기본 공통 헤더를 설정합니다.
- `applyCommonReturn`: 성공 응답을 `{ result, data, metadata, message, errorCode, errorCodeName }` 형식으로 정규화합니다.
- `shouldForceLogoutOnError`: 에러가 강제 로그아웃 대상인지 판별합니다.
- `normalizeHttpError`: 에러 응답을 공통 에러 형식으로 정규화합니다.
- `resolveHttpErrorHandling`: 로그아웃 필요 여부와 정규화된 에러를 함께 반환합니다.

### 3-3) 수정해야 하는 경우

- 공통 헤더 키가 바뀌었다.
- 토큰, 조직, 메뉴 정보를 읽는 기준이 바뀌었다.
- 공통 응답 포맷이 바뀌었다.
- 에러 payload 구조가 바뀌었다.
- 인증 만료 판별 기준이 `errorCodeName` 또는 HTTP status 기준에서 달라졌다.

### 3-4) 수정 방식

1. **공통 HTTP client에서 `httpAdapter`를 호출하는 부분을 먼저 확인합니다.**
    ```js
    // client.js
    this.client.interceptors.request.use(function (config) {
      applyRequestAuthHeaders(config);
      return config;
    });

    this.client.interceptors.response.use(
      (response) => applyCommonReturn(response),
      (error) => {
        const { shouldLogout, handledError } = resolveHttpErrorHandling(error);
        return Promise.reject(handledError);
      },
    );
    ```
2. 변경된 백엔드 규약에 맞춰 `httpAdapter`의 공통 헤더/응답/에러 정규화 로직을 수정합니다.
    ```js
    // httpAdapter.js
    export const applyRequestAuthHeaders = (config = {}) => {
      const { authorization, orgId, menuId } = getAuthHeaders();
      config.headers = config.headers || {};

      if (authorization) {
        config.headers.Authorization = authorization;
      }

      if (orgId) {
        config.headers['X-Org-Id'] = orgId;
      }

      if (!config.headers['X-Menu-Id'] && menuId) {
        config.headers['X-Menu-Id'] = menuId;
      }

      return config;
    };
    ```
    - 공통 헤더 키 변경은 `getAuthHeaders`, `applyRequestAuthHeaders`, `applyDefaultAuthHeaders`에서 함께 맞춥니다.
    - 응답 구조 변경은 `applyCommonReturn`, `normalizeHttpError`에서 함께 맞춥니다.
    - private helper는 adapter 내부에서만 사용합니다.

### 3-5) client와의 관계

- `httpAdapter`는 개별 화면 훅에서 직접 호출하지 않습니다.
- `src/shared/api/http/client.js`에서 interceptor를 통해 공통으로 사용합니다.
- adapter는 헤더/응답/에러 형식만 맞추고, 실제 메시지 표시, 로그아웃 실행, 리다이렉트는 `client.js` 같은 호출 계층이 담당합니다.

기본 패턴:

```js
this.client.interceptors.request.use(function (config) {
  applyRequestAuthHeaders(config);
  return config;
});
```

응답 패턴:

```js
this.client.interceptors.response.use(
  (response) => applyCommonReturn(response),
  (error) => {
    const { shouldLogout, handledError } = resolveHttpErrorHandling(error);
    return Promise.reject(handledError);
  },
);
```

## 4. 개발 시작에 필요한 가이드 — 로그인 / 메뉴 조회 / 화면 권한 (✨개발시  필수확인✨)

처음 로그인 후 메인 화면 진입까지 adapter가 연결되는 지점입니다.  
백엔드 연동·mock 전환 시 **아래 3개 훅의 API 호출 부분**만 확인하면 됩니다.

| 순서 | 훅 | adapter | mock JSON |
|---|---|---|---|
| 1 | `useLogin.js` | `authAdapter.toLoginResult` | `shared/adapters/data/login.json` |
| 2 | `useMenuTree.js` | `menuAdapter.toMenuTreeResult` | `shared/adapters/data/menu.json` |
| 3 | `useMenuPermission.js` | `menuAdapter.toMenuPermissionResult` | `shared/adapters/data/menuPermission.json` |

공통 패턴:

```js
const data = xxxAdapter.toXxxResult(
  await fetchXxx(...),  // 실 API
  // mockData,           // mock 사용 시: API 줄 주석 + JSON 사용
);
```

### 4-1) 로그인 — `useLogin.js`

**파일:** `src/features/auth/login/model/useLogin.js`

```js
const data = authAdapter.toLoginResult(
  await login(id, password, organizationId), // 공통 backend API
  // loginData,                               // mock: login.json
);
const authState = authAdapter.toAuthState(data);
```
#### [ 로그인 개발시 참고 사항 ]
##### 1. 공통 backend (JWT/세션) — `authState.isAuthenticated === true`

`authAdapter`가 JWT 또는 세션 방식으로 인증 성공을 판별한 경우입니다.

```js
if (authState.isAuthenticated) {
  const userData = data.data;
  const org = userData.userOrganizationList[0];

  if (authState.authMode === 'jwt' && authState.accessToken) {
    localStorage.setItem('jwtsessiontoken', authState.accessToken);
  }
  localStorage.setItem('OrgId', org.organizationId);
  localStorage.setItem('UserId', userData.userId);
  localStorage.setItem('UserName', userData.fullName);
  localStorage.setItem('GroupId', org.userGroupId);

  navigate('/', {
    state: {
      orgId: org.organizationId,
      autId: org.userGroupId,
      username: userData.fullName,
      name: userData.fullName,
      userId: userData.userId,
    },
  });
}
```

##### 2. 공통 backend가 아닌 경우 — `else` 분기

로그인 API가 공통 모듈 형식(`accessToken`, `userOrganizationList` 등)을 반환하지 않으면  
`authState.isAuthenticated`가 `false`가 됩니다. 이 경우 **별도 사용자 조회 API**로 정보를 받아  
localStorage와 `navigate` state를 직접 세팅해야 합니다.

> **주의:** `localStorage`의 `UserId`가 없으면 메인 화면(`useMenuTree`)에서 메뉴 조회가 실행되지 않아 페이지 이동이 불가합니다.

```js
} else {
```

### 4-2) 메뉴 리스트 조회 — `useMenuTree.js`

```js
const loadMenuTree = async () => {
  if (!userId) return;
```

### 4-3) 메뉴 선택 시 권한 조회 — `useMenuPermission.js`

**파일:** `src/features/navigation/authenticated-layout/model/useMenuPermission.js`

메뉴를 선택하면 `selectedMenu`(menuId)가 바뀌고, 해당 메뉴의 화면 권한을 조회합니다.

```js
const loadMenuPermission = async () => {
  if (!userId || !menuId) return;

  try {
    setLoading(true);
    const data = menuAdapter.toMenuPermissionResult(
      await fetchMenuPermission(connector, userId, menuId), // 공통 backend API
      menuId,
      // menuPermissionData,                               // mock: menuPermission.json
    );
    setMenuAuthInfo({ ...data, _menuId: menuId });
  } catch {
    setMenuAuthInfo(undefined);
  } finally {
    setLoading(false);
  }
};
```

- 변환 결과는 `winiAut`(`select`, `insert`, `update` 등)로 변환되어 화면 권한 체크에 사용됩니다.
- 변환 상세: `menuAdapter.toMenuPermissionResult` (2-2절 참고)
- **세션 유효성 확인:** 공통 backend가 아닌 경우, 메뉴/화면 API 호출 전에 `authAdapter.isSessionValid()`로 서버 세션을 확인할 수 있습니다. (상세: [2-7) isSessionValid](#2-7-issessionvalid-세션-유효성-확인))
  - 요청마다 확인: `client.js` request interceptor에서 `await authAdapter.isSessionValid()` 호출
  - 진입 시 1회 확인: `useUserInit` 또는 `useAuthenticatedLayout` 마운트 시 호출
