# S-700·701 대시보드 - 관리자 등록 가이드 및 알려진 제한

## 배경

Step 8 Phase 6(설계문서 `13_화면설계_Step8_Phase6-7.md` §1~2)에 따라 대시보드 위젯 10종을
"데이터의 일이 형태를 결정한다" 원칙으로 구현했다. 원본 기능정의서의 원형차트는 전부
가로 막대·누적 막대·표·미터로 바꿨다(§1 참조) - 종류·위치가 여러 개인데 파이로 그리면
순위 비교가 안 되고, 만료 예정은 분포가 아니라 "지금 무엇을 처리해야 하는가"가 일이라
표가 맞다.

**캐시 없이 실시간 집계** - 설계문서는 위젯 10개를 집계쿼리 1~2개+5분 캐시로 묶는 것을
권장했으나, 이 규모(자산 수천 건)에서는 매 요청 재계산해도 체감 지연이 크지 않다고
판단해 캐시를 두지 않았다(요청에 따른 결정). 캐시 무효화 로직 자체가 없어 구현도 단순하다.

**자산 총계(KPI)는 S-230과 같은 계산을 재사용한다** - `DashboardServiceImpl`이 새 집계
쿼리를 짜는 대신 `DepreciationService.loadStatus(fiscalYear, quarter)`를 그대로 호출한다.
이 덕분에 대시보드 숫자와 감가상각 현황(S-230) 화면 숫자가 항상 일치하고, D7(확정 기간은
스냅샷, 미확정 기간은 실시간 산출)의 의미도 그대로 이어받는다.

## 구현 범위 - 백엔드·프런트엔드 전부 완료

**백엔드**
- `V25__dashboard_widget_config.sql` - 개인별 위젯 표시여부·순서 저장
- `domain/dashboard/` - `DashboardService`(집계 10종 + 설정 조회·저장), 위젯별 정보 DTO
  (`DashboardSummaryInfo`의 중첩 클래스), `DashboardWidgetKey` enum(10종)
- 기존 도메인에 최소 침습으로 집계 쿼리 추가: `TangibleAssetReader`(종류·위치·상태별
  그룹핑), `ExpenseRecordReader`(월별 그룹 합계), `LicenseAssignedUserReader`/
  `LicensePurchaseRecordReader`(라이선스별 그룹핑 + 미연결 배정 카운트), `TicketReader`
  (상태 그룹·SLA초과·최근완료 카운트), `LoanReader`(대여중·연체 카운트),
  `InventoryReader`(진행중 조사 목록) - 새 리포지토리를 따로 만들지 않고 각 도메인이
  이미 소유한 Reader/Repository에 쿼리를 추가했다
- `GET /dashboard/summary`, `GET/PUT /dashboard/widget-config` 3개 API
- 테스트: `DashboardServiceImplTest`(V4 7범주 상한 접기, Q-53 실제액 우선, Q-47 정합성
  비교, 티켓 상태 집계, 월별 추이 순서 - 8건 단위테스트) + 실제 Postgres 통합 테스트
  3건(`TangibleAssetDashboardQueryTest`, `ExpenseRecordDashboardQueryTest`,
  `LicenseDashboardQueryTest`)

**프런트엔드**
- `entities/dashboard` - API + 위젯 레지스트리(10종 키·라벨·기본순서)
- `features/dashboard/{summary,distribution,trend,action,process,settings}` - 위젯별
  컴포넌트. 카드 셸(`WidgetCard`)과 KPI 타일(`StatTile`)은 기존 화면(S-303
  `ProgressSummary`)의 카드 규약(`rounded border border-solid border-gray-200 bg-white`)을
  그대로 따른다
- 차트는 이미 설치돼 있던 `chart.js`+`react-chartjs-2`를 처음으로 실제 사용했다(그 전엔
  전역 등록만 돼 있고 쓰이지 않았음) - 새 의존성 추가 없음
- `pages/dashboard` - S-700 페이지. 배치 순서는 설계문서 그대로: **요약→분포→추세→
  조치필요→프로세스현황**, 소제목으로 구획을 나눠 시각적으로도 드러낸다
- S-701 설정은 체크박스(표시여부) + 위/아래 화살표(순서) + 저장/기본값/취소 모달
- 검증: Playwright로 격리 렌더링(실제 로그인 세션 없이) 후 데스크톱(1440px)·태블릿
  (900px)·모바일(390px) 3개 폭 스크린샷으로 레이아웃 확인 - 확인 과정에서 모바일 KPI
  4칸이 세로 1열로 쌓이는 문제를 발견해 `grid grid-cols-2 sm:grid-cols-4`로 수정
  (설계문서 §2 "KPI 4칸은 2×2")

## 알려진 제한

- **드릴다운은 화면 이동까지만, 필터 전달은 없다** - 설계문서는 "막대·범례·표 행을
  클릭하면 필터가 적용된 목록으로 이동"을 규정했다. 만료 예정의 "목록 보기", 티켓
  현황의 "칸반 보기"는 각각 무형자산 목록·서비스데스크로 이동은 하지만 URL 쿼리로
  필터를 넘기지 않는다 - 대상 화면이 쿼리 파라미터를 읽어 초기 필터를 적용하는 로직까지
  갖추려면 그 화면들도 함께 손대야 해서 이번 범위에서 제외했다. 재도입 시 각 목록
  페이지의 `model` 훅에 초기 필터 파싱을 추가하면 된다.
- **위젯 개인화에 권한 교집합이 없다** - 설계문서(S-701)는 "위젯 목록은 메뉴 접근권한과
  교집합"을 규정했다. 이 앱의 `checkMenuAut`는 현재 활성화된 메뉴/폼 컨텍스트의 권한만
  확인할 수 있고, "이 사용자가 라이선스 메뉴에 접근 가능한가"처럼 임의 프로그램 코드로
  조회하는 API가 없어 그대로 구현할 수 없었다. 대신 표시여부·순서만 개인화하고, 권한
  자체는 대시보드 프로그램 하나에 대한 메뉴 접근권한으로만 걸린다(부분 구현).
- **만료 예정 위젯은 무형자산만 대상** - 설계문서는 라이선스 만료도 함께 다루는 것을
  전제했으나, 스키마 확인 결과 `license`/`license_purchase_record`에는 만료일 컬럼이
  없다(라이선스는 수량 기반이라 Q-48 "만료 경고"가 실제로는 구현되지 않은 상태 -
  이번 단계에서 새로 발견). 무형자산(`intangible_asset.expiry_date`)만 대상으로
  좁혔다.
- **월별 비용추이는 "기타" 계열이 없다** - 설계문서는 렌탈·라이선스·기타 3계열을
  전제했으나 `expense_record.src_type`은 RENTAL/LICENSE 2종만 있어(스키마 확인) 2계열만
  표시한다.
- **위젯 데이터는 캐시 없이 매 요청 재계산** - 위 배경에 적은 대로 의도한 결정이지만,
  자산·라이선스·티켓 규모가 크게 늘면(수만 건 이상) 진입이 느려질 수 있다. 그때는
  `DashboardServiceImpl.loadSummary()` 결과에 Spring `@Cacheable` + TTL을 얹으면 된다
  (계산 로직은 그대로 두고 캐시만 감싸면 됨).
- **`dashboard_widget_config`에 관리 화면이 없다** - 개인화 데이터라 사용자가 S-701에서
  직접 편집하고, 관리자용 별도 조회/편집 화면은 만들지 않았다.

## 관리자 등록 절차 (메뉴관리)

### S-700 대시보드
1. **프로그램 등록**: 프로그램명 `대시보드`, 코드 `SMARTASSET_DASHBOARD`, 매핑
   `dashboard/ui/DashboardPage`
2. **메뉴 매핑**: 최상위 메뉴로 추가(설계문서 경로 `/admin/dashboard`) - 로그인 후 가장
   먼저 보이길 원하면 메뉴 순서를 맨 위로
3. **접근권한 부여**: ADMIN에 체크
4. **API 액션 등록**:

   | HTTP | URI | authType |
   |---|---|---|
   | GET | `/api/v1/smart-asset/dashboard/summary` | SELECT |
   | GET | `/api/v1/smart-asset/dashboard/widget-config` | SELECT |
   | PATCH | `/api/v1/smart-asset/dashboard/widget-config` | UPDATE |

   > ⚠️ 위젯 설정 저장은 **PATCH**다(2026-09-21 이전 버전 문서는 PUT으로 적어뒀으나
   > 오류였다 - 아래 "확인된 동작·발견한 문제" 참조). 이미 PUT으로 등록해뒀다면 다시
   > 등록할 필요 없다 - `auth_type=UPDATE` + URI만 일치하면 되고, HTTP 메서드 자체는
   > `program_action` 테이블에 저장되지 않는다.

5. 대시보드는 `/api/v1/smart-asset/process-config`(대여 현황 위젯 표시 여부 판단용)도
   호출하므로, 해당 API 액션이 이미 등록돼 있는지(프로세스 설정 화면 등록 시 함께
   등록됐을 것) 확인한다.
6. 재로그인 후 위젯 10개가 모두 노출되는지, 설정(⚙) 버튼으로 표시여부·순서를 바꾸고
   저장한 뒤 새로고침해도 유지되는지 확인한다.

  4칸은 2×2" 요구사항). 이 확인·수정 후 프로브 파일은 삭제했다.
- **`WiniBox`를 가로로 나열하면 첫 번째와 나머지의 크기(높이)가 달라지는 문제를
  발견해 수정했다** (사용자 보고로 재확인, 2026-09-21). 원인은 `WiniBox`(`shared/ui/wini/Box/WiniBox.jsx`)에
  기본 내장된 "auto-gap" 규칙 - "같은 부모 밑에서 자신이 첫 번째 WiniBox가 아니면
  `margin-top`을 자동으로 붙인다"(`&:not(:first-of-type)`)는 세로 스택 전용 설계라,
  여러 `WiniBox`를 가로 `flex`/`grid`로 나열하면 첫 항목만 그 여백이 없어 나머지가
  `align-items: stretch` 아래에서 짧게/아래로 밀려 보인다. `WiniGridItem`은 이 규칙이
  없어 안전하다(License/Rental 상세 다이얼로그를 `WiniGridLayout`+`WiniGridItem`으로
  고친 이전 사례와 동일 계열의 문제). 이번엔 반응형 컬럼 분할이 필요 없는 단순
  가로나열이라 `WiniGridItem` 대신 순수 `div`로 바꿔 해결했다 - `StatTile`,
  `WidgetCard`, `ExpiringSoonWidget`의 3버킷 타일, `StatusDistributionWidget`의
  범례 항목, `DashboardSettingsDialog`의 행 내부 두 그룹. Playwright로 각 그룹의
  `getBoundingClientRect()`를 측정해 수정 전/후를 비교 - 수정 후 같은 그룹 안 모든
  요소의 top·height·width가 소수점 이하 오차 내로 완전히 일치함을 확인했다.
  **후속 조치**: 사용자 요청으로 전체 코드베이스를 마저 점검해 같은 패턴을 가진 화면
  8곳을 추가로 고쳤다 - 상세 목록과 점검 방법은 `WiniBox_가로배치_버그.md` 참조.

- **"대시보드 반응형이 전혀 안 되어있다"(사용자 보고, 2026-09-21) - 실제로는 뷰포트
  기준 반응형 자체가 이 레이아웃 구조에서 근본적으로 성립하지 않는 문제였다.**
  `AuthenticatedLayout`(`app/layouts/AuthenticatedLayout.jsx`)은 `isMobile = useMediaQuery(theme.breakpoints.down('sm'))`
  (MUI 기본값 600px) 아래에서만 사이드바를 오버레이로 바꾼다 - 그 위(600px~) 에서는
  사이드바가 고정 280px(`drawerWidth`, `shared/ui/layout/styled.js`)를 항상 차지한다.
  즉 뷰포트가 900px이어도 실제 콘텐츠 폭은 약 600px밖에 안 되는데, Tailwind의
  `md:`/`lg:`(뷰포트 기준) 클래스는 900px 쪽을 보고 다단으로 풀어버려 실제로는 비좁은
  칸에 여러 열을 억지로 채워 넣는 것처럼 보인다 - "반응형이 전혀 안 되는 것처럼" 느껴지는
  이유. 사이드바를 열고 닫을 수도 있어(56px/280px) 고정 보정값을 더하는 방식으로도 못
  맞춘다.
  **조치**: 뷰포트가 아니라 실제 렌더된 콘텐츠 폭을 기준으로 반응형을 판단하도록 CSS
  컨테이너 쿼리(Tailwind v4 네이티브 기능)로 바꿨다. `WiniFormNormal`(모든 페이지가
  쓰는 공용 콘텐츠 래퍼)에 `@container`를 한 번 열어두고, 대시보드의 `md:`/`lg:` 클래스를
  `@min-[Npx]:`로 교체했다 - `WidgetCard`에도 중첩 `@container`를 열어, 카드 내부의
  반응형(예: 티켓현황 KPI 4칸)이 카드 자신의 실제 폭을 기준으로 판단하게 했다.
  **함정 하나 더 발견**: `@container`의 rem 단위는 `@media`와 다르게 브라우저 기본
  루트 폰트크기가 아니라 "지금 실제로 적용된" 루트 폰트크기를 기준으로 계산된다
  (CSS 스펙상 의도된 차이 - `@media`는 항상 초기값 기준이라 이 문제가 없다). 이 앱은
  `main.css`에서 `html { font-size: 62.5% }`를 전역으로 걸어둬서, 이름 있는 컨테이너
  크기(`@md`, `@lg`, `@4xl` 등, 전부 rem 기반)를 쓰면 임계값이 62.5%로 쪼그라든다
  (예: `@4xl`=56rem=896px가 아니라 560px에서 풀림). 그래서 이름 있는 크기 대신
  픽셀 임의값(`@min-[576px]:`, `@min-[672px]:`, `@min-[896px]:`)을 썼다. Playwright로
  가짜 280px 사이드바 + 실제 `DashboardPage` 컴포넌트를 함께 마운트해 900/1100/1440px
  창 폭 3개에서 재현→수정→재확인했고, 마지막엔 실제 `useDashboard`가 부르는
  `connector.client`까지 모킹해 진짜 페이지 컴포넌트 자체로 검증했다(손으로 베낀
  구조를 쓰다 한 번 실수해서 헛짚었었다 - 실제 컴포넌트로 다시 검증).

- **"대시보드 설정 변경 시 오류(smart-asset/dashboard/widget-config 404)" (사용자 보고,
  2026-09-21)** - 위젯 설정 저장 API를 **PUT**으로 구현한 게 원인이었다. 이 플랫폼의
  API 게이트웨이(`services/api-gateway/.../common/filter/AuthorizationFilter.java`
  `getAuthType()`)는 HTTP 메서드를 권한 종류로 매핑할 때 `GET→SELECT`,
  `POST→INSERT`, `PATCH→UPDATE`, `DELETE→DELETE`**만** 처리하고 **PUT은 아예
  처리하지 않는다** - PUT 요청은 `default` 분기로 떨어져 `AUTHTYPE` 쿼리파라미터가
  없으면 무조건 "권한이 없습니다. (3)"으로 거부된다. `program_action`에 아무리
  올바르게 등록해도(실제로 사용자가 이미 4건 모두 정확히 등록해뒀음을 DB로 직접
  확인했다) PUT 요청 자체가 권한 종류를 못 찾아 항상 미인가로 막힌다. 이 프로젝트의
  다른 모든 "수정" API가 PATCH를 쓰는 이유도 이것이었는데, 대시보드 설정 저장만
  실수로 REST 관례(전체 교체=PUT)를 따라 PUT을 썼다가 이 함정에 걸렸다.
  **조치**: `apiSpec.yaml`의 `/dashboard/widget-config`를 `put:` → `patch:`로,
  프런트 `saveDashboardWidgetConfig`를 `connector.client.patch(...)`로 변경. URI와
  `auth_type=UPDATE`는 그대로라 **사용자가 이미 등록해둔 API 액션을 다시 등록할
  필요는 없다**(`program_action` 테이블에는 HTTP 메서드 컬럼 자체가 없음을 DB로
  확인) - 위 "관리자 등록 절차" 표도 PATCH로 정정했다. 백엔드 컴파일·OpenAPI
  재생성 확인.
