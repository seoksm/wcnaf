# S-410~412,420,421 대여 관리 - 관리자 등록 가이드 및 알려진 제한

## 배경

Step 6(Phase 3-2)의 대여 관리. `loan` 테이블(`V18__loan.sql`)에 대여 1건씩 append-only로 쌓이며
(L5), 동시 대여 경쟁(L1)은 이 테이블의 잠금이 아니라 `tangible_asset`의 기존 `@Version` 낙관적
잠금을 그대로 재사용한다 - `TangibleAsset.borrow()`가 `LOANABLE → ON_LOAN` 전이와 함께 그 잠금을
건드리므로, 동시에 같은 자산을 스캔한 두 요청 중 하나만 성공하고 나머지는
`ObjectOptimisticLockingFailureException` → "이미 다른 분이 대여했습니다" 메시지로 정리된다.

연체(L2)는 컬럼이 아니라 `status=ACTIVE AND dueDate < 오늘`로 매 조회 시 계산하는 파생값이다.
Q-38~42(전역 기본 대여기한 7일·승인옵션 OFF·연체 시 차단·연장 1회·동시대여 무제한)는 S-400
(`process_config`)에서 그대로 읽어와 적용한다.

## 대여 승인 옵션(Q-39)의 실제 동작 순서 - "승인 후 대여"가 아니라 "대여 후 승인"

설계문서 흐름도는 "대여가능 → 승인대기 → 대여중"으로 읽혀 승인이 먼저라고 오해하기 쉽지만, 실제
구현은 **QR 스캔 시점에 이미 실물을 가져간 것으로 보고 즉시 `TangibleAsset.assignType`을
`ON_LOAN`으로 바꾼다** - S-420이 "실물 앞에서 QR을 찍어야만 대여한다"고 강제하는 이유가 바로
그 스캔이 곧 물리적 반출의 증거이기 때문이다. Q-39 승인 옵션(`requireApproval`)이 켜져 있으면
그 `loan` 행이 `PENDING_APPROVAL`로 시작할 뿐, 자산 상태 전이 자체는 미뤄지지 않는다 - 승인은
사후 결재(회계/감사 목적)이고, 반려되면 그때 자산을 다시 `LOANABLE`로 되돌린다
(`LoanServiceImpl.rejectLoan`). 이 결정을 몰랐다면 "승인 전인데 왜 이미 대여중으로 보이나"로
헷갈릴 수 있다.

## 이번 구현 범위 - 관리자(S-410~412) + 임직원 모바일(S-420,421) 전부 완료

백엔드·프런트엔드 전부 구현했다. S-420(대여 가능 자산)은 목록에서 "QR 스캔으로 대여하기"를
누르면 연속 스캔 화면으로 전환되고(S-311과 동일한 카메라/디코딩 재사용), 스캔마다
`POST /loan/self`를 호출한다. S-421(내 대여 자산)은 연체 건을 최상단에 강조 표시하고, 반납은
QR 재스캔 후 정상/이상 선택(L3)을 거쳐 `PATCH /loan/{id}/self-return`을 호출하며, 연장은
`PATCH /loan/{id}/self-extend`를 바로 호출한다(한도 초과 시 서버 오류 메시지를 그대로 보여줌).

## 알려진 제한

- **S-412 자산 선택이 정확한 자산코드 입력 + 조회 방식이다.** 별도의 "대여가능 자산만 걸러 보여주는"
  자동완성/피커 엔드포인트를 새로 만들지 않고, 기존 자산 검색(`GET /tangible-asset?keyword=`)에서
  정확히 일치하는 코드를 찾는 방식으로 처리했다. 자산이 실제로 `LOANABLE` 상태가 아니면 서버가
  `TangibleAsset.borrow()`에서 명확한 오류 메시지로 거부한다.
- **S-410에 "관리자 대행" 버튼을 넣었지만, 설계문서가 요구하는 D-day(기한 임박) 강조는 아직 없다.**
  연체(overdue)만 빨간 글씨로 강조하고, "1일 전" 같은 임박 표시는 넣지 않았다.
- **L3의 "이상 반납 시 티켓 자동 생성 제안"은 구현하지 않았다.** 서비스데스크(티켓) 자체가 Step 7에서
  만들어지므로, 지금은 이상 반납 시 자산을 REPAIR로 전환하는 것까지만 한다.
- **알림(신규 대여·연체·승인/반려)은 발송하지 않는다.** 이 프로젝트에 알림 발송 인프라 자체가 아직
  없다(여러 운영 문서에서 반복적으로 언급된 공통 제한).
- **S-421 연장 한도 소진 시 버튼이 사라지지 않는다.** 설계문서는 "소진 시 버튼이 사라지고 문구로
  대체"를 요구하지만, 프런트가 `process_config.maxExtendCount` 값을 따로 조회하지 않아 버튼은
  항상 노출하고 한도 초과는 서버가 반려하며 그 메시지("연장 한도를 모두 사용했습니다")를 그대로
  보여주는 방식으로 단순화했다.
- **L-EMP 모바일 하단 4탭 셸이 아직 없다** (S-310/311과 동일한 기존 제한). S-420/421도 독립된
  화면으로 메뉴에 직접 등록해 진입한다 - "대여" 탭 안에 두 화면을 통합하는 것은 셸 자체가 만들어질
  때 함께 처리한다.

## 관리자 등록 절차 (메뉴관리)

`process-config` 등록과 동일한 방식(`프로세스_설정.md` 참고). 화면 2개를 각각 등록한다.

### S-410 대여 현황
1. **프로그램 등록**: 프로그램명 `대여 현황`, 코드 `SMARTASSET_LOAN`, 매핑
   `loan-management/ui/LoanManagementPage`
2. **메뉴 매핑**: "자산관리" 그룹의 형제 메뉴로 추가 (메뉴-프로그램 매핑 기능 사용)
3. **접근권한 부여**: ADMIN에 체크
4. **API 액션 등록**:

   | HTTP | URI | authType |
   |---|---|---|
   | GET | `/api/v1/smart-asset/loan` | SELECT |
   | POST | `/api/v1/smart-asset/loan` | INSERT |

### S-411 대여 승인대기
1. **프로그램 등록**: 프로그램명 `대여 승인대기`, 코드 `SMARTASSET_LOAN_PENDING`, 매핑
   `loan-pending-approval/ui/LoanPendingApprovalPage`
2. **메뉴 매핑**: 동일하게 "자산관리" 그룹의 형제 메뉴로 추가
3. **접근권한 부여**: ADMIN에 체크
4. **API 액션 등록**:

   | HTTP | URI | authType |
   |---|---|---|
   | GET | `/api/v1/smart-asset/loan/pending` | SELECT |
   | PATCH | `/api/v1/smart-asset/loan/{loanId}/approve` | UPDATE |
   | PATCH | `/api/v1/smart-asset/loan/{loanId}/reject` | UPDATE |

   > S-410 프로그램에 등록한 `GET /loan`(SELECT)과 `POST /loan`(INSERT) 액션도 S-412 모달이 같은
   > 화면(S-410)에서 뜨므로 별도 등록이 필요 없다. 다만 이 코드베이스의 액션 등록은 화면(프로그램)
   > 단위라 - S-411 화면이 `/loan/{loanId}/approve`·`/loan/{loanId}/reject`를 직접 호출하므로 그
   > URI는 S-411 프로그램에도 등록해야 한다.

5. 재로그인 후 두 메뉴 모두에서 정상 노출·동작을 확인한다.

### S-420 대여 가능 자산 (임직원 모바일)
1. **프로그램 등록**: 프로그램명 `대여 가능 자산`, 코드 `SMARTASSET_LOAN_AVAILABLE`, 매핑
   `loan-available/ui/LoanAvailablePage`, **모바일상태: 사용** (S-310/311의 `my-inventory`와
   동일한 임직원 자가서비스 화면이라 관리자 메뉴와 별개로 등록)
2. **메뉴 매핑**: 임직원이 접근 가능한 메뉴 그룹에 추가
3. **접근권한 부여**: 전체 임직원 권한그룹에 체크 (관리자 전용이 아님)
4. **API 액션 등록**:

   | HTTP | URI | authType |
   |---|---|---|
   | GET | `/api/v1/smart-asset/loan/available` | SELECT |
   | POST | `/api/v1/smart-asset/loan/self` | INSERT |

### S-421 내 대여 자산 (임직원 모바일)
1. **프로그램 등록**: 프로그램명 `내 대여 자산`, 코드 `SMARTASSET_LOAN_MY`, 매핑
   `my-loan/ui/MyLoanPage`, **모바일상태: 사용**
2. **메뉴 매핑**: S-420과 동일한 그룹에 추가
3. **접근권한 부여**: 전체 임직원 권한그룹에 체크
4. **API 액션 등록**:

   | HTTP | URI | authType |
   |---|---|---|
   | GET | `/api/v1/smart-asset/loan/my` | SELECT |
   | PATCH | `/api/v1/smart-asset/loan/{loanId}/self-return` | UPDATE |
   | PATCH | `/api/v1/smart-asset/loan/{loanId}/self-extend` | UPDATE |

5. 재로그인 후 실제 모바일 기기(또는 모바일 폭 브라우저)에서 카메라 권한·HTTPS 접속을 확인한다
   (S-311과 동일한 전제 - `vite.config.ts`의 mkcert 인증서, mixed content 회피용 s3-proxy 등은
   대여 사진 첨부가 없어 해당하지 않는다).

## 확인된 동작

- V18 마이그레이션 적용 확인 (`docker exec wcnf-postgres psql -d smart-asset`)
- `smart-asset` 컨테이너 재기동 후 정상 부팅 확인, 기존 테스트 스위트 통과 (available-assets
  엔드포인트 추가 후 재확인 포함)
- 미등록 상태에서 `GET /loan`, `GET /loan/pending`, `GET /loan/available` 직접 호출 시
  `COMMON_UNAUTHORIZED`(403)로 정상 차단 확인
- 프런트엔드 `npm run build` 정상 완료 (`LoanManagementPage-*.js`, `LoanPendingApprovalPage-*.js`,
  `LoanAvailablePage-*.js`, `MyLoanPage-*.js` 청크 생성 확인)
- **발견 후 수정한 버그 1**: 동시 대여 경쟁 시 던져지는 `ObjectOptimisticLockingFailureException`을
  처음엔 `LoanServiceImpl` 메서드 본문 안에서 잡도록 했는데, 이 예외는 `@Transactional` 메서드가
  커밋되며(즉 메서드가 반환된 뒤) 던져져서 실제로는 잡히지 않는 구조였다. `TangibleAssetFacade.
  withConflictTranslation`과 동일하게 `LoanFacade`로 옮겨 고쳤다 - 재컴파일·재기동·테스트로 재확인함.
- **발견 후 수정한 버그 2** (사용자 리포트): `TangibleAsset.borrow()`/`returnFromLoan()`가
  `asset_assignment` 이력을 전혀 남기지 않고 있었다. 유형자산관리(S-212)에서 배정형태를
  PERSONAL/ON_LOAN으로 바꿀 때는 `TangibleAssetServiceImpl.applyUpdate`가 항상 현재 배정을
  `release()`하고 새 배정을 `openAssignment()`로 여는데, `LoanServiceImpl`은 이 단계를 빼먹어서
  자산 상세의 "배정 이력" 탭에 대여 기록이 전혀 보이지 않았다. `LoanServiceImpl`에 동일한
  `openAssignment`/`releaseCurrentAssignment` 로직을 추가해 대여 시작(borrow)·반납(return)·반려
  (reject) 시점에 `asset_assignment` 행을 열고 닫도록 고쳤다.
