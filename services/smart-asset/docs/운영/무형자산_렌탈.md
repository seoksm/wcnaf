# S-500~502 무형자산, S-510~512 렌탈·구독 - 관리자 등록 가이드 및 알려진 제한

## 배경

Step 7(Phase 4-1)의 첫 부분. Q-46 확정대로 무형자산(도메인·인증서·상표권)과 SW 라이선스를
완전히 분리했다 - `intangible_asset` 테이블에는 SW가 들어가지 않는다. 렌탈·구독은
Q-52(지출 원장 공용)·Q-53(예상액·실제액 분리)을 반영했다.

**무형자산의 만료 상태(정상/임박/만료)는 컬럼이 아니라 `expiryDate`에서 매번 계산하는
파생값이다** - L2(대여 연체 파생값)와 동일한 이유. `IntangibleAsset.isExpired()`/
`isNearExpiry()`가 매 조회마다 계산하므로 배치가 실패해도 상태가 어긋나지 않는다.

## 구현 범위 - 백엔드·프런트엔드 전부 완료

- **S-500/501/502** (`intangible-asset-management/ui/IntangibleAssetManagementPage`) - 목록
  (키워드+만료구간 필터, 기본 90일)에서 "무형자산 등록" 모달(S-501)과 행 클릭 시 상세·갱신
  모달(S-502)로 진입. **S-501/502를 별도 화면이 아니라 S-500 안의 모달로 구현했다** -
  대여·확인서와 동일한 이유(메뉴당 프로그램 1개 매핑 구조).
- **S-510/511/512** (`rental-management/ui/RentalManagementPage`) - 목록에서 "렌탈·구독 등록"
  모달(S-511)과 행 클릭 시 상세 모달(S-512, 결제 스케줄 추가·실제금액 확정 포함)로 진입.

## 알려진 제한

- **만료 알림 발송은 구현하지 않았다.** `alert_days`(예: "30,7,3,1")는 목록 압축 표기와 임박
  판정에만 쓰이고, 실제 발송은 이 프로젝트에 알림 인프라 자체가 없어 미구현이다(반복된 공통
  제한). `expiry_alert_rule`을 별도 테이블로 두지 않고 `intangible_asset.alert_days`
  CSV 컬럼으로 단순화한 것도 같은 이유 - 실제 소비자(배치)가 없는 상태에서 정규화 테이블을
  미리 만들 필요가 없었다.
- **S-512의 "지출내역" 탭은 별도로 만들지 않았다.** `expense_record`(Q-52 공용 지출 원장)는
  자체 화면·API가 없다 - 결제 스케줄 확정(`confirmPaymentSchedule`) 시 내부적으로만 upsert되고,
  Step 8 대시보드가 나중에 직접 조회할 대상으로 미리 쌓아두는 용도다. 지금은 결제 스케줄 탭에서
  확정된 실제금액을 보는 것으로 충분하다고 판단했다.
- **S-512는 탭 구조(설계문서 "탭 3") 대신 한 다이얼로그 안에 기본정보+결제스케줄을 세로로
  배치했다.** S-432(확인서 상세)에서도 탭 5개 대신 좌우 2분할로 단순화한 것과 같은 판단.
- ~~결제 스케줄 입력 줄(귀속월/결제일/예상금액)이 순수 텍스트였고, 레이아웃도 깨져 보였다~~
  **(수정 완료, 2단계)** 1차로 텍스트 입력을 `WiniDatePicker`로만 바꿨는데도 여전히 레이아웃이
  깨졌다 - 진짜 원인은 `WiniText`/`WiniSelect`/`WiniDatePicker`를 `ui="column"`으로 쓰면
  내부 `FormControl`이 폭을 항상 `width:100%`로 강제해서, 한 줄에 여러 개를 좁은 고정폭
  `className`(`w-32`, `w-40` 등)으로 나열하면 서로 100% 폭을 다투며 깨진다는 것. 이 앱에서
  여러 필드를 한 줄에 배치하는 유일한 표준 방식은 `WiniGridLayout container` +
  `WiniGridItem size={{ xs: N }}`(합 12)이다 - `AcknowledgementDetailDialog`에서 실제로
  이 조합이 올바르게 렌더링되는 걸 확인한 뒤 `RentalDetailDialog`의 결제 스케줄 줄을 통째로
  이 구조로 바꿨고, mock props로 격리 렌더링한 스크린샷으로 최종 확인했다. 라이선스 상세
  (S-533)의 구매내역/배정/포함SW 줄도 같은 원인·같은 방식으로 고쳤다 - 상세는
  `소프트웨어_라이선스_공급사.md` 참고.

## 확인된 동작 · 발견한 문제

- **`intangible_asset_action_log`에 또 `update_at` 컬럼을 빼먹었다** - V15(inventory_inspector),
  V20(acknowledgement_approval)에 이어 **이번 세션 세 번째로 반복한 동일한 실수**다. append-only
  이력 테이블도 `AbstractEntity`를 상속하는 한 예외 없이 `update_at`이 필요하다는 걸 계속
  잊는다. V22로 컬럼을 보강했다. (다음에 새 이력/로그 테이블을 만들 때는 CREATE TABLE 작성
  직후 `create_at`/`update_at` 둘 다 있는지 먼저 확인할 것.)
- V21(intangible_asset·intangible_asset_action_log·rental_asset·payment_schedule·
  expense_record 5개 테이블) 적용 확인, V22 보강 후 `smart-asset` 컨테이너 정상 부팅 확인,
  기존 테스트 스위트 통과.
- 미등록 상태에서 `GET /intangible-asset`, `GET /rental-asset` 직접 호출 시
  `COMMON_UNAUTHORIZED`(403)로 정상 차단 확인.
- 프런트엔드 `npm run build` 정상 완료 (`IntangibleAssetManagementPage-*.js`,
  `RentalManagementPage-*.js` 청크 생성 확인).
- **(추후 발견) `GET /intangible-asset?withinDays=90` 호출 시 `COMMON_SYSTEM_ERROR`.** 실제
  원인은 PostgreSQL SQLState 42P18 `could not determine data type of parameter $3` -
  `IntangibleAssetRepository`의 `(:expiryBefore IS NULL OR a.expiryDate <= :expiryBefore)`
  처럼 선택 필터 파라미터가 `IS NULL` 위치에서만 쓰이면 Postgres가 prepared statement 파싱
  단계에서 타입을 정하지 못하는 문제였다(Hibernate 5 + pgjdbc 조합, `AssetHistoryRepository.
  findRecentByFilter`의 기존 주석과 동일한 근본 원인 - 그 교훈이 이 리포지토리를 만들 때는
  적용되지 않았었다). keyword/expiryBefore 조건 조합별로 쿼리 자체를 4개로 나눠(null 바인딩에
  의존하지 않도록) 고쳤다 - `IntangibleAssetRepository`/`IntangibleAssetReaderImpl` 수정,
  `IntangibleAssetRepositoryTest`(실제 Postgres 통합 테스트)·`IntangibleAssetServiceImplTest`
  (withinDays 회귀 테스트) 추가로 검증. API 계약(URL·요청·응답 DTO)은 변경하지 않았다.
