# 불용자산 처리(S-240~242) 설계 요약 · 운영 가이드 (V13)

## 배경

S-240(불용자산 목록)·S-241(불용 처리)·S-242(처분 처리)는 설계문서(09_화면설계_Step4)에는
있었지만 구현이 전혀 없었다(`disposal_asset` 테이블·엔티티·컨트롤러·프런트 전부 없음). 이 문서는
그 구현이 실제로 어떤 설계 결정을 내렸는지와, 특히 `DepreciationCalculator`가 기존에 갖고 있던
"S-240 구현 전까지는 불용/처분완료 자산을 전부 상각 제외 처리한다"는 임시 placeholder를 실제 동결
규칙(D4)으로 교체하면서 생긴 트레이드오프를 기록한다.

## 상태 전이 (Q-28)

```
USE / STORAGE / REPAIR --disuse()--> DISUSE --dispose()--> DISPOSED (종결, 되돌릴 수 없음)
                                        |
                                        +--restoreFromDisuse()--> USE
```

- `DISUSE`(불용/처분대기) → `DISPOSED`(처분완료)는 일방향이다. `TangibleAsset.dispose()`는 현재
  상태가 `DISUSE`가 아니면 예외를 던진다.
- `DISPOSED`는 `TangibleAsset.modify()`(일반 수정/일괄 변경/엑셀 업서트가 모두 공유하는 단일
  진입점)에서 두 가지를 강제로 막는다: ① 이미 `DISPOSED`인 자산은 어떤 필드도 못 바꾼다, ②
  일반 수정 경로로 `DISPOSED`로 전환하는 것 자체도 막는다. **처분완료로 가는 유일한 길은
  `dispose()`뿐이다** - `disposal_asset` 행 없는 처분완료 자산이 생기는 것을 원천적으로 방지한다.
- `DISUSE` → `USE` 복귀는 허용한다(Q-28 ① 처분대기 상태만 복귀 허용, 실수로 불용 처리한 경우의
  구제책). `restoreFromDisuse()`는 현재 상태가 `DISUSE`가 아니면 예외를 던진다.
- 불용 전환 시 배정을 강제 해제한다(A1, Step3 규칙) - `disuse()`가 `assignType`을
  `UNASSIGNED`로 정규화하고, 서비스가 활성 배정을 `release()` 처리한다.

## API 계약

| 메서드 | 경로 | 설명 |
|---|---|---|
| `PATCH` | `/tangible-asset/{tangibleAssetId}/disuse` | 불용 처리. `{ reason }`(선택) - 이력에만 남기고 자산 메모는 건드리지 않는다 |
| `PATCH` | `/tangible-asset/{tangibleAssetId}/restore` | 불용 → 사용 복귀 |
| `POST` | `/tangible-asset/{tangibleAssetId}/dispose` | 처분 처리. `{ disposalReasonCode(필수), disposalAmount, counterparty, memo }` |
| `GET` | `/tangible-asset/disposal` | 불용자산 목록. `lifeStatus`(DISUSE\|DISPOSED, 생략 시 둘 다)·`page`·`size`·`sort` |

세 액션 모두 `TangibleAssetFacade.withConflictTranslation`을 거치므로, 다른 요청과 동시에 같은
자산을 수정해 낙관적 잠금(`TangibleAsset.version`)이나 배정 유니크 제약이 충돌하면 "다른 곳에서
이미 이 자산 정보를 변경했습니다" 메시지로 변환된다(Q-16/D8과 동일한 규약).

## 처분손익(Q-26)과 장부가 고정

- `disposal_asset.book_value_at_disposal`은 처분 처리 시점의 장부가를 **그대로 복사해 고정**한다.
  이후 감가상각 스냅샷을 다시 계산해도 이 값은 바뀌지 않는다(설계문서 §4 "나중에 감가상각
  스냅샷을 뒤져 재계산하면 값이 흔들린다"는 요구사항 그대로).
- 처분손익(`DisposalAsset.disposalGainLoss()`) = `disposalAmount - bookValueAtDisposal`.
  `disposalAmount`가 없으면(단순 폐기 등) `null`.
- 목록(S-240)에서는 아직 처분되지 않은 `DISUSE` 행은 `disposal_asset`이 없으므로, 그 시점의
  "현재(동결된) 장부가"를 매번 다시 계산해 보여준다(`TangibleAssetServiceImpl.currentBookValue`).

## D4 동결 규칙과 알려진 한계 (핵심)

**설계 요구사항(D4, 09_화면설계_Step4 §4)**: "불용 처리한 달까지는 상각하고 그 다음 달부터
중단한다." 구현 전에는 `DepreciationCalculator.excludedReason()`이 `DISUSE`/`DISPOSED` 자산을
**어느 분기를 조회하든 무조건 전부 제외** 처리하는 임시 placeholder였다(그마저도 확정된
과거 분기는 스냅샷이 있어 영향받지 않았다). 이번에 `TangibleAsset.lifeStatusChangedAt`(생애상태가
마지막으로 바뀐 시각)을 추가하고, `DepreciationCalculator.calculate()`가 조회 대상 월이
`lifeStatusChangedAt`보다 나중이면 그 시점으로 클램프(`freezeIfNeeded`)하도록 바꿔 실제 D4대로
동작하게 했다.

**트레이드오프 - `lifeStatusChangedAt`은 "가장 최근 전이 시점" 하나만 기억한다.** 상태 변화의
전체 이력(언제 몇 번 불용됐다가 복귀했는지)을 별도 테이블로 남기지 않고, 엔티티에 타임스탬프
컬럼 하나만 두는 가장 단순한 설계를 택했다. 그 결과:

- `DISUSE → USE(복귀) → DISUSE(재불용)` 라운드트립을 거치면, `lifeStatusChangedAt`은 **두 번째
  불용 시점**으로 덮어써진다. 최초 불용 시점은 `lifeStatusChangedAt` 필드만으로는 더 이상 알 수
  없다(단, `asset_history`에 `DISUSE`/`STATUS_CHANGE` 타입 이력이 남으므로 감사 추적 자체는
  가능하다 - 단지 상각 계산이 참조하는 "동결 기준점"은 항상 최신 전이 시점이라는 뜻이다).
- 이는 의도된 단순화다: 회계적으로도 "지금 불용 상태가 된 시점"부터 다시 상각을 멈추는 것이
  합리적이며, 재불용 사이 짧게 복귀했던 기간까지 상각을 계속 멈춰야 한다는 요구사항은 설계문서에
  없다. 만약 향후 그런 요구가 생기면(예: 복귀 기간에도 상각을 멈춰야 한다는 정책으로 바뀌면),
  `lifeStatusChangedAt` 단일 컬럼을 상태 전이 이력 테이블로 확장해야 한다.
- `@Deprecated`로 남긴 `DepreciationCalculator.ExcludedReason.NOT_DEPRECIABLE_STATUS`는 이
  변경 전에 이미 확정되어 저장된 `depreciation_snapshot` 행이 이 값을 갖고 있을 수 있어 호환성
  때문에 열거값만 유지한다 - 새 계산은 더 이상 이 사유를 반환하지 않는다.

  에서 열어볼 수 없었다 - 이 작업 환경에는 브라우저를 직접 조작하는 도구도, `system` 서비스
  API를 호출할 로그인 세션(JWT)도 없어 메뉴 등록과 그 이후의 수동 UI 검증(목록 표시, 복귀/처분
  버튼 동작, 폼 검증 등)은 운영자가 직접 진행해야 한다.

## 마이그레이션(V13) 백필

`tangible_asset.life_status_changed_at`은 `NOT NULL`이라 기존 행에 값을 채워야 했다. 이미
등록된 자산이 "언제 지금 상태가 됐는지"를 정확히 알 방법이 없으므로(과거 이력을 저장하지
않았었다), `create_at`(등록 시각)으로 백필했다 - 기존 `DISUSE`/`DISPOSED` 자산은 실제보다 늦게
동결되어(=등록 시각부터 동결) 상각이 과소 계산될 수 있다는 뜻이다. 마이그레이션 시점에 이미
`DISUSE`/`DISPOSED`였던 자산이 있다면, 운영자가 실제 불용/처분 시점을 알고 있는 경우
`UPDATE tangible_asset SET life_status_changed_at = '<실제 시점>' WHERE tangible_asset_id = '<id>'`로
직접 보정하는 것을 권장한다(자동 보정은 하지 않는다 - 추측으로 회계 수치에 영향을 주는 값을
바꾸지 않는다는 원칙, `자산배정_중복_보정.md`와 동일한 방침).
