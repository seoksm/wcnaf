# S-600~603·610·611 서비스데스크 - 관리자 등록 가이드 및 알려진 제한

## 배경

Step 7 Phase 5. 화면설계 인덱스 문서 기준으로 Step 7은 Phase 4(무형자산·렌탈·라이선스)와
Phase 5(서비스데스크)를 함께 묶은 단계로, Phase 4-1(무형자산·렌탈)·4-2(소프트웨어·라이선스·
공급사)에 이어 이번이 Step 7의 마지막 조각이다.

**티켓이 "완료 잠금"되는 append-only 워크플로우**라는 점이 이 모듈의 핵심이다 - `Ticket.
complete()` 이후에는 `modify()`/`assign()`/`moveStatus()`/`complete()` 전부가
`InvalidParamException`을 던진다(엔티티 단위 테스트로 검증). 잘못 처리된 건은 새 티켓으로
다시 만들고, 이미 생성된 자산은 자산 화면에서 고친다(설계문서 그대로).

**유형별 완료 연쇄 처리(Q-49)** - PURCHASE(신규구매) 티켓을 완료하면 자산 등록(S-212 필수
5개와 동일: 자산명·종류·위치·취득일·취득가액) → 요청자 개인배정(`TangibleAssetService.
createTangibleAsset`이 `currentMemberId`+`assignType=PERSONAL`을 받으면 배정 이력까지
자동으로 열어준다, Step 3에서 확립된 동작 재사용) → 수령확인서 요청
(`AcknowledgementService.requestAcknowledgement`, RECEIPT)이 한 번에 처리된다. RETURN
(라이선스 회수) 티켓을 완료하면 연결된 `LicenseAssignedUser`가 회수된다(잔여 수량 증가).
그 외 유형(REPAIR·REPLACE·EXTEND·DISPOSAL)은 완료 시 상태만 바뀐다 - "기존 자산이 있으므로
상태 변경만"(설계문서 §4)이라는 판단대로, 자산 자체의 `life_status` 변경은 관리자가 자산
화면에서 별도로 한다.

**라이선스 회수 요청 → RETURN 티켓 자동 생성 연동** - S-550(내 라이선스)의 "회수 요청"
버튼이 이제 실제 `Ticket`(RETURN)을 만든다. `LicenseServiceImpl`과 `TicketServiceImpl`이
서로를 직접 참조하면 Spring 순환 참조가 나므로, 이 연쇄는 **Service가 아니라 Facade
계층**(`LicenseFacade.requestRelease`)에서 `LicenseService`와 `TicketService`를 둘 다
주입받아 순서대로 호출하는 방식으로 풀었다 - `TicketServiceImpl → LicenseService`(완료 시
회수)와 `LicenseFacade → TicketService`(요청 시 티켓 생성)는 방향이 달라 순환이 아니다.

## 구현 범위 - 백엔드·프런트엔드 전부 완료

- **S-600/601** (`ticket-management/ui/TicketManagementPage`) - 데스크톱(≥768)은 칸반
  보드(네이티브 HTML5 드래그&드롭, 별도 라이브러리 없음), <768은 자동으로 페이지형 목록으로
  전환한다(설계문서 "C4"). **하나의 페이지 컴포넌트가 반응형으로 두 레이아웃을 다 처리한다** -
  두 화면 ID를 위해 메뉴를 두 개 만들지 않고, `useMediaQuery('(max-width:767px)')` 하나로
  분기했다.
- **S-602** (`TicketDetailDialog`, 목록/칸반 카드 클릭 시 모달) - 담당자 배정(Q-50)·상태
  변경(WAITING/RECEIVED/IN_PROGRESS 사이만)·완료 처리(유형별 연쇄, 위 참고)·코멘트 스레드를
  한 화면에 담았다. 요청자 본인 코멘트는 배경색으로 구분(`isRequester`, 서버가 로그인 사용자
  와 `ticket.requestedBy`를 비교해 계산 - 클라이언트가 스스로 표시하지 않는다).
- **S-603** (`TicketDialog`, 목록 상단 "티켓 등록") - 관리자가 요청자를 직접 지정. 연결
  자산은 S-412(대여 관리자 대행)와 동일한 방식으로 자산코드 조회 후 확정.
- **S-610/611** (`my-ticket/ui/MyTicketPage`) - 임직원 모바일. 목록 + "새 티켓 등록" 모달 +
  코멘트 전용 상세 모달(관리자용 배정·상태·완료 컨트롤은 노출하지 않는다).

## 알려진 제한

- **S-610의 "QR 간편 신청"은 만들지 않았다.** 카메라로 스캔해 바로 티켓을 만드는 플로우
  대신, S-412/S-430과 동일하게 **자산코드를 직접 입력해 조회 확정**하는 방식으로
  단순화했다. QR 스캔 화면(S-217)에 "수리 요청" 액션을 추가하는 것이 정식 경로인데, 이번
  단계 범위에서는 빼고 별도 자산코드 입력 필드로 대체했다.
- **자산 상세(S-211)의 "수리 요청" 버튼은 만들지 않았다.** 기능분석 문서(01번)에 임직원이
  본인 자산 상세에서 바로 수리 티켓을 만드는 흐름이 있는데, S-610(내 티켓 등록)에서 자산코드를
  입력하는 것으로 대체 가능해 별도 버튼은 추가하지 않았다. 필요해지면 TangibleAsset 상세
  화면에 "티켓 등록" 버튼을 추가하고 `tangibleAssetId`를 미리 채워 S-610 다이얼로그를 여는
  정도의 작업이다.
- **대여 반납 이상(L3 "티켓 생성 제안")은 연동하지 않았다.** Loan의 이상 반납 시 자산이
  수리중으로 전환되는 것까지는 이미 되어 있지만(Step 6), 그 시점에 REPAIR 티켓을 자동
  생성/제안하는 UI는 이번 단계에 포함하지 않았다 - 필요하면 반납 처리 다이얼로그에 "수리
  티켓 만들기" 버튼을 추가하고 `createTicketByAdmin`을 호출하면 된다.
- **마일리지/예산 사용 티켓 유형은 없다.** 화면설계 인덱스 §14 "1차 제외분"에 마일리지가
  후속 확장으로 명시되어 있어, `Ticket.Type`에는 원본 기능분석의 6종 중 예산 사용(BUDGET_USE)
  을 빼고 PURCHASE·REPAIR·REPLACE·RETURN·EXTEND·DISPOSAL 6종만 두었다.
- **정정 (2026-09-21, Phase 7 QA 점검에서 발견)**: 이전 버전 문서는 여기서 "알림(상태변경·
  코멘트 시 메일)은 기존 로그 전용 어댑터 그대로다"라고 적어뒀으나 **사실이 아니다** -
  전체 코드베이스(smart-asset·common·system) 어디에도 알림 발송 인프라가 없다. 로그
  전용 어댑터조차 존재하지 않는다(`Notification` 관련 클래스·테이블·`@Async`·
  `@TransactionalEventListener` 전부 0건). 이 오류는 `전수조사_1차구현.md`·
  `대여_관리.md`·`무형자산_렌탈.md`·`수령반납_승인.md` 4개 문서가 이미 일관되게 적어둔
  "알림 발송 인프라 자체가 이 프로젝트에 없다(반복된 공통 제한)"와 상충해 발견됐다.
  즉 서비스데스크 티켓의 상태변경·코멘트 알림은 **발송되지 않는다** - 실제 채널이
  정해지면(Q-7 미정) 인프라 자체(도메인 이벤트 발행 → 비동기 리스너 → 로그 기록,
  N1~N5 규약)를 이번에 처음 만들어야 한다.
- **`ticket_type_config`(유형별 SLA 목표일·자동등록 여부)를 고치는 화면이 없다.** V24에서
  6종 기본값을 시드해뒀고(PURCHASE 7일/REPAIR 3일/REPLACE 5일/RETURN 3일/EXTEND 3일/
  DISPOSAL 5일 - 설계문서에 구체적 일수가 없어 판단해 정한 값), 바꿔야 하면 직접 SQL로
  갱신한다(`expense_record`와 동일한 "화면 없는 내부 테이블" 판단). `default_assignee_id`
  컬럼은 Q-50이 수동배정으로 확정됐으므로 자동배정에 쓰지 않고 예비 컬럼으로만 둔다.
- **목록(S-601) 필터는 keyword(제목)·status 2개뿐이다.** ticketType 필터는 넣지 않았다 -
  `IntangibleAssetRepository` 버그(선택 필터 2개 이상에서 `(:param IS NULL OR ...)`가
  Postgres 파라미터 타입 추론에 실패하는 문제, 42P18)를 다시 겪지 않으려고 조합별 쿼리
  분리 방식을 그대로 따랐는데, 필터가 3개면 조합이 8개로 늘어나 keyword+status 2개까지만
  유지했다. 유형은 목록/카드에 이미 배지로 보이니 화면에서 눈으로 걸러도 된다고 판단했다.

## 관리자 등록 절차 (메뉴관리)

### S-600/601 서비스데스크 (관리자)
1. **프로그램 등록**: 프로그램명 `서비스데스크`, 코드 `SMARTASSET_TICKET`, 매핑
   `ticket-management/ui/TicketManagementPage`
2. **메뉴 매핑**: 최상위 메뉴로 추가(설계문서 경로 `/admin/tickets`)
3. **접근권한 부여**: ADMIN에 체크
4. **API 액션 등록**:

   | HTTP | URI | authType |
   |---|---|---|
   | GET | `/api/v1/smart-asset/ticket/kanban` | SELECT |
   | GET | `/api/v1/smart-asset/ticket` | SELECT |
   | POST | `/api/v1/smart-asset/ticket` | INSERT |
   | GET | `/api/v1/smart-asset/ticket/{ticketId}` | SELECT |
   | PATCH | `/api/v1/smart-asset/ticket/{ticketId}` | UPDATE |
   | PATCH | `/api/v1/smart-asset/ticket/{ticketId}/assign` | UPDATE |
   | PATCH | `/api/v1/smart-asset/ticket/{ticketId}/status` | UPDATE |
   | PATCH | `/api/v1/smart-asset/ticket/{ticketId}/complete` | UPDATE |
   | GET | `/api/v1/smart-asset/ticket/{ticketId}/comment` | SELECT |
   | POST | `/api/v1/smart-asset/ticket/{ticketId}/comment` | INSERT |

### S-610/611 내 티켓 (임직원 모바일)
1. **프로그램 등록**: 프로그램명 `내 티켓`, 코드 `SMARTASSET_TICKET_MY`, 매핑
   `my-ticket/ui/MyTicketPage`, **모바일상태: 사용**
2. **메뉴 매핑**: 서비스데스크와 같은 그룹에 추가(설계문서 경로 `/my/tickets`)
3. **접근권한 부여**: 전체 임직원 권한그룹에 체크 (관리자 전용이 아님)
4. **API 액션 등록**:

   | HTTP | URI | authType |
   |---|---|---|
   | GET | `/api/v1/smart-asset/ticket/my` | SELECT |
   | POST | `/api/v1/smart-asset/ticket/self` | INSERT |
   | GET | `/api/v1/smart-asset/ticket/{ticketId}/comment` | SELECT |
   | POST | `/api/v1/smart-asset/ticket/{ticketId}/comment` | INSERT |

5. 재로그인 후 두 메뉴 모두에서 정상 노출·동작을 확인한다. 특히 칸반 보드는 데스크톱
   폭에서, 목록 대체 화면은 브라우저를 768px 이하로 좁혀서 전환을 확인한다.

## 확인된 동작 · 발견한 문제

- V24(ticket·ticket_comment·ticket_type_config 3개 테이블) 마이그레이션 작성 시 `awk`
  스크립트로 `create_at`/`update_at` 존재를 사전 검증 - 문제 없음 확인.
- **`LicenseFacade`가 `TicketService`를, `TicketServiceImpl`이 `LicenseService`를 서로
  참조하게 되면서 Spring 순환 참조 위험이 있었다.** 실제로는 방향이 달라(Facade→Service,
  Service→Service, 서로 다른 인터페이스) 순환이 아니지만, 설계 단계에서 미리 점검하고
  컨테이너 재기동으로 `BeanCurrentlyInCreationException`이 없는지 직접 확인했다.
- 컴파일 성공, `smart-asset` 컨테이너 재기동 후 정상 부팅 확인(Hibernate
  `ddl-auto=validate` 통과), 기존 테스트 스위트(`./gradlew test`) 통과 + 신규 7건
  (`TicketTest` 4건 - 완료 잠금 불변조건, `TicketServiceImplTest` 3건 - 요청자 기록·
  PURCHASE 연쇄 처리·RETURN 라이선스 회수) 통과.
- 미등록 상태에서 `GET /ticket`, `GET /ticket/kanban`, `GET /ticket/my` 직접 호출 시
  `COMMON_UNAUTHORIZED`(403)로 정상 차단 확인.
- 프런트엔드 `npx eslint`(신규 파일만 대상) 클린, `npm run build` 정상 완료
  (`TicketManagementPage-*.js`, `KanbanBoard-*.js`, `TicketDetailDialog-*.js`,
  `MyTicketPage-*.js` 등 청크 생성 확인).
