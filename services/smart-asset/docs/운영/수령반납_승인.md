# S-430~433,440 수령·반납 승인 - 관리자 등록 가이드 및 알려진 제한

## 배경

Step 6(Phase 3-3)의 마지막 부분. `ack_template`(문구 2종, V19 시드) · `acknowledgement`(요청 1건) ·
`acknowledgement_approval`(승인 단계마다 쌓이는 append-only 증빙, K2/K3) 3개 테이블로 구성된다.

**확인서 "승인"이 곧 자산 상태를 확정하는 트리거다** - 요청 시점이 아니라 승인 시점에
`TangibleAsset`이 바뀐다. 대여의 "대여 후 승인"(`대여_관리.md`)과 같은 이유의 설계다.

- **RECEIPT(수령)**: 임직원이 승인하는 순간 `TangibleAsset.assignPersonal()`이 호출돼 개인배정이
  확정된다(`AcknowledgementServiceImpl.applyCompletionSideEffect`). **요청 시점에는 자산이 아직
  개인배정 상태가 아니어도 된다** - 관리자가 "이 자산을 이 사람에게 줄 예정"이라는 의미로 먼저
  확인서를 요청하고, 임직원이 실제로 받아서 승인하면 그때 배정이 완성되는 흐름이다. 이미
  유형자산관리(S-212/218)에서 개인배정을 끝내놓고 뒤늦게 확인서만 받는 것도 그대로 동작한다
  (같은 사람에게 재확정하는 것은 멱등). 다만 **승인 시점에 이미 다른 사람에게 배정돼 있으면
  거부한다** - 조용히 덮어쓰지 않는다.
- **RETURN(반납)**: 담당자 승인 옵션(`process_config.requireManagerApproval`)이 켜져 있으면
  임직원 승인 후 `PENDING_MANAGER`로 넘어가고, **담당자가 승인하는 순간에야**
  `TangibleAsset.completeReturn()` + `asset_assignment` 이력 해제가 실행된다. 옵션이 꺼져 있으면
  담당자 단계 없이 **임직원 승인 시점에 바로** 같은 처리가 실행되며, 이때 담당자가 지정할 다음
  상태가 없으므로 `process_config.defaultReturnStatus`(S-400 기본 제안값)를 그대로 쓴다.

두 경로 모두 `TangibleAsset.version` 낙관적 잠금과 경쟁하므로, 그 충돌
(`ObjectOptimisticLockingFailureException`)은 트랜잭션 커밋 시점(서비스 메서드가 아니라 그것을
호출하는 지점)에 던져진다는 점도 `대여_관리.md`와 동일 - `AcknowledgementFacade`에
`withConflictTranslation`을 추가해 처리한다.

## 구현 범위 - 백엔드·프런트엔드 전부 완료

- **S-433** (`ack-template-management/ui/AckTemplateManagementPage`) - 문구 2종 탭 전환, 변수
  칩 클릭 삽입(커서 위치), 저장 시 미정의 변수 검출·차단.
- **S-431** (`acknowledgement-management/ui/AcknowledgementManagementPage`) - 목록(상태 필터),
  행 클릭 시 S-432 상세 모달, "확인서 요청" 버튼으로 S-430 모달 진입. **S-430/432를 별도 화면이
  아니라 S-431 안의 모달로 구현했다** - 이 코드베이스가 메뉴 하나당 프로그램 하나를 매핑하는
  구조라, 상세/등록을 위한 별도 라우트를 만들지 않고 기존 등록/처리 다이얼로그 패턴(S-412 등)을
  재사용하는 쪽을 택했다.
- **S-440** (`my-acknowledgement/ui/MyAcknowledgementPage`) - 임직원 본인의 승인대기 목록 ↔
  상세(본문 스크롤 + 체크박스 동의 + 승인) 전환, K4 2단계 확인.

## 알려진 제한

- **RECEIPT 요청 후 승인 전에 자산이 다른 사람에게 배정되면, 승인 시점에 "이미 다른 사용자에게
  배정된 자산입니다" 오류로 거부된다.** 조용히 스킵하거나 강제로 덮어쓰지 않는다 - 의도된 동작.
  이 경우 관리자가 잘못된 확인서 요청을 취소(S-431)하고 다시 요청해야 한다.
- **문서에 들어가는 {{담당자}}/{{대상자}} 이름은 프런트가 넘겨준다.** `smart-asset` 서비스는
  멤버 이름을 모른다(system 서비스 소관, cross-DB) - S-430 요청 시 관리자가 이미 불러온
  사용자 목록에서 이름을 골라 함께 보내는 방식으로 우회했다. 프런트를 거치지 않고 API를 직접
  호출하면 이름 없이 ID만 스냅샷에 남을 수 있다.
- **K2 "접속 IP는 부분 마스킹해 표시하고, 전체 값은 감사 로그에서만 조회"** 중 뒷부분(감사 로그
  전체 조회 화면)은 만들지 않았다. 전체 IP는 DB(`acknowledgement_approval.approver_ip`)에
  그대로 저장되어 있으나, 이를 보여주는 화면이 없다 - 필요해지면 이 컬럼을 그대로 조회하면 된다.
- **K6 "미승인 자산 조회 차단"은 구현하지 않았다.** 차단 대상인 "임직원 내 자산 조회" 화면
  자체가 아직 없다(L-EMP 모바일 셸의 "내 자산" 탭 미구현, 여러 운영 문서에서 반복된 공통 제한).
- **S-431/432 설계문서의 "재발송" 액션은 없다.** 알림 발송 인프라 자체가 이 프로젝트에 없다
  (공통 제한).
- **S-432 담당자 승인의 배정형태 선택지는 UNASSIGNED·SHARED·LOANABLE 3개로 제한했다.**
  PERSONAL/ON_LOAN은 특정 사용자(currentMemberId)가 필요한 배정형태라
  (`TangibleAsset.completeReturn`가 이를 거부한다) 반납 직후 지정할 수 있는 선택지가 아니다.

## 관리자 등록 절차 (메뉴관리)

`process-config`/`대여_관리.md`와 동일한 방식. 화면 3개를 각각 등록한다.

### S-433 확인서 문구 관리
1. **프로그램 등록**: 프로그램명 `확인서 문구 관리`, 코드 `SMARTASSET_ACK_TEMPLATE`, 매핑
   `ack-template-management/ui/AckTemplateManagementPage`
2. **메뉴 매핑**: "자산관리" 그룹의 형제 메뉴로 추가
3. **접근권한 부여**: ADMIN에 체크
4. **API 액션 등록**:

   | HTTP | URI | authType |
   |---|---|---|
   | GET | `/api/v1/smart-asset/ack-template` | SELECT |
   | PATCH | `/api/v1/smart-asset/ack-template/{type}` | UPDATE |

### S-431 확인서 현황 (S-430/432 포함)
1. **프로그램 등록**: 프로그램명 `확인서 현황`, 코드 `SMARTASSET_ACKNOWLEDGEMENT`, 매핑
   `acknowledgement-management/ui/AcknowledgementManagementPage`
2. **메뉴 매핑**: "자산관리" 그룹의 형제 메뉴로 추가
3. **접근권한 부여**: ADMIN에 체크
4. **API 액션 등록**:

   | HTTP | URI | authType |
   |---|---|---|
   | GET | `/api/v1/smart-asset/acknowledgement` | SELECT |
   | POST | `/api/v1/smart-asset/acknowledgement` | INSERT |
   | GET | `/api/v1/smart-asset/acknowledgement/{acknowledgementId}` | SELECT |
   | PATCH | `/api/v1/smart-asset/acknowledgement/{acknowledgementId}/manager-approve` | UPDATE |
   | PATCH | `/api/v1/smart-asset/acknowledgement/{acknowledgementId}/cancel` | UPDATE |

### S-440 확인서 승인 (임직원 모바일)
1. **프로그램 등록**: 프로그램명 `확인서 승인`, 코드 `SMARTASSET_ACKNOWLEDGEMENT_MY`, 매핑
   `my-acknowledgement/ui/MyAcknowledgementPage`, **모바일상태: 사용**
2. **메뉴 매핑**: 임직원이 접근 가능한 메뉴 그룹에 추가
3. **접근권한 부여**: 전체 임직원 권한그룹에 체크
4. **API 액션 등록**:

   | HTTP | URI | authType |
   |---|---|---|
   | GET | `/api/v1/smart-asset/acknowledgement/my` | SELECT |
   | GET | `/api/v1/smart-asset/acknowledgement/my/{acknowledgementId}` | SELECT |
   | PATCH | `/api/v1/smart-asset/acknowledgement/{acknowledgementId}/employee-approve` | UPDATE |

5. 재로그인 후 세 메뉴 모두에서 정상 노출·동작을 확인한다.

## 확인된 동작 · 발견한 문제

- V19(`ack_template`/`acknowledgement`/`acknowledgement_approval` 생성 + 문구 2종 시드) 적용
  중 **`acknowledgement_approval`에 `update_at` 컬럼을 빼먹어 Hibernate 스키마 검증이 시작
  시점에 실패했다** - append-only라 갱신이 없을 거라 판단했지만 `AbstractEntity`를 상속하는
  모든 엔티티는 `@UpdateTimestamp`가 매핑되어 예외 없이 `update_at`이 필요하다. `V15`
  (`inventory_inspector`/`inventory_excluded_member`에서 겪은 동일한 실수)와 같은 방식으로
  `V20`을 추가해 컬럼을 보강했다.
- `smart-asset` 컨테이너 재기동 후 정상 부팅 확인, 기존 테스트 스위트 통과.
- 미등록 상태에서 `GET /ack-template`, `GET /acknowledgement` 직접 호출 시
  `COMMON_UNAUTHORIZED`(403)로 정상 차단 확인.
- ack_template 시드 데이터(수령/반납 2종 기본 문구) 정상 삽입 확인.
- 프런트엔드 `npm run build` 정상 완료 (`AckTemplateManagementPage-*.js`,
  `AcknowledgementManagementPage-*.js`, `MyAcknowledgementPage-*.js` 청크 생성 확인).
