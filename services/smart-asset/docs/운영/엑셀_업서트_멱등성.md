# 유형자산 엑셀 업서트(S-213) 확정(commit) 멱등성/장애 복구 가이드 (V12)

## 배경

기존에는 `excel_commit_request`(commit_id만으로 판단)만으로 중복 처리를 막았는데 다음 한계가 있었다.

- 같은 commitId라도 내용이 다른 요청이 오면 그대로 예전 결과를 돌려주거나 뒤섞일 위험이 있었다.
- stale 검사(미리보기 시점 자산 상태 확인)와 실제 반영 사이에 경쟁 상태(TOCTOU)가 남아 있었다.
- 처리 프로세스가 죽으면 그 commitId가 영구히 `IN_PROGRESS`로 남아 재시도가 불가능했다.
- 일부 행만 반영된 상태에서 죽으면, 재시도 시 이미 반영된 행이 중복 반영될 수 있었다.

## API 계약 변경

이 엔드포인트들(`/tangible-asset/excel/preview`, `/tangible-asset/excel/commit`)은 `apiSpec.yaml`
파이프라인을 쓰지 않는, 파일 업/다운로드 전용 컨트롤러다(`TangibleAssetExcelApiController` 상단
주석 참고) - 손으로 쓴 `TangibleAssetExcelRow`/`TangibleAssetExcelCommitRequest`/
`TangibleAssetExcelCommitResult` DTO를 Jackson이 그대로 직렬화한다. 따라서 apiSpec.yaml 변경은
필요 없고, 이 문서가 그 계약을 대신 기술한다.

- **`TangibleAssetExcelRow`(preview 응답의 행 1개)**: `assetUpdatedAt`(문자열) 필드를 제거하고
  `entityVersion`(정수, `TangibleAsset.version` 그대로)을 추가했다. 프런트엔드는 이 필드를 직접
  읽거나 표시하지 않고 preview→commit 사이에 그대로 되돌려주기만 하므로(불투명 전달), 이 이름 변경
  자체로는 프런트 코드 수정이 필요 없다.
- **commit 요청/응답 형태(`{commitId, rows}` → `{createdCount, updatedCount, skippedCount,
  failedRows}`)는 변하지 않았다.** 다만 `failedRows[].errorMessage`가 이제 원인별로 더 구체적인
  문구(서명 불일치/사용자 없음/자산 없음/버전 불일치 등)를 담으므로, 프런트는 이를 행별로 보여주도록
  개선했다(`ExcelUpsertDialog.jsx`) - 이전에는 실패 건수만 보여주고 공통 안내문 하나만 붙였다.
- commit 실패 시 메시지로 상황을 구분한다(별도 에러 코드 없이 메시지 문자열로 구분되며, 프런트는
  그 메시지를 그대로 보여준다):
  - "동일한 요청이 이미 처리 중입니다. 잠시 후 다시 확인해주세요." - 유효한 lease를 가진 다른
    처리가 진행 중(IN_PROGRESS_ELSEWHERE).
  - "이 확정 번호는 이미 다른 내용의 요청에 사용되었습니다. 새로 미리보기 후 다시 시도해주세요." -
    같은 commitId, 다른 내용(REQUEST_MISMATCH).
  - 행별 `errorMessage`에 "다른 곳에서 이미 이 자산을 수정했습니다. 다시 미리보기해주세요." - 버전
    불일치(stale).

## 상태 전이

### 요청 레벨 (`excel_commit_request`)

```
(없음) --claim()--> IN_PROGRESS --complete()--> COMPLETED (종결, 재사용됨)
                        |
                        +--예상 못한 예외--> FAILED --claim() 재시도--> IN_PROGRESS (attempt_count+1)
                        |
                        +--lease 만료(처리 중 프로세스가 죽음)--> claim() 재시도 시 IN_PROGRESS로 재claim(attempt_count+1)
```

`COMPLETED`만 종결 상태다. `FAILED`와 "lease 만료된 IN_PROGRESS"는 둘 다 "재claim 가능" 상태로,
같은 조건(`request_hash` 일치)에서 재시도가 새로 claim해 처리를 이어간다. `EXPIRED`를 별도 상태값으로
저장하지 않고 "IN_PROGRESS + lease_expires_at 지남"이라는 조건으로만 판단한다 - 그 순간 즉시
재claim으로 전이되는 일시적 조건이라 별도로 영속화할 필요가 없다고 판단했다.

### 행 레벨 (`excel_commit_row`)

```
(없음) --claimRow()--> IN_PROGRESS --completeRow()--> COMPLETED (종결, 재사용됨)
                            |
                            +--예외--> FAILED (종결, 재사용됨 - 같은 commitId 재시도 시 재실행되지 않음)
                            |
                            +--claim 단계에서 프로세스가 죽음--> 다음 claimRow() 시도가 재claim
```

**행 레벨은 COMPLETED와 FAILED 모두 종결(재사용) 상태**다 - 한 번 실패로 확정된 행은 같은 commitId를
아무리 재시도해도 다시 실행되지 않고 그 실패 사유를 그대로 재사용한다. 이는 의도된 설계다: 요청 전체가
`COMPLETED`로 확정된 이후에는 그 결과가 고정되어야 하므로, 그 안의 개별 행도 같은 원칙을 따른다.
**특정 행만 다시 시도하고 싶다면 새로 미리보기해서 새 commitId로 확정해야 한다** - 이것이 "실패한
행의 재시도 가능 여부"에 대한 답이다: 같은 commitId 안에서는 불가능하고(멱등성 보장을 위해 의도적),
새 commitId(=새 preview)로는 언제나 가능하다.

## 트랜잭션 경계

- **요청 전체를 감싸는 트랜잭션은 없다** (`TangibleAssetExcelFacade.commit()` 자체는
  `@Transactional`이 아니다) - 한 행의 실패가 다른 행의 커밋을 막지 않아야 하기 때문이다.
- **행 하나(claim → 재검증 → 자산 등록/수정 → 행 완료 기록)는 정확히 하나의 트랜잭션
  (`@Transactional(propagation = REQUIRES_NEW)`, `ExcelCommitRowExecutor.processInNewTransaction()`)
  안에서 원자적으로 처리된다.** `TangibleAssetService.createTangibleAsset/updateTangibleAsset`은
  기본 전파(REQUIRED)라 이 트랜잭션에 합류하므로, 자산 저장과 행 완료 기록은 항상 함께 커밋되거나
  함께 롤백된다.
- **행 실패 기록(`recordFailure()`)은 반드시 별도의 새 트랜잭션**이어야 한다 - 실패한 시도의
  트랜잭션은 이미 롤백 대상으로 표시돼 있어, 그 안에서 실패를 기록하면 그 기록조차 롤백되기
  때문이다. 이 조정은 트랜잭션이 없는 `ExcelCommitRowProcessor`가 맡는다.
- **`ExcelCommitRowProcessor`(조정)와 `ExcelCommitRowExecutor`(실제 트랜잭션)를 별도 스프링 빈으로
  나눈 이유**: 같은 클래스 안에서 `this.xxx()`로 `@Transactional` 메서드를 호출하면(self-invocation)
  스프링 AOP 프록시를 거치지 않아 트랜잭션 어노테이션이 조용히 무시된다. 두 책임을 별도 빈으로
  분리해 항상 프록시를 통해 호출되도록 했다.
- stale 검사도 트랜잭션 경계와 맞물려 있다: `TangibleAssetServiceImpl.applyUpdate()`가 자산을 다시
  읽은 "직후"(같은 트랜잭션 안, 실제 반영 직전) `expectedVersion`을 비교한다 - 이전처럼 별도 시점에
  검사만 하고 실제 반영은 나중에 다른 트랜잭션에서 하지 않는다. 이 비교 직후부터 실제 UPDATE까지의
  아주 짧은 구간은 `TangibleAsset.version`의 낙관적 잠금이 그대로 커버한다(다른 요청이 먼저
  커밋하면 이 트랜잭션의 UPDATE는 0건 매치로 실패해 `ObjectOptimisticLockingFailureException`이
  발생한다).

## 장애 발생 지점별 복구 방식

| 장애 시점 | 결과 | 재시도 시 동작 |
|---|---|---|
| claim() 직후, 첫 행 처리 전에 프로세스 종료 | 요청이 IN_PROGRESS로 남고 lease가 곧 만료 | lease 만료 후 재claim, 모든 행을 처음부터 처리 |
| N번째 행 처리 중(그 행의 REQUIRES_NEW 트랜잭션 안) 종료 | 그 행은 자산 저장+완료 기록 모두 롤백(원자적) - claim 표시도 함께 사라짐 | 그 행은 "끝나지 않음"으로 보여 다시 claim되어 재처리됨 |
| N번째 행 완료(커밋됨) 직후, N+1번째 처리 전에 종료 | N번째 행은 COMPLETED로 확정, 요청은 IN_PROGRESS로 남고 lease 만료 예정 | 재시도 시 N번째 행은 findFinished로 재사용(재실행 안 함), N+1번째부터 이어서 처리 |
| 모든 행 처리 후, idempotencyStore.complete() 호출 전에 종료 | 모든 행은 COMPLETED, 요청 레벨만 IN_PROGRESS로 남음 | 재시도 시 모든 행이 findFinished로 즉시 재사용되어 순식간에 COMPLETED로 전환 |
| 요청 루프 자체에서 예상 못한 예외(예: DB 커넥션 끊김) | idempotencyStore.fail()이 FAILED로 기록 | FAILED는 재claim 가능 상태이므로 즉시 재시도 가능 |
| completeRow() 자체가 실패(예: DB 순간 장애) | 같은 REQUIRES_NEW 트랜잭션이므로 자산 저장도 함께 롤백 | 그 행은 처음부터 다시 처리됨(중복 없음) |

## 요청 내용 지문(request_hash)

각 행의 `signature`(HMAC, 이미 서버 키로 서명되어 위변조 불가능)를 `rowNum:signature` 형태로 모아
정렬 후 이어붙인 문자열의 SHA-256 해시를 사용한다. signature 자체가 위변조 방지를 담당하므로,
request_hash는 순수하게 "같은 commitId가 재사용될 때 내용이 정말 같은지"만 가린다.

## 행 식별자(row_key)

`rowNum-서명해시앞8바이트` 형태다. rowNum만으로는 재요청 시 내용이 바뀐 행(예: 사용자가 새로
미리보기해서 같은 rowNum에 다른 자산 데이터가 들어온 경우)을 구분할 수 없으므로 서명의 해시를
함께 사용한다.

## 알려진 한계 / 향후 개선 여지

- **lease 기간은 10분 고정이고, 처리 도중 자동 연장하지 않는다.** 최대 2000행(MAX_UPLOAD_ROWS)을
  순차 처리하는 일반적인 경우 충분한 여유지만, 유난히 느린 환경에서 2000행 전체 처리가 10분을
  넘기면 다른 요청이 아직 살아있는 처리를 "죽은 것으로" 오판해 재claim할 수 있다. 필요해지면 행마다
  주기적으로 lease를 연장하는 방식을 검토한다.
- **오래된 완료/실패 요청 보존·정리 정책**: 현재는 `excel_commit_request`/`excel_commit_row`를
  자동으로 정리하지 않는다. 운영에서 데이터가 누적되면, 예를 들어 아래와 같은 정리 SQL을 주기
  배치(예: 매일 새벽)로 실행하는 것을 권장한다(예시 - 실제 보존 기간은 운영 정책에 맞게 조정):

```sql
DELETE FROM excel_commit_row
WHERE commit_id IN (
    SELECT commit_id FROM excel_commit_request
    WHERE status = 'COMPLETED' AND update_at < now() - interval '30 days'
);
DELETE FROM excel_commit_request
WHERE status = 'COMPLETED' AND update_at < now() - interval '30 days';
```

  `FAILED` 상태로 오래 방치된 요청은 자동 삭제하지 말고, 왜 실패가 반복됐는지 먼저 확인 후
  수동으로 정리하는 것을 권장한다(자동 삭제 대상에서 의도적으로 제외).
