# 자산 배정(asset_assignment) 활성 중복 보정 가이드 (V11)

## 배경

지금까지 `asset_assignment`는 자산당 "현재 배정"(`released_at IS NULL`)이 항상 1건이라고 가정했지만,
그 가정을 DB가 강제하지 않는 일반 partial index(`idx_asset_assignment_tangible_asset_current`)만
있었다. 배정 변경/회수 사이의 경쟁 상태(read-then-write race)로 인해 이론상 한 자산에 활성 배정이
2건 이상 쌓일 수 있었다. `V11__asset_assignment_unique_active.sql`은 이를 막기 위해 유니크 인덱스
(`idx_asset_assignment_tangible_asset_active`)로 교체하며, **적용 전 중복이 있으면 마이그레이션
자체를 실패시켜** 운영자가 먼저 수동 보정하도록 한다(임의로 지우거나 종료 처리하지 않는다).

## 1) 사전 점검 - 마이그레이션 적용 전 반드시 먼저 실행

```sql
SELECT tangible_asset_id, COUNT(*) AS active_count
FROM asset_assignment
WHERE released_at IS NULL
GROUP BY tangible_asset_id
HAVING COUNT(*) > 1
ORDER BY COUNT(*) DESC;
```

결과가 0건이면 V11을 그대로 적용해도 안전하다. 1건이라도 있으면 아래 보정 절차를 먼저 진행한다.
(V11 자체도 이 조건을 다시 확인해 중복이 있으면 마이그레이션을 실패시키므로, 이 점검을 건너뛰고
바로 배포해도 안전하게 막히기는 하지만, 배포 실패로 알게 되는 것보다 미리 확인하는 편이 낫다.)

## 2) 중복 상세 확인

```sql
SELECT a.asset_assignment_id, a.tangible_asset_id, t.asset_code, t.asset_name,
       a.member_id, a.assign_type, a.assigned_at, a.assigned_by
FROM asset_assignment a
JOIN tangible_asset t ON t.tangible_asset_id = a.tangible_asset_id
WHERE a.tangible_asset_id IN (
    SELECT tangible_asset_id FROM asset_assignment
    WHERE released_at IS NULL
    GROUP BY tangible_asset_id
    HAVING COUNT(*) > 1
)
AND a.released_at IS NULL
ORDER BY a.tangible_asset_id, a.assigned_at;
```

## 3) 유지할 배정 행을 결정하는 기준

같은 자산에 활성 배정이 여러 건이면, 아래 순서로 "진짜 현재 배정"을 판단한다.

1. **`tangible_asset.current_member_id`와 `member_id`가 일치하는 행을 최우선으로 유지한다** -
   비정규화된 이 컬럼이 화면/조회에 실제로 쓰이고 있으므로, 이미 사용자에게 보여지고 있는 값과
   일치하는 배정 이력을 "진짜"로 간주하는 것이 가장 안전하다.
2. 여러 행이 모두 `current_member_id`와 일치하거나(있을 수 없지만) 아무도 일치하지 않으면,
   **`assigned_at`이 가장 최근인 행**을 유지한다(가장 나중에 실제로 반영된 배정일 가능성이 높다).
3. 그래도 판단이 서지 않으면(예: 완전히 동시에 생성된 것으로 보이는 행들), 자산 담당 부서/현업에
   실제 현재 사용자가 누구인지 확인 후 결정한다 - 시스템 데이터만으로 확신할 수 없는 경우 추측으로
   자동 보정하지 않는다.

## 4) 나머지 배정의 released_at 보정 예시

유지하기로 정한 행(`<keep_id>`)을 제외한 나머지를, 그 유지 행의 `assigned_at`(또는 지금 시각)으로
회수 처리한다.

```sql
-- 자산 하나(<tangible_asset_id>)에 대해, 유지하기로 정한 <keep_id> 이외의 활성 배정을 모두 회수 처리
UPDATE asset_assignment
SET released_at = now()
WHERE tangible_asset_id = '<tangible_asset_id>'
  AND released_at IS NULL
  AND asset_assignment_id <> '<keep_id>';
```

자산이 여러 건이면 위 UPDATE를 자산별로 반복한다(한 번에 일괄 처리하는 스크립트가 필요하면, 2)의
결과를 바탕으로 자산별 "유지 ID" 매핑을 먼저 만들고 나서 실행한다 - 이 매핑 결정 자체를 자동화하지
않는다는 것이 이 절차의 핵심이다).

## 5) 보정 후 확인

```sql
-- 1)과 동일한 쿼리 - 0건이어야 한다
SELECT tangible_asset_id, COUNT(*) AS active_count
FROM asset_assignment
WHERE released_at IS NULL
GROUP BY tangible_asset_id
HAVING COUNT(*) > 1;
```

0건을 확인한 뒤 V11을 적용(배포)한다. 적용 후에는 아래로 유니크 인덱스가 실제로 생겼는지 확인한다.

```sql
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'asset_assignment';
```

`idx_asset_assignment_tangible_asset_active`가 `UNIQUE`로 나타나고
`idx_asset_assignment_tangible_asset_current`는 더 이상 없어야 한다.

## 롤백 / 장애 대응

- **마이그레이션이 중복 때문에 실패한 경우**: 애플리케이션은 기동에 실패한 상태로 남는다(스키마가
  V10에 머무름) - 데이터를 자동으로 어떻게 하지 않으므로 안전하다. 위 1)~5) 절차대로 보정 후 다시
  기동하면 그 시점에 V11이 적용된다. 별도 롤백 스크립트는 필요 없다(아직 아무 것도 바뀌지 않았으므로).
- **유니크 인덱스 적용 이후 문제가 발견된 경우**(예: 정상적인 업무 흐름인데 배정 변경이 막히는
  버그가 나중에 발견된 경우): 인덱스 자체를 걷어내는 롤백은 구조적 안전장치를 다시 제거하는
  것이므로 신중해야 한다 - 우선 애플리케이션 쪽 원인을 먼저 조사한다(TangibleAssetFacade의
  `withConflictTranslation`이 `InvalidParamException`으로 감싸는 지점, `TangibleAsset.version`
  낙관적 잠금 충돌 여부를 로그로 확인). 정말 인덱스 자체가 원인이라고 확인되면
  `DROP INDEX idx_asset_assignment_tangible_asset_active;`로 되돌릴 수 있지만, 이 경우 다시
  중복 활성 배정이 생길 수 있는 원래 문제로 돌아간다는 점을 감안한다.
- **낙관적 잠금 충돌(`ObjectOptimisticLockingFailureException`)이 예상보다 자주 발생하는 경우**:
  같은 자산에 대한 동시 요청 빈도가 예상보다 높다는 신호다 - 사용자에게는 이미
  "다른 곳에서 이미 이 자산 정보를 변경했습니다. 새로고침 후 다시 시도해주세요." 메시지가 나가므로
  기능적으로는 안전하지만, 빈도가 높다면 화면에서 동시 편집을 유도하는 흐름(예: 같은 자산 상세를
  여러 창에서 열어두고 오래 편집)이 있는지 UX 차원에서 점검한다.
