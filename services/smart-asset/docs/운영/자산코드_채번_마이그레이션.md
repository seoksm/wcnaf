# 자산코드(AST-YYYY-NNNN) 채번 백필 - V10 운영 가이드

## 배경

`V6__asset_code_sequence.sql`이 도입한 `asset_code_sequence`(연도별 채번 카운터)는, 그 이전부터
이미 존재하던 `tangible_asset`의 기존 `AST-YYYY-NNNN` 코드를 카운터에 반영하지 않았다. 운영 DB에
이미 이런 기존 코드가 있는 상태에서 카운터 테이블에 해당 연도 행이 없다면, 다음 신규 등록이 다시
`0001`부터 채번을 시도해 기존 코드와 유니크 제약(`tangible_asset_asset_code_key`) 충돌을 일으킬 수
있었다. `V10__asset_code_sequence_backfill.sql`은 기존 코드에서 연도별 최대 순번을 계산해
`asset_code_sequence.last_seq`에 반영한다.

## 사전 점검 SQL - 마이그레이션 전에 먼저 실행

### 1) 정확히 `AST-YYYY-NNNN` 형식인 코드가 연도별로 몇 건, 최대 순번이 얼마인지 확인

```sql
SELECT
    substring(asset_code FROM 5 FOR 4) AS fiscal_year,
    COUNT(*) AS matching_count,
    MAX(substring(asset_code FROM 10 FOR 4)::integer) AS max_seq
FROM tangible_asset
WHERE asset_code ~ '^AST-[0-9]{4}-[0-9]{4}$'
GROUP BY substring(asset_code FROM 5 FOR 4)
ORDER BY fiscal_year;
```

### 2) 형식이 다른("잘못된"/수동 입력) 자산코드 목록 - V10이 조용히 건너뛰는 대상

```sql
SELECT tangible_asset_id, asset_code, create_at
FROM tangible_asset
WHERE asset_code !~ '^AST-[0-9]{4}-[0-9]{4}$'
ORDER BY create_at;
```

이 목록에 나온 행은 V10을 실행해도 채번 카운터 집계에 전혀 반영되지 않는다(마이그레이션이 실패하지도
않는다). 운영팀이 보고 "이 코드들이 실제로 의도된 예외(수동 이관 데이터 등)인지"만 확인하면 된다 -
필요하다면 이 시점에 정책적으로 코드값을 표준 형식으로 정정할 수도 있지만, 그것은 V10과 무관한 별도
데이터 정정 작업이다.

## 마이그레이션 방식 요약 (`V10__asset_code_sequence_backfill.sql`)

- 정규식 `^AST-[0-9]{4}-[0-9]{4}$`(연도 4자리 + 순번 4자리, 그 외 어떤 변형도 불허)으로 필터링한
  `tangible_asset.asset_code`만 대상으로, 연도별 `MAX(순번)`을 집계해
  `asset_code_sequence`에 `INSERT ... ON CONFLICT (fiscal_year) DO UPDATE SET last_seq = GREATEST(...)`한다.
- **형식이 다른 코드는 실패 없이 제외**된다(요구사항 6) - 위 점검 SQL 2)로 별도 확인.
- **이미 해당 연도의 카운터 행이 있으면 `GREATEST(기존값, 집계값)`을 유지**한다(요구사항 5) - 예를
  들어 V6 배포 이후 이미 몇 건이 새 방식으로 채번된 상태였어도 그 값 밑으로 절대 내려가지 않는다.
- 이 마이그레이션은 **멱등적**이다 - 같은 입력에 대해 다시 실행해도(같은 SQL을 재실행해도) 결과가
  줄어들지 않는다(`GREATEST` 덕분). 다만 Flyway는 한 번 적용된 버전을 재실행하지 않으므로, 실제로
  다시 실행되는 경우는 "이 SQL 내용을 그대로 다른 환경에 수동 적용"하는 상황 정도다.
- 기존 코드가 전혀 없는 연도는 이 마이그레이션이 아무 행도 만들지 않으므로, 그 해의 첫 발급은
  `AssetCodeSequencerImpl`의 기존 동작 그대로 `0001`부터 시작한다(요구사항 9).
- 동시 발급의 원자성은 `AssetCodeSequencerImpl`의 `INSERT ... ON CONFLICT ... RETURNING`이 그대로
  담당한다 - 이번 변경은 그 로직 자체를 건드리지 않는다(요구사항 10).

## 배포 순서

이번 V10은 **데이터만** 채우는 마이그레이션이며, `AssetCodeSequencerImpl`/`AssetCodeGenerator`가
그 데이터를 읽는 방식(원자적 `INSERT ... ON CONFLICT`) 자체는 바꾸지 않는다 - 유일한 코드 변경은
`AssetCodeGenerator`에 9999 상한 체크를 추가한 것뿐이다. 따라서 이번 배포에서 롤링 중 "구버전
코드"와 "신버전 코드"가 서로 다른 채번 알고리즘을 쓰며 경쟁할 위험은 없다(그 위험은 애초에
`V6`이 이전의 count-then-insert 방식을 원자적 시퀀서로 교체했을 때 해당하는 문제였고, 그 전환은
이미 완료되어 있다 - 지금 모든 인스턴스는 항상 `AssetCodeSequencerImpl`만 사용한다).

그럼에도 아주 좁은 창구가 하나 있다: Flyway는 인스턴스가 기동할 때 마이그레이션을 적용하고,
동시에 여러 인스턴스가 뜨더라도 Flyway의 마이그레이션 잠금 덕분에 V10은 정확히 한 번만 실행된다.
하지만 롤링 배포 중 **아직 재시작 전인 기존 인스턴스**가 V10이 커밋되기 **이전**에 레거시 코드가
있는 연도로 신규 등록 요청을 처리하면, 그 순간만큼은 `asset_code_sequence`에 그 연도 행이 아직
없어 `0001`부터 채번을 시도할 수 있다. 이 창구를 없애려면:

1. 배포 파이프라인에서 신규 인스턴스(또는 카나리 1대)를 먼저 기동해 V10이 커밋되는 것을 확인한다.
2. V10 커밋 확인 후에 나머지 인스턴스를 순차 재시작(또는 트래픽 전환)한다.
3. 즉, "마이그레이션 적용 완료 확인 → 전체 트래픽 전환" 순서를 지키면, 기존 인스턴스가 살아있는
   동안에도 이미 올바른 카운터 값을 읽으므로 문제가 없다.

## 9999 초과 정책

`AST-YYYY-NNNN` 형식(순번 4자리 고정)을 그대로 유지하는 쪽을 선택했다 - 형식을 5자리 이상으로
늘리지 않는다. 대신 `AssetCodeGenerator.generate()`가 발급받은 순번이 9999를 넘으면 그 해의 신규
발급 자체를 즉시 차단한다(`IllegalStatusException`, "…에 발급 가능한 자산코드 순번(최대 9999건)을
모두 사용했습니다. 관리자에게 문의해주세요."). 한 해에 자산을 9999건 넘게 등록하는 것은 현재
사업 규모상 현실적이지 않다고 보고, 형식을 깨서 기존 파싱/검색/화면 표시 로직에 영향을 주는 것보다
발급을 막고 명확한 오류로 관리자 개입을 요구하는 쪽이 더 안전하다고 판단했다. 이후 실제로 그 한도에
근접하면, 그때 연도별 파일 분리(예: 접두사 확장)나 자릿수 확장을 별도 기능 개선으로 검토한다.

## 마이그레이션 이후 점검 SQL

```sql
-- 연도별 카운터가 실제 최대 사용 코드와 일치하는지 재확인
SELECT
    s.fiscal_year,
    s.last_seq AS counter_last_seq,
    t.max_seq AS actual_max_seq_in_tangible_asset
FROM asset_code_sequence s
LEFT JOIN (
    SELECT
        substring(asset_code FROM 5 FOR 4)::integer AS fiscal_year,
        MAX(substring(asset_code FROM 10 FOR 4)::integer) AS max_seq
    FROM tangible_asset
    WHERE asset_code ~ '^AST-[0-9]{4}-[0-9]{4}$'
    GROUP BY substring(asset_code FROM 5 FOR 4)
) t ON t.fiscal_year = s.fiscal_year
ORDER BY s.fiscal_year;
```

`counter_last_seq`는 항상 `actual_max_seq_in_tangible_asset` 이상이어야 한다(다음 채번은 이 값+1이므로).
