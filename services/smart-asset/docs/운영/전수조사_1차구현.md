# 전수조사(자산실사) 1차 구현 - S-300~306, 308 (목록·생성·진행현황·검수·리포트·스케줄·종결) (V14/V15)

## 배경

Step 5(`10_화면설계_Step5_Phase2.md`) 전체는 화면 10종(S-300~306, 308, 310~311)이지만, 관리자
화면부터 단계적으로 구현하기로 했다(2026-09-17). 이 문서가 다루는 1차 구현 범위는
**S-300(목록)·S-301(생성-임직원형)·S-302(생성-관리자형)·S-303(진행 현황)·S-304(검수 승인/반려)·
S-305(리포트)·S-306(반복 시행 스케줄)·S-308(종결 처리)** 다 - 모바일 검수(S-310/311)만 아직
구현하지 않았다.

## 왜 모바일 검수 없이 진행 현황/검수/종결까지 구현했나 - "관리자 대체 확인"

S-303/304/308은 원래 "검수 결과가 실제로 들어와 있다"는 전제 위에서 동작하는 화면이고, 그 결과는
정상적으로는 모바일 QR 연속 스캔(S-311)을 통해 들어온다. S-311은 이 프로젝트 전체의 PoC 리스크
1순위(저조도·곡면 라벨 인식률, iOS Safari 카메라 정책, 연속 스캔 중 세션 유지)라 실제 기기 검증
없이는 구현을 확정하기 어렵다.

그래서 `InventoryResult`의 상태 전이 메서드(`confirm`/`reportAnomaly`/`approve`/`reject`/`close`,
I3~I6 규칙을 캡슐화)는 그대로 두고, **그 확인 입력 경로만 S-311 대신 "관리자 대체 확인/이상보고"
API(`PATCH /inventory-result/{id}/confirm`, `.../anomaly`)로 임시 대체했다.** 이렇게 하면:
- S-303(진행 현황)·S-304(검수 승인/반려)·S-308(종결 처리) 세 화면 모두 실제 데이터로 끝까지
  동작을 확인할 수 있다(빈 화면이 아니다).
- S-310/311을 나중에 구현할 때는 이 두 임시 API의 **호출부(컨트롤러 액션)만 걷어내고 도메인
  로직(`InventoryResult.confirm/reportAnomaly`)은 그대로 재사용**하면 된다 - 다시 만들 필요가
  없다.
- 화면/문서 어디에도 "관리자 대체 확인"이라는 문구를 명시해 실제 모바일 검수와 구분한다.

## 대상 산정 규칙 (Q-32)

설계문서의 "개인배정/공용·미배정" 구분을 `TangibleAsset.AssignType`으로 그대로 매핑했다.

| 조사 유형 | 대상 배정형태 | 비고 |
|---|---|---|
| 임직원형(MEMBER) | `PERSONAL` | Step 6(대여) 미구현이라 `ON_LOAN`은 실질 데이터가 없다 |
| 관리자형(ADMIN) | `UNASSIGNED`, `SHARED`, `LOANABLE`, `ON_LOAN` | PERSONAL의 여집합 - "임직원이 책임질 수 없는 자산은 관리자형" 원칙을 그대로 적용 |

두 유형 모두 `lifeStatus = USE`인 자산만 대상이다(불용/처분완료 자산은 실사 대상이 아니다).

⚠️ **이 산정은 워크스페이스에 실재하는 모든 대상 자산을 그대로 쓸어담는다** - 특정 테스트나 화면
호출과 무관하게, 이미 등록되어 있는 개인배정 자산이라면 전부 포함된다(의도된 동작). 통합 테스트
작성 시 "내가 만든 자산 개수 = 대상 개수"라고 가정하면 틀린다(실제로 한 번 이 때문에 테스트가
깨졌다 - 이미 존재하던 다른 개인배정 자산이 함께 대상에 포함되었다). S-306 반복 시행 스케줄의
`existsInProgressByType` 판정도 같은 성격이다 - 이 워크스페이스에 실재하는 "다른" 진행 중 조사
전체를 보는 org-wide 판정이라, 통합 테스트 작성 시 이 값을 특정 방향으로 단언할 수 없다.

## S-305 리포트 - PDF는 왜 없나

설계문서 §4는 "종료 확정 후에만 PDF를 생성한다(진행 중엔 엑셀만)"고 요구하지만, 이 프로젝트
어디에도(smart-asset·common 모두) **PDF 생성 인프라가 없다**(엑셀은 `WiniExcel`/jxls-poi가 이미
있어 S-213 엑셀 업서트가 쓰고 있고, 이번 리포트도 그대로 재사용했다). 감사 제출용 PDF 하나를
위해 새 라이브러리와 템플릿 파이프라인을 들이는 것은 이번 1차 구현 범위를 벗어난다고 판단해,
**화면 조회 + 엑셀 다운로드(참고용)까지만 구현하고 PDF는 만들지 않았다**(진행 중/종료 여부와
무관하게 둘 다 항상 가능하다 - "종료 후에만"이라는 제약은 PDF 전용이라 지금은 적용할 대상이
없다). 핵심 섹션인 "미확인 처리 내역"(§4 "69건이 미확인이었고 그중 12건은 휴직자 이월, 2건은
분실 처리")은 화면·엑셀 둘 다에서 `closureAction`이 채워진(`InventoryResult.close()`가 남긴)
항목을 그대로 노출하는 방식으로 구현했다.

## S-306 반복 시행 스케줄 - 자동 실행(cron)은 왜 없나

설계문서 §4는 "자동 시행은 직전 조사 종료를 전제로 한다(I2). 진행 중 조사가 있으면 실행하지
않고 알림만 보낸다"는 자동 생성 job을 요구한다. 이번 1차 구현에서는 이 자동 실행 자체를
만들지 않았다 - 두 가지 이유다:

1. **알림 인프라가 없다** - "실행 건너뜀"을 사람에게 알릴 방법이 없으면, 자동 실행이 조용히
   건너뛰어질 때 아무도 모른 채 실사 1회가 누락된다(§4가 정확히 경고하는 그 상황).
2. **무인 자동 생성 자체가 이 기능의 성격과 안 맞는다** - 전수조사 생성은 Q-32 산정 규칙에 따라
   워크스페이스에 실재하는 대상 자산을 org-wide로 그대로 쓸어담는 동작이다. 사람의 확인 없이
   이걸 무인으로 주기 실행하는 것은, 알림도 없는 상태에서는 더욱 성급하다.

대신 **예정일 안내 + "템플릿 복제"(수동 생성)** 까지만 지원한다 - 이게 설계문서가 말하는 실제
기본 동선이기도 하다("반기마다 대상 범위·옵션을 다시 고르는 건 낭비다. 직전 조사를 복제해
기간만 바꾸는 것이 기본 동선"). `GET /inventory/schedules`가 유형(임직원형/관리자형)별로
가장 최근 종료된 조사 + 그 조사의 `recurrenceRule`을 기준으로 다음 예정일을 계산해 보여주고,
관리자가 "템플릿으로 새로 만들기"를 누르면 `GET /inventory/{id}/clone-template`으로 그 조사의
생성 옵션(제목·승인 옵션·신규 등록 허용·반복 주기·제외 임직원/검수자)을 그대로 읽어와 생성
다이얼로그를 미리 채운다. 대상 자산 자체는 항상 시행 시점에 새로 산정되므로(Q-32 스냅샷
원칙) 복제 대상에는 포함하지 않는다.

## 알려진 한계

- **S-305 PDF 미구현** - 이 프로젝트에 PDF 생성 인프라가 없어 화면 조회 + 엑셀(참고용)까지만
  구현했다(위 "S-305 리포트" 절 참고).
- **S-306 자동 실행(cron) 미구현** - 알림 인프라 부재 + 무인 org-wide 생성의 위험성 때문에
  예정일 안내와 "템플릿 복제"(수동)까지만 구현했다(위 "S-306 반복 시행 스케줄" 절 참고).
- **분실(LOST) 종결 처리가 실제 처분(disposal)으로 이어지지 않음** - `InventoryResult.close()`는
  `closureAction=LOST`를 기록만 하고, `TangibleAsset.lifeStatus`나 `disposal_asset`은 건드리지
  않는다. 리포트의 "분실 처리 자산" 섹션이 처분손실 규모를 보여주긴 하지만, 실제로 그 자산을
  불용/처분 처리(S-240~242)하는 것은 별도 수동 작업이다 - 두 기능이 아직 연결돼 있지 않다.
- **Q-37 "휴직·장기출장자 자동 제외" 미구현** - `common_user`(CDC 복제 read-model)의 상태값은
  `ENABLE`/`DISABLE` 2종뿐이고, 원 설계가 요구하는 "사용/정지/퇴사/휴직" 4종 상태는 `system`
  서비스의 실제 회원 모델에만 있을 수 있는 더 세분화된 값이라(이번에 확인은 했지만 손대지
  않았다) 이 서비스에서는 알 수 없다. **제외 임직원은 관리자가 수동으로 선택하는 방식만
  지원한다**(`InventoryExcludedMember`) - S-301 화면에서 직접 골라야 한다.
- **알림(리마인드·미매핑 경고) 발송 미구현** - 백엔드 전체에 알림 발송 인프라 자체가 없다(Step 2
  "완료" 표시는 설계문서만 완료된 것이었다). S-301의 "미매핑 경고", S-303의 "선택 리마인드"는
  구현하지 않았다.
- **실제 검수 확인 경로 없음** - 위에서 설명한 "관리자 대체 확인/이상보고"가 S-310/311(모바일
  QR 연속 스캔)을 대신한다. 실제 임직원이 자기 자산을 스캔하는 경로는 아직 없다.
- **관리자형 대상에 위치 담당자 개념 없음** - Q-32 대안(② 위치 담당자 지정)은 채택하지 않고
  권장안(① 관리자형으로 분리)만 구현했다 - 검수자 풀(`inventory_inspector`) 전체가 모든 대상을
  검수할 수 있다.
- **반려(I5) 시 재검수 알림 없음** - 반려하면 상태는 미확인으로 정확히 되돌아가지만, "임직원에게
  재검수 알림이 간다"는 부분은 위 알림 인프라 부재로 구현하지 않았다.

## 마이그레이션

- `V14__inventory.sql`: `inventory`/`inventory_target`/`inventory_inspector`/
  `inventory_excluded_member`/`inventory_result` 5개 테이블 신설.
- `V15__inventory_missing_update_at.sql`: V14에서 `inventory_inspector`/
  `inventory_excluded_member`에 `update_at` 컬럼을 빠뜨려 Hibernate 스키마 검증이 기동 시점에
  실패했던 것을 바로 다음 버전으로 수정. **교훈**: 이 프로젝트의 모든 엔티티는 `AbstractEntity`를
  상속해 `create_at`/`update_at` 둘 다 매핑되므로, "이 테이블은 갱신될 일이 없으니 update_at은
  생략해도 된다"는 판단은 틀렸다 - 예외 없이 두 컬럼을 함께 만들어야 한다.
- **JPQL 작성 시 주의** - 이 프로젝트의 Hibernate(classic HQL 파서)는 (a) `com.foo.Bar.Enum.VALUE`
  형태의 완전정규화 enum 리터럴을 쿼리 문자열에 직접 쓰는 것과 (b) 매핑되지 않은 임의 조건의
  `join X on ...` 구문을 부트스트랩 시점에 `QuerySyntaxException`으로 거부한다(`InventoryTargetRepository.
  existsCarriedOver`에서 실제로 겪음). enum 값은 항상 `@Param`으로 바인딩하고, 조인은 매핑된
  연관관계 경로(`r.inventoryTarget.inventory.id`처럼)만 타고 들어가는 방식으로 작성해야 한다.

## 프런트엔드

- `pages/inventory-management/` - 목록(S-300) + 생성 다이얼로그 2종(S-301/302) + 선택한 조사의
  진행 현황/검수/종결 처리 인라인 패널(S-303/304/308). 원래 설계는 진행현황(P-2 탭)·검수
  승인반려(P-1)·종결처리(P-1)가 서로 다른 화면이지만, 이 코드베이스의 "P-3는 목록 옆 인라인
  패널" 관례를 그대로 이어받아 **하나의 결과 목록(상태 필터) + 선택한 행에 대한 컨텍스트 액션
  패널**로 합쳤다 - 미확인 행은 확인/이상보고/종결 버튼을, 승인대기 행은 승인/반려 버튼을 보여주는
  식이다.
- `entities/inventory/`, `features/inventory/list/`, `features/inventory/create/`,
  `features/inventory/detail/`, `features/inventory/report/`, `features/inventory/schedule/` -
  기존 `disposalAsset`/`tangibleAsset` 슬라이스와 동일한 FSD 구조. 리포트(S-305)는 다이얼로그로,
  스케줄(S-306)은 목록 상단 토글 패널로 - 원래 설계는 별도 화면(`/admin/inventory/:id/report`,
  `/admin/inventory/schedules`)이지만, 이 화면과 메뉴/프로그램/액션을 하나 더 등록하는 부담을
  줄이려고 같은 `inventory-management` 프로그램 안에 인라인으로 합쳤다(액션 등록만 추가로
  필요하고, 새 메뉴·프로그램 등록은 필요 없다).
- 검수자·제외 임직원 선택은 `entities/tangibleAsset`의 `fetchCommonUsers`(배정 대상 후보 목록)를
  재사용했다 - 별도의 "임직원 선택기" 컴포넌트를 새로 만들지 않았다. "템플릿 복제"(S-306)도
  같은 후보 목록을 그대로 쓴다 - 복제된 검수자/제외 임직원 ID가 이 목록에 없는 사람이면(퇴사 등)
  화면에는 ID만 남고 이름이 비어 보일 수 있다 - 별도 검증 없이 값 그대로 다이얼로그에 채운다.
- ⚠️ 이 화면도 아직 메뉴에 등록되지 않았다. 등록 절차는 `docs/운영/불용자산_처분처리.md`의
  "프런트엔드" 절과 동일한 방식(프로그램 등록 → "자산관리" 그룹에 메뉴-프로그램 매핑 → 메뉴
  접근권한 부여)이며, 이 화면의 `programMapping`은 `inventory-management/ui/InventoryManagementPage`
  다.
  ⚠️ **액션 등록은 반드시 프런트엔드 코드가 실제로 호출하는 API를 하나하나 추적해서 빠짐없이
  등록해야 한다** - "불용 처리" 때 이미 한 번 액션 등록을 빠뜨려 권한없음 오류가 났었다(운영
  문서 `불용자산_처분처리.md` 참고). 액션 URI는 `X-Menu-Id`로 지정된 "현재 메뉴"의 프로그램
  기준으로만 검사되므로, 다른 화면(유형자산 관리 등)에 이미 등록된 액션이라도 이 화면에서
  호출하면 별도로 다시 등록해야 한다 - `commonUser` 조회가 정확히 이런 경우다(검수자/제외
  임직원 후보를 불러오는 데 쓰지만, 유형자산 관리 프로그램에 등록된 것과는 별개로 취급된다).
  필요한 액션 전체 목록. **`authType`은 의미(조회성이냐)가 아니라 HTTP 메서드로 고정된다**

  등록해서 권한없음 오류가 났었다(2026-09-17) - POST면 무조건 INSERT로, PATCH는 무조건
  UPDATE로 등록해야 한다.
