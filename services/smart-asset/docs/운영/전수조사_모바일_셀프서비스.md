# 전수조사 모바일 셀프서비스 - S-310/311 (내 전수조사 · 연속 스캔 검수)

## 배경

Step 5 화면설계 10종 중 마지막으로 남아있던 S-310(내 전수조사)·S-311(연속 스캔 검수) - 일반
임직원이 본인에게 배정된 자산을 QR로 직접 확인하는 모바일웹 화면이다. 이 문서 작성 시점까지
S-303/304/308(관리자)은 "관리자 대체 확인"으로 이 확인 입력 경로를 임시 대체하고 있었는데,
이번에 그 실제 경로(S-310/311)를 구현했다. **관리자 대체 확인 API(`PATCH .../confirm`,
`.../anomaly`)는 그대로 남겨뒀다** - 관리자가 대신 처리해야 하는 예외 상황(장기 부재자 등)에
계속 쓸 수 있고, 이미 다른 화면에서 참조하고 있어 제거할 이유가 없다. 이번에 만든 것은 그
"실제 임직원 셀프서비스" 경로를 별도로 추가한 것이다.

## 왜 새 화면/라우트를 안 만들고 관리자 콘솔에 그대로 얹었나

설계문서(§2)는 S-310/311이 "L-EMP 임직원 셸"(모바일 전용 상단바+하단 4탭 셸, `/my/*` 라우트)에
속한다고 되어 있다. 하지만 **이 코드베이스에는 L-EMP 셸이 아직 전혀 존재하지 않는다** - 지금
실제로 운영 중인 프런트엔드는 위니텍 공통 관리자 콘솔(GNB+LNB, 메뉴/권한 시스템) 하나뿐이고,
Step 6~7의 다른 모든 L-EMP 화면(대여, 확인서 승인, 라이선스, 티켓)도 전부 미착수 상태다. 지금
이 하나의 기능만을 위해 완전히 새로운 모바일 셸·라우팅 체계·로그인 분기(`/login` → `/my` vs
`/admin`)를 만드는 것은 범위를 크게 벗어난다.

대신 이미 있는 정확한 선례를 그대로 따랐다: **S-217 QR 스캔**(`/asset-scan`, `/asset-scan/:id`)이
이미 "사이드바 메뉴 밖의 단독 라우트 + 특정 관리자 메뉴의 권한을 빌려오는" 패턴
(`useStandaloneMenuContext`)으로 모바일웹에서 동작하고 있다. 다만 그 기존 패턴은 **관리자/자산
관리자가 자기 폰으로 조회하는 용도**(그 메뉴의 SELECT 권한이 있어야 열린다)라 "권한이 전혀 없는
일반 임직원"에게는 그대로 안 맞는다. 그래서 S-310/311은:

- 화면 자체는 **일반 메뉴로 등록**한다(`SMARTASSET_INVENTORY_MY`, 표준 메뉴-프로그램 매핑 경로 그대로
  사용 - `useStandaloneMenuContext` 같은 특수 처리 불필요). 목록(S-310)과 연속 스캔(S-311)은
  라우트를 따로 만들지 않고 **한 페이지 안에서 모드 전환**(`pages/my-inventory/ui/MyInventoryPage`)
  으로 구현했다 - 이 코드베이스는 메뉴 1개 = 페이지 1개 = URL 1개 구조라, 스캔 화면만 위한 새
  메뉴를 또 만들 이유가 없다.
- **API 권한은 메뉴 ACL이 아니라 소유권 검사로 처리한다** - `selfConfirmResult`/
  `selfConfirmResultWithoutScan`/`selfReportWrongHolder` 모두 `InventoryTarget.memberId ==
  로그인한 본인`인지를 서비스 계층에서 직접 확인하고(`findOwnResult`), 아니면 예외를 던진다.
  이렇게 해야 "이 일반 임직원이 자산관리자용 관리 메뉴에 대한 세밀한 수정 권한까지 갖고 있는가"를
  신경 쓸 필요가 없다 - 새 메뉴(`SMARTASSET_INVENTORY_MY`)에 대한 최소한의 게이트웨이 통과
  권한만 있으면 되고, 실제 "내 것인가"는 매번 서버가 다시 확인한다.

## 확인 경로 3종 (I3/§3)

| 경로 | 화면 | 결과 상태 | API |
|---|---|---|---|
| QR 연속 스캔 | S-311 | 조사의 `approvalRequired`에 따라 CONFIRMED 또는 PENDING_APPROVAL | `PATCH /inventory-result/{id}/self-confirm` |
| 라벨 없음/훼손(사진) | S-310 목록에서 직접 선택 | **항상 PENDING_APPROVAL** (I3 예외 - 스캔 없는 확인은 검수자 승인 강제) | `PATCH /inventory-result/{id}/self-confirm-photo` |
| 제 자산이 아닙니다 | S-310 목록 | ANOMALY / WRONG_HOLDER | `PATCH /inventory-result/{id}/self-wrong-holder` |

QR 인코딩 값은 **S-217/S-216과 완전히 동일한 포맷**(`{origin}/asset-scan/{tangibleAssetId}` 또는
순수 UUID)을 그대로 재사용한다 - 이미 발행된 QR 라벨을 새로 찍을 필요가 없다.

## S-311 연속 스캔 - 기존 S-217과 무엇이 다른가

`features/inventory/scan/model/useContinuousQrScanner.js`는 `pages/asset-scan/model/
useQrScanner.js`의 카메라/디코딩 로직(BarcodeDetector 우선, jsQR 폴백, getUserMedia 에러 처리)을
그대로 재사용하되 두 가지를 바꿨다:
- 스캔 성공 시 `navigate()`로 화면을 떠나지 않고 `onDecoded(assetId)` 콜백만 호출 - 스캐너가
  계속 켜져 있다("연속 스캔", §3 핵심 차별점).
- 같은 자산을 카메라가 계속 잡고 있어도 매 프레임 콜백이 중복 발생하지 않도록, 직전에 스캔한
  자산ID+시각을 기억해 2.5초 쿨다운을 둔다.

디코딩된 자산ID가 "내 미확인 대상" 목록에 없으면(이미 처리됐거나 남의 자산) 조용히 실패
피드백만 보여주고 계속 스캔한다 - 자동으로 "제 자산이 아닙니다"를 신고하지는 않는다(그건 목록
화면에서 임직원이 직접 판단해서 누르는 별도 동작이다).

## C-201 촬영 (라벨 없음/훼손 예외)

설계문서 요구사항("촬영 시각과 업로드 시각을 함께 기록") 그대로, `<input type="file"
accept="image/*" capture="environment">`로 앨범 선택을 차단하고, 파일을 받은 시점(`capturedAt`)과
실제 업로드(S3 PUT) 완료 시점(`uploadedAt`)을 각각 클라이언트에서 타임스탬프로 찍어 서버에 함께
보낸다 - `inventory_result.photo_captured_at`/`photo_uploaded_at`(V16 마이그레이션)에 저장된다.

⚠️ **이 타임스탬프는 클라이언트(브라우저) 시각이다, EXIF 촬영 시각이 아니다.** 사진 파일의 EXIF
메타데이터를 읽어 실제 셔터 시각을 확인하는 것은 별도 라이브러리가 필요해 이번 범위에서는
하지 않았다 - "앨범에서 미리 찍어둔 사진을 나중에 올렸는지"를 이 두 타임스탬프(파일을 받은
시각과 업로드 완료 시각의 간격이 비정상적으로 크지 않은지)로 대략 판별하는 수준이다.

### 실제 파일 업로드 - 공용 헬퍼를 못 쓰고 직접 구현한 이유 (모바일 실기기에서 실제로 겪은 문제 3가지)

실제 사진 바이트 저장은 새 인프라를 만들지 않고 기존 공용 첨부파일 업로드(`commonFile`,
`services/common`의 `CommonFileController.prepareUpload` → S3 presigned PUT)를 그대로
재사용한다. 다만 **공용 업로드 헬퍼(`winiFile.upload`, `shared/lib/file.ts`)는 그대로 못 쓰고**
`features/inventory/scan/model/usePhotoCapture.js`가 prepareUpload 호출 + presigned URL로의
PUT을 직접 구현한다 - 모바일(LAN의 다른 기기)에서 실제로 겪은 문제 3가지 때문이다:

1. **Mixed Content** - 이 프론트엔드는 카메라(getUserMedia) 때문에 HTTPS로 뜨는데(모바일에서
   보안 컨텍스트가 필요), presigned URL(`uploadUrl`)은 MinIO를 그대로 가리키는 **HTTP** 절대
   URL이라 브라우저가 mixed content로 요청 자체를 막는다. `/api`를 vite가 대신 중계하는 것과
   똑같은 이유 - 그래서 이 업로드도 같은 오리진의 `/s3-proxy`로 바꿔친 뒤 보낸다
   (`vite.config.ts`의 `s3ProxyPlugin`).
2. **Vite 내장 프록시의 대용량 PUT 버그** - `/s3-proxy`를 Vite 5.4.9의 내장 `server.proxy`
   (http-proxy 기반)로 처음 구현했더니, 약 350~400KB를 넘는 PUT 바디에서 500을 던졌다(실측
   확인 - 실제 폰 사진 크기에서 항상 재현됨). 그래서 Node 기본 `http` 모듈로 요청/응답 스트림을
   그대로 파이프하는 수제 프록시(`s3ProxyPlugin`의 `configureServer`)로 바꿨다 - 50MB까지
   직접 테스트해 정상 동작을 확인했다.
3. **"multiple authentication types" 충돌** - presigned URL은 쿼리 문자열 자체에 서명(인증)이
   있는데, 이 프로젝트의 공용 axios 인스턴스(`connector.client`)는 요청 인터셉터가 모든 요청에
   `Authorization`/`X-Org-Id`/`X-Menu-Id`를 **무조건** 다시 채워 넣는다(요청 시점에 `null`로
   지워도 무시하고 재주입한다). 그 결과 실제 요청에는 "URL 서명"과 "Authorization 헤더" 두
   인증 방식이 동시에 붙어서 MinIO가 `InvalidRequest: request has multiple authentication
   types, please use one`으로 거부한다(직접 재현해서 확인). 그래서 이 PUT 하나만 그 인터셉터를
   안 타는 **순정 `fetch()`**로 보낸다 - `prepareUpload` 호출(일반 API, 인증 필요)은 여전히
   `connector.client`를 쓴다.

## API 계약

| 메서드 | 경로 | 설명 |
|---|---|---|
| `GET` | `/inventory/my` | 내 전수조사(S-310) - 본인 배정 대상 목록. I2에 의해 진행 중 조사는 최대 1건 |
| `PATCH` | `/inventory-result/{inventoryTargetId}/self-confirm` | QR 연속 스캔 확인(S-311). 소유권 검사 |
| `PATCH` | `/inventory-result/{inventoryTargetId}/self-confirm-photo` | 라벨 없음/훼손 - 사진으로 확인. `{ photoFileId(필수), capturedAt, uploadedAt }` |
| `PATCH` | `/inventory-result/{inventoryTargetId}/self-wrong-holder` | 제 자산이 아닙니다. `{ note }` |

## 알려진 한계 / PoC 리스크 (미해결)

- **실기기 검증을 못 했다** - 이 작업 환경에는 브라우저 자동화 도구가 없어 실제 카메라 동작을
  전혀 확인할 수 없었다. 설계문서가 지목한 PoC 리스크 1순위 3가지(저조도·곡면 라벨 인식률,
  iOS Safari 카메라 정책, 연속 스캔 중 세션 유지)는 여전히 **실제 스마트폰으로 직접 확인이
  필요하다** - 코드 리뷰만으로는 검증할 수 없다.
- **"완료 버튼 노출" 관리자 토글 미구현** - 설계문서는 "관리자가 완료 버튼 노출을 끄면 버튼
  자체가 사라지고 관리자만 종결한다"는 조사별 옵션을 요구하지만, `Inventory` 엔티티에 이 옵션을
  추가하지 않았다. 지금은 항상 버튼이 보이고, 미확인이 남아있으면 비활성 + 남은 건수만 표시한다.
- **EXIF 촬영 시각 미검증** - 위 "C-201 촬영" 절 참고.
- **L-EMP 셸 자체가 없다** - 이번 화면은 기존 관리자 콘솔의 메뉴 등록 방식을 재사용했을 뿐,
  Step 6~7의 다른 L-EMP 화면(대여, 확인서 승인, 라이선스, 티켓)이 실제로 착수되면 진짜 모바일
  셸(상단바+하단 탭)이 필요해질 수 있다 - 그때 이 화면도 그 셸로 옮겨야 할 수 있다.
- **알림 미구현** - 반려·재검수 알림과 마찬가지로, 확인 완료/이상보고에 대한 푸시/알림은 없다
  (기존 한계와 동일, 알림 인프라 부재).

## 등록 절차 (아직 등록 전)

**1) 프로그램 등록**
| 프로그램명 | 프로그램 코드 | 프로그램 매핑 | 상태 | 메뉴상태 | 모바일상태 |
|---|---|---|---|---|---|
| 내 전수조사 | `SMARTASSET_INVENTORY_MY` | `my-inventory/ui/MyInventoryPage` | 사용 | 사용 | **사용** (모바일 전용 화면이므로 다른 화면들과 달리 모바일상태도 사용으로) |

**2) 메뉴에 매핑** - "자산관리" 하위(순번 8)에 메뉴-프로그램 매핑 기능으로 추가. `menu_type=PROGRAM`
확인 필수(불용자산 처리 문서와 동일한 주의사항).

**3) 메뉴 접근권한 부여** - ⚠️ **이 메뉴는 관리자뿐 아니라 전체 일반 임직원에게도 열어줘야
한다** - 이 시스템에 "전체 직원" 같은 포괄적인 권한 그룹이 있다면 그 그룹에, 없다면 운영자가
판단해서 임직원 전체가 속한 권한 그룹(들)에 이 메뉴의 조회·수정 권한(ALLOW)을 부여해야 한다.
어떤 권한 그룹에 부여할지는 운영자가 결정해야 하는 부분이라 이 문서에서 특정 그룹명을 지정하지
않았다 - 기존 권한 그룹 목록을 확인 후 적절한 대상에 부여해주세요.

**4) 액션 등록** (`SMARTASSET_INVENTORY_MY` 프로그램)
| 권한유형 | HTTP | URI |
|---|---|---|
| 조회(SELECT) | GET | `smart-asset/inventory/my` |
| 수정(UPDATE) | PATCH | `smart-asset/inventory-result/*/self-confirm` |
| 수정(UPDATE) | PATCH | `smart-asset/inventory-result/*/self-confirm-photo` |
| 수정(UPDATE) | PATCH | `smart-asset/inventory-result/*/self-wrong-holder` |
| 등록(INSERT) | POST | `smart-asset/commonFile/prepareUpload` |

마지막 행(`commonFile/prepareUpload`)은 사진 업로드 준비 API - 실제 파일 바이트는 이 호출 후
발급된 S3 presigned URL로 직접 PUT되므로(게이트웨이를 거치지 않음) 별도 등록이 필요 없다.
