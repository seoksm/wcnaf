## §1 레이아웃 설계 원칙

- **R1** — 관리자와 임직원은 별개의 셸을 쓴다. 같은 URL 아래 권한으로 화면을 분기하지 않고, /admin/* 과 /my/* 로 진입점부터 나눈다. 임직원이 관리자 화면 구조를 볼 일이 없어야 하고, 모바일웹 최적화 대상도 다르다.
- **R2** — 관리자는 데스크톱 우선, 임직원은 모바일 우선. 관리자 화면은 1280 이상에서 완전한 형태를 갖추고 축소 시 열을 접는다. 임직원 화면은 360 기준으로 설계하고 넓어지면 여백을 준다.
- **R3** — 화면은 6개 패턴 중 하나에 반드시 속한다. 목록 / 상세 / 폼 / 트리+상세 / 마법사 / 모달. 새 패턴을 만들기 전에 기존 6개로 표현 가능한지 먼저 확인한다. 1인 개발에서 패턴 수는 곧 유지보수 비용이다.
- **R4** — 목록은 언제나 같은 4단 구조. 페이지 헤더 → 검색·필터 → 액션바 → 결과 테이블 → 페이징. 순서와 위치가 화면마다 달라지면 사용자가 매번 다시 학습한다.
- **R5** — 저장 버튼은 항상 오른쪽 아래. 취소는 그 왼쪽. 폼이 길면 하단 고정 바로 띄운다. 화면마다 위치가 바뀌지 않는다.
- **R6** — 파괴적 동작은 목록에서 실행하지 않는다. 삭제·정지·처분 같은 되돌리기 어려운 동작은 상세 화면에서만 노출하고, 확인 단계를 둔다. 목록의 체크박스 일괄 동작은 되돌릴 수 있는 것만 허용한다.
- **R7** — 비어있는 상태를 화면마다 설계한다. 자산 0건, 부서 0개, 검색결과 0건은 서로 다른 안내가 필요하다. 빈 테이블만 보여주면 사용자는 고장으로 읽는다.

## §3 반복 패턴 6종

이후 모든 Phase의 화면은 이 6개 패턴을 조합해 만든다. 패턴을 먼저 확정하면 Phase 1 이후 설계가 “어떤 패턴에 어떤 필드” 수준으로 단순해진다.

**[도면 P-1] 목록**  ·  _가장 많이 쓰임_

| 설계 포인트 | 내용 |
|---|---|
| **필터** | 4열 그리드 고정. 조건이 4개를 넘으면 “상세 검색” 접기 로 내린다. 검색 조건은 URL 쿼리에 반영 해 뒤로가기·북마크가 동작하게 한다. |
| **첫 열** | 항상 주요 식별자이며 상세로 가는 링크. 자산이면 자산명, 멤버면 이름. |
| **상태** | 색이 아니라 칩(테두리+라벨) 으로 표현. 테마 미적용 상태에서도 읽히고, 색맹 대응도 된다. |
| **<768** | 테이블 → 카드 리스트. 카드에는 식별자 + 상태 + 속성 2개까지만. 나머지는 상세에서 본다. |

**[도면 P-2] 상세**  ·  _탭형_

| 설계 포인트 | 내용 |
|---|---|
| **구조** | 헤더(이름·상태·액션) → 기본정보 카드 → 탭. 탭 안은 항상 목록 이라 P-1을 재사용한다. |
| **수정** | 기본정보는 별도 수정 화면(P-3) 으로 이동. 인라인 편집은 쓰지 않는다 — 저장 시점이 모호해지고 이력 기록이 꼬인다. |
| **히스토리** | 모든 상세 화면이 마지막 탭에 히스토리 를 갖는다. 위치를 고정하면 사용자가 찾지 않는다. |

**[도면 P-3] 등록 · 수정 폼**

| 설계 포인트 | 내용 |
|---|---|
| **배치** | 레이블 위, 필드 아래. 2열 그리드. 좌우 레이블은 한글 길이 편차 때문에 정렬이 무너진다. |
| **필수** | * 표시 + 제출 시 일괄 검증. 입력 중 실시간 오류는 이메일 형식 정도만. |
| **오류** | 필드 아래 한 줄로 무엇이 왜 틀렸고 어떻게 고치는지. 상단 요약 배너와 병행. |
| **이탈** | 변경 후 이동 시 확인 다이얼로그. 1인 개발이므로 공통 가드로 한 번만 만든다. |

**[도면 P-4] 트리 + 상세 2분할**  ·  _조직도 · 메뉴권한_

| 설계 포인트 | 내용 |
|---|---|
| **비율** | 좌 280 고정 : 우 가변. <768에서는 트리만 먼저 보이고 선택 시 상세로 전환 (드릴다운). |
| **트리** | 노드에 인원수 뱃지 를 붙인다. 드래그로 부서를 옮기지 않는다 — department_path 재계산이 무겁고 실수가 치명적이다. 상세의 “상위 부서” 셀렉트로만 이동. |

**[도면 P-5] 엑셀 업로드 마법사**  ·  _4단계 고정_

| 설계 포인트 | 내용 |
|---|---|
| **원칙** | 부분 성공 금지. 오류가 1건이라도 있으면 확정 버튼을 잠근다. “500행 중 480행 성공”은 사용자가 무엇을 고쳐 재업로드할지 알 수 없게 만든다. |
| **오류** | 반드시 행번호 + 컬럼 + 입력값 + 사유 4종. 사유는 시스템 용어가 아니라 사람 말로 쓴다. |
| **재사용** | 이 마법사는 멤버·자산·무형자산·라이선스에서 동일 컴포넌트로 재사용 한다. 검증 규칙만 주입. |

**[도면 P-6] 모달**  ·  _필드 6개 이하일 때만_

| 설계 포인트 | 내용 |
|---|---|
| **기준** | 입력 필드 6개 이하 + 단일 목적 이면 모달, 그 이상은 페이지. 모달 안에 탭이나 스크롤이 생기면 설계가 틀린 것이다. |
| **금지** | 모달 위의 모달. 확인 다이얼로그도 모달 위에 겹치지 않고 모달 내부를 확인 상태로 전환 한다. |

### S-001 · 로그인

**[도면 S-001] 로그인**  ·  _공용 · 반응형_

| 설계 포인트 | 내용 |
|---|---|
| **가입 없음** | 관리자 직접 등록만 허용하므로 회원가입·소셜로그인 링크가 존재하지 않는다. 비밀번호 찾기도 셀프 서비스가 아니라 관리자 문의로 안내한다. |
| **실패** | 5회 실패 시 10분 잠금. 남은 횟수를 노출해 사용자가 상황을 알게 한다. 계정 존재 여부는 노출하지 않는다. |
| **분기** | 성공 후 must_change_password 참이면 S-002로 강제 이동. 역할이 임직원이면 /my, 그 외는 /admin. |
| **2FA** | 관리자급이고 2단계 인증 대상이면 코드 입력 단계를 이 화면 안에서 전환. 별도 페이지를 만들지 않는다. |

### S-020 · 조직도 관리

**[도면 S-020] 조직도 관리**  ·  _패턴 P-4_

| 설계 포인트 | 내용 |
|---|---|
| **삭제** | 소속 멤버나 하위 부서가 있으면 삭제 차단 하고, 몇 명·몇 개 때문인지 숫자로 알려준다. “삭제할 수 없습니다”만 띄우면 사용자는 다음 행동을 모른다. |
| **경로** | 부서 저장 시 department_path (예 /1/5/12/)를 갱신한다. 상위 부서 변경이면 하위 전체를 재귀 갱신 하고 트랜잭션으로 묶는다. |
| **루트** | 최상위 “본사”는 삭제·이동 불가. 이름 변경만 허용. |
| **스코프** | 부서자산관리자에게는 이 화면 자체를 노출하지 않는다. 조직 편집은 관리자 이상. |

### S-030 · 멤버 목록

**[도면 S-030] 멤버 목록**  ·  _패턴 P-1_

| 설계 포인트 | 내용 |
|---|---|
| **보유자산** | 목록에 보유 자산 수를 노출 한다. 퇴사·정지 상태인데 보유 자산이 남아 있으면 경고 표시 — 이 한 컬럼이 회수 누락을 막는다. |
| **일괄** | 부서·권한·상태 변경만 허용. 삭제는 없다 (R6). 멤버는 물리 삭제하지 않고 퇴사 처리한다. |
| **스코프** | 부서자산관리자로 접속하면 부서 필터가 자기 부서+하위로 고정 되고 변경 불가 상태로 표시된다. 숨기지 말고 왜 고정인지 보이게 한다. |
| **빈 상태** | 검색결과 0건과 멤버 0명은 다른 안내. 후자는 “멤버 등록” 또는 “엑셀 일괄등록”으로 유도한다. |

### S-032 · 멤버 상세

**[도면 S-032] 멤버 상세**  ·  _패턴 P-2_

| 설계 포인트 | 내용 |
|---|---|
| **탭 구성** | 유형자산 / 라이선스 / 확인서 / 히스토리. 탭 라벨에 건수를 붙인다 — 열어보지 않고도 있는지 알 수 있다. |
| **비밀번호** | 관리자는 초기화만 가능하고 조회는 불가. 초기화하면 must_change_password 가 서고 새 임시 비밀번호를 화면에 1회만 표시한다. |
| **퇴사** | 상태를 퇴사로 바꾸면 보유 자산 목록을 확인 다이얼로그에 그대로 띄우고 “이 자산들은 회수 대상으로 남습니다”를 명시한다. |
| **연락처** | 목록에서는 마스킹, 상세에서 권한 있을 때만 전체 표시. |

### S-040 · 메뉴 접근권한

**[도면 S-040] 메뉴 접근권한**  ·  _패턴 P-4 변형_

| 설계 포인트 | 내용 |
|---|---|
| **2단** | 왼쪽에 역할 기본값 4종 + 개별 관리자. 개별 설정이 없으면 역할 기본값을 따르고, 있으면 개별이 우선한다. 이 관계를 화면에 문장으로 적어둔다. |
| **미리보기** | 체크 결과로 실제 LNB가 어떻게 보이는지 를 즉시 문장으로 보여준다. 이게 없으면 저장하고 로그아웃해서 확인하는 일이 반복된다. |
| **안전장치** | 최고관리자 본인의 환경설정 메뉴는 해제 불가. 스스로를 잠그는 실수를 막는다. |
| **임직원 권한** | 2개뿐이라 별도 화면(S-041)을 만들지 않고 이 화면 하단에 통합 했다. 화면 수를 줄이는 편이 1인 개발에 유리하다. |

> ✅ 화면 수 정리 결과 — 목록의 S-041(임직원 공통 권한)은 S-040에 통합해 11종 → 10종 이 된다. S-002와 S-050은 같은 컴포넌트를 모드만 바꿔 재사용하므로 실제 구현 단위는 9개 다.

## §5 이번 단계에서 결정할 것

다음 단계(Phase 0-2 알림 · 0-3 첨부파일)로 넘어가기 전에 답이 필요한 항목이다. 나머지는 해당 Phase에서 묻겠다.

| ID | 항목 | 설명 | 선택지 |
|---|---|---|---|
| Q-1 | **로그인 아이디는 무엇으로 하나** | 이메일 / 사번 / 둘 다 허용. 사번은 인사 데이터와 맞추기 쉽고, 이메일은 메신저 계정 매핑에 유리하다. | ① 이메일 단일 ② 사번 단일 ③ 둘 다 허용 (권장) |
| Q-2 | **부서 계층은 몇 단계까지** | 깊이 제한이 없으면 트리 UI와 department_path 갱신 비용이 커진다. 실제 조직도 기준으로 상한을 두는 편이 낫다. | ① 2단계 (본부-팀) ② 3단계 (권장) ③ 무제한 |
| Q-3 | **부서자산관리자를 실제로 운영하나** | 앞서 짚었던 항목. 쓰지 않으면 데이터 스코프(RLS)가 통째로 사라지고 권한이 3단계로 줄어 M03 난이도가 크게 낮아진다. | ① 지금부터 사용 ② 1차는 제외, 이후 확장 (권장) ③ 사용 안 함 |
| Q-4 | **직급 · 직책을 코드로 관리하나** | 자유 입력이면 표기가 흩어져 통계·필터가 안 된다. 코드로 두면 마스터 관리 화면이 하나 늘어난다. | ① 자유 입력 ② 공통코드 마스터 (권장) ③ 직급만 코드 |
| Q-5 | **멤버 식별자를 사번으로 둘 것인가** | 스키마의 member 에 사번 컬럼이 없다. 인사 데이터 이행과 엑셀 업서트 키로 쓰려면 필요하다. | ① employee_no 추가 (권장) ② 이메일을 업서트 키로 ③ 사번 미사용 |
| Q-6 | **워크스페이스는 진짜 멀티테넌트인가** | 스키마 전반에 workspace_id 가 있다. 사내 단일 회사용이면 이 컬럼은 비용만 되고, 향후 그룹사 확장 계획이 있으면 유지가 맞다. | ① 단일 워크스페이스 전제, 컬럼은 유지 (권장) ② 완전 멀티테넌트 ③ 컬럼 제거 |

> ⚠️ Q-3이 가장 큰 갈림길이다. ②를 택하면 이번 Phase의 권한 구현이 “역할 4종 + 메뉴 ACL”로 끝나고, S-030의 부서 스코프 고정 로직과 department_path 기반 조회 필터가 전부 빠진다. 나중에 붙이더라도 목록 조회 Mapper만 손보면 되므로, 1차 제외의 비용이 낮다.
