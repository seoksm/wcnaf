## §1 알림 유형 카탈로그

알림 화면을 그리기 전에 무엇이 알림을 발생시키는지 전수를 먼저 확정한다. 이 목록이 곧 notification_rule.notification_type 의 enum이며, 나중에 항목을 추가하는 것보다 지금 빠짐없이 세는 편이 훨씬 싸다.

| 코드 | 발생 시점 | 기본 수신 | 발송 | Phase |
|---|---|---|---|---|
| ACCOUNT_CREATED | 관리자가 계정 생성 | 본인 DM | 즉시 | 0-1 |
| PASSWORD_RESET | 관리자가 비밀번호 초기화 | 본인 DM | 즉시 | 0-1 |
| AUTH_2FA_CODE | 관리자 2단계 인증 | 본인 DM | 즉시 | 0-1 |
| INVENTORY_STARTED | 전수조사 시행 | 참여 임직원 DM | 즉시 | 2 |
| INVENTORY_REMIND | 미완료자 대상 | 미완료자 DM | 매일 09:00 배치 | 2 |
| INVENTORY_CLOSED | 전수조사 완료 처리 | 검수자 DM + 관리자 채널 | 즉시 | 2 |
| ACK_REQUESTED | 수령·반납 확인서 요청 | 대상자 DM | 즉시 | 3-3 |
| ACK_APPROVED | 승인 완료 | 요청 관리자 DM | 즉시 | 3-3 |
| LOAN_OVERDUE | 대여 반납 기한 초과 | 대여자 DM + 관리자 채널 | 일 1회 배치 | 3-2 |
| INTANGIBLE_EXPIRING | 만료 D-30/7/3/1 | 지정 담당자 DM | 일 1회 배치 | 4-1 |
| RENTAL_PAYMENT_DUE | 결제일 도래 | 지정 담당자 DM | 일 1회 배치 | 4-1 |
| LICENSE_EXPIRING | 라이선스 만료 임박 | 지정 담당자 DM | 일 1회 배치 | 4-2 |
| TICKET_CREATED | 티켓 등록 | 관리자 채널 | 즉시 | 5 |
| TICKET_ASSIGNED | 담당자 지정 | 담당자 DM | 즉시 | 5 |
| TICKET_STATUS_CHANGED | 상태 전이 | 요청자 DM | 즉시 | 5 |
| TICKET_COMMENTED | 코멘트 등록 | 상대방 DM | 즉시 | 5 |

> ℹ️ 16종 중 5종이 배치 발송이다. 즉 알림 인프라는 “이벤트 → 발송”만이 아니라 스케줄러 + 발송 큐 + 재시도 까지 이번 Step에서 함께 서야 한다. 이걸 나중에 얹으려 하면 5개 모듈의 알림 호출부를 전부 다시 손대게 된다.

### 발송 규약

- **N1** — 알림은 트랜잭션 밖에서 비동기로 나간다. 업무 저장이 커밋된 뒤 큐에 적재하고, 발송 실패가 업무 트랜잭션을 롤백시키지 않는다. 메신저 장애로 자산 등록이 막히는 일은 없어야 한다.
- **N2** — 발송 대상이 0명이면 발송하지 않고 그 사실을 이력에 남긴다. “메신저 계정이 매핑되지 않아 발송 대상 없음”이 로그에 없으면, 알림이 안 온 이유를 영원히 못 찾는다.
- **N3** — 재시도는 3회, 간격 1·5·30분. 3회 실패 후에는 관리자 채널에 실패 요약을 보낸다 — 실패 알림까지 실패하면 그때는 화면에서만 확인한다.
- **N4** — 같은 이벤트·같은 수신자에게 5분 내 중복 발송 금지. 저장 버튼 연타나 배치 중복 실행으로 스팸이 되는 것을 막는다.
- **N5** — 어댑터는 인터페이스로 두고 초기 구현은 로그 전용. 메신저 제품이 정해지기 전에도 나머지 모듈이 알림 호출부를 완성할 수 있게 한다.

## §3 Phase 0-3 — 첨부파일 공용 컴포넌트

화면이 아니라 컴포넌트 다. 자산 사진(최대 4장), 실사 사진, 티켓 첨부, 회사 로고가 전부 이걸 쓴다. 변형은 3종으로 고정하고 그 외를 만들지 않는다.

| ID | 컴포넌트 | 사용처 | 제약 |
|---|---|---|---|
| C-200 | 이미지 그리드 업로더 | 자산 사진, 티켓 첨부 | 최대 4장 · 장당 10MB · jpg/png/webp/heic |
| C-201 | 모바일 촬영 업로더 | 전수조사 실사 사진 | 촬영 강제 옵션 · 1장 필수 |
| C-202 | 단일 파일 업로더 | 회사 로고, 엑셀 업로드 | 1개 · 교체 시 기존 삭제 |
| C-203 | 이미지 뷰어 | 공통 | 확대·좌우 이동·다운로드 |

**[도면 C-200 / C-201] 이미지 업로더 2종**  ·  _데스크톱 · 모바일_

| 설계 포인트 | 내용 |
|---|---|
| **파생본** | 업로드 시 썸네일 200 / 뷰어 1024 / 원본 3종을 생성한다. 목록에서 원본을 로드하면 자산 100건 화면이 수백 MB가 된다. |
| **HEIC** | 아이폰 기본 포맷이라 반드시 들어온다. 서버에서 JPEG로 변환해 저장하고, 변환 실패 시 “이 형식은 지원하지 않습니다”가 아니라 어떻게 바꿔 올릴지 를 안내한다. |
| **대표** | 첫 번째 이미지가 목록 썸네일. 드래그로 순서를 바꾸면 대표도 바뀐다 — attachment.sort_order 로 관리. |
| **C-201** | 전수조사 전용. capture="environment" 로 앨범 선택을 차단 하고 현장 촬영만 허용한다(허위 실사 방지). 다만 일부 브라우저는 이 속성을 무시 하므로, 촬영 시각과 업로드 시각의 간극을 서버에서 함께 기록해 사후 판별 근거를 남긴다. |
| **업로드 중** | 진행률과 취소를 제공하고, 업로드 완료 전에는 저장 버튼을 잠근다. 모바일 회선에서 가장 흔한 사고가 업로드 미완료 상태의 저장이다. |

### 저장 구조

- **F1** — 물리 경로는 날짜 기반으로 분산한다. /upload/2026/09/09/{uuid}.jpg. 한 디렉터리에 수만 개가 쌓이면 파일시스템 성능이 떨어진다.
- **F2** — DB에는 경로만, 파일 자체는 BLOB로 넣지 않는다. 백업 용량과 조회 성능이 함께 나빠진다.
- **F3** — 삭제는 소프트 삭제 후 배치 정리. 자산 삭제 시 첨부를 즉시 지우면 복구가 불가능하다. del_yn 표시 후 30일 뒤 물리 삭제.
- **F4** — 다운로드는 반드시 서버 경유. 파일 URL을 직접 노출하면 권한 없는 사람이 링크만으로 접근한다. /files/{id} 로 받아 권한 확인 후 스트리밍.
- **F5** — 용량 추이를 설정 화면에서 볼 수 있게 한다. 전수조사 1회당 자산수 × 1~4장이 쌓이므로, 3년 뒤 용량을 예측할 수 있어야 한다.

> ℹ️ 용량 추정 — 자산 1,000건 기준. 자산 사진 3장(평균 2MB) = 6GB, 전수조사 연 2회 × 1장 = 4GB/년, 파생본 포함 약 1.4배. 3년 누적 약 25GB. 로컬 파일시스템으로 충분하되, 백업 대상 용량이 이만큼 늘어난다는 점을 운영 계획에 반영한다.

| 설계 포인트 | 내용 |

| **시스템 그룹** | 자산 상태·티켓 유형처럼 코드가 로직에 물려 있는 그룹 은 editable=false 로 잠그고 명칭만 수정 가능하게 한다. 사용자가 “대여중”을 지우면 상태머신이 깨진다. |
| **삭제 규칙** | 참조 0건일 때만 물리 삭제. 그 외에는 사용 해제. 이 규칙 하나로 자산 종류·위치 삭제 문제까지 같은 방식으로 해결된다. |
| **확장** | Phase 1-1의 자산 종류·위치도 이 화면 구조를 그대로 쓴다. 다만 종류는 다국어 명칭과 감가상각 기준이 붙으므로 별도 화면으로 분리한다(Step 3에서 설계). |
