## §1 감가상각 계산 규칙 — 화면보다 먼저

정액법 자체는 나눗셈 한 번이다. 문제는 언제부터 상각하고, 기중 취득·처분을 어떻게 처리하며, 다 상각된 자산을 얼마로 남기는가 다. 이 셋이 회계팀과 다투게 되는 지점이다.

> ✅ Q-21 확정 — 배치가 아니라 이벤트 기반, 총액법, 분기 누적  
> ① 스케줄 배치를 두지 않는다. 자산 이벤트(등록 · 취득가액 변경 · 불용 · 처분)가 발생할 때, 그리고 결산 자료를 산출하는 시점에 계산한다.  
> ② 산출 기간은 회계연도 초부터의 누적 — 1~3월 · 1~6월 · 1~9월 · 1~12월. 월 단위 자료를 만들지 않는다.  
> ③ 총액법으로 표시한다. 취득가액 · 감가상각누계액 · 장부가 세 값을 모두 노출하고, 장부가만 보여주는 순액법 표기를 쓰지 않는다.

### ① 기산 시점 — 월할 상각

| 방식 | 2026-03-11 취득 시 | 비고 |
|---|---|---|
| 취득월 포함 (권장) | 2026-03부터 상각 시작 | 법인세법상 월할 계산과 일치. 취득한 날이 속하는 달부터 |
| 익월부터 | 2026-04부터 상각 시작 | 일부 기업 내규 |
| 일할 계산 | 3월은 21/31일분만 | 정확하지만 계산·검증 부담이 크고 실익이 적음 |

### ② 비망가액 — 다 상각된 자산의 잔액

> ⚠️ 실무에서 반드시 물어보는 항목이다. 잔존가치율을 0%로 두면 내용연수 종료 시 장부가가 정확히 0원이 된다. 그런데 자산은 여전히 회사에 있고 사용 중 이다. 장부가 0원 자산은 대장에서 존재감이 사라져 관리 대상에서 빠지기 쉽다.  
> 한국 실무 관행은 비망가액(memorandum value) 1,000원 을 남기는 것이다. 폐기·처분 시점에 이 1,000원을 제거한다. 시스템에서는 "최종 상각 시 장부가가 비망가액 아래로 내려가지 않도록" 마지막 달 상각액을 조정한다.

### ③ 계산 예시

| 조건 | 값 |
|---|---|
| 취득가액 | 2,890,000 |
| 내용연수 / 잔존가치율 | 5년(60개월) / 0% |
| 비망가액 | 1,000 |
| 월 상각액 = (2,890,000 − 1,000) ÷ 60 | 48,150 |
| 취득 2024-03 → 2026-09 (31개월 경과) | 누적 1,492,650 / 장부가 1,397,350 |
| 60개월 후 (2029-02) | 장부가 1,000 (비망가액) |

### ④ 산출 규칙

- **D1** — 이벤트 기반 산출 — 스케줄 배치 없음. 자산 등록 · 취득가액 변경 · 불용 · 처분 이벤트가 발생하면 해당 자산의 상각 정보를 갱신하고, 결산 자료는 산출 요청 시점에 그 시점 기준으로 계산 한다. 매월 새벽에 도는 배치가 없으므로 배치 실패·재실행 운영 부담이 사라진다.
- **D2** — 산출 단위는 회계연도 누적 분기. 1~3월 · 1~6월 · 1~9월 · 1~12월 네 가지만 제공한다. 월별 자료를 만들지 않으므로 depreciation_snapshot 의 period 는 연도 + 분기 구분 으로 단순해진다.
- **D3** — 총액법으로 표시한다. 취득가액 · 감가상각누계액 · 장부가를 항상 세 컬럼으로 나란히 보여준다. 감가상각누계액은 취득가액의 차감 계정이므로 둘을 함께 보여야 자산의 원가와 소모 정도가 동시에 읽힌다.
- **D4** — 감가상각 대상은 생애 상태 기준 (Step 3 규칙 A3). 사용·보관·수리중은 상각, 불용·처분완료는 중단. 불용 처리한 달까지는 상각하고 그 다음 달부터 중단 한다.
- **D5** — 취득가액이 0이거나 비어 있으면 상각 대상에서 제외 하고 목록에 “기준 미비”로 표시한다. 조용히 0원 상각으로 처리하면 자산총계가 틀어진다.
- **D6** — 종류별 기준이 없는 자산은 상각하지 않고 별도로 모아 보여준다. 새 종류를 추가하고 감가상각 기준 설정을 잊는 것이 가장 흔한 누락이다.
- **D7** — 결산 자료를 확정하면 그 산출 결과를 저장한다. 배치는 없지만 “확정” 액션은 남긴다 — 아래 설명 참조.

> ⚠️ 이벤트 기반 산출이 감수하는 것과, 그 보완책  
> 배치 스냅샷을 두지 않으면 운영은 가벼워지지만 재현성이 약해진다. 3월에 뽑은 1분기 자료를 9월에 다시 뽑았을 때, 그 사이 어떤 자산의 취득가액이 정정되었다면 같은 기간인데 숫자가 달라진다. 회계 감사에서 “3월에 제출한 자료와 왜 다르냐”는 질문을 받는 지점이다.  
> 이건 배치를 되살리자는 말이 아니다. “확정” 액션 하나로 해결된다 — 결산 자료를 뽑아 회계에 넘기는 시점에 [확정] 버튼 을 누르면 그때의 산출 결과가 depreciation_snapshot 에 그대로 저장되고, 이후 같은 분기를 조회하면 재계산 대신 저장된 값을 보여준다. 확정하지 않은 분기는 언제나 실시간 계산이다.  
> 스케줄러는 없고, 확정은 사람이 누른다. 이벤트 기반이라는 결정을 유지하면서 감사 대응 근거를 남기는 최소 장치다.

### S-220 · 자산 히스토리 탭

**[도면 S-220] 자산 히스토리**  ·  _타임라인 · append-only_

| 설계 포인트 | 내용 |
|---|---|
| **저장 형식** | 변경 필드만 저장 한다(전체 스냅샷 아님). 자산 1건당 수십 건의 이력이 쌓이는데 매번 전체 행을 복사하면 용량이 자산 테이블의 수십 배가 된다. 단 불용·처분·배정 3종은 스냅샷을 함께 남긴다 — 감사에서 그 시점 전체 상태를 요구한다. |
| **표시** | 변경 이력은 표 형태의 diff (항목/전/후)로. 서술형 문장("위치가 변경되었습니다")은 무엇이 어떻게 바뀐지 알 수 없다. |
| **배치 추적** | 엑셀 일괄 등록·일괄 변경은 배치 ID를 함께 남긴다. 잘못된 엑셀로 42건이 바뀌었을 때 그 42건을 한 번에 찾아낼 유일한 방법이다. |

| **유형 필터** | 등록 / 정보수정 / 상태변경 / 배정 / 전수조사 / 대여 / 확인서 / 불용. 이력이 수십 건 쌓이면 필터 없이는 못 읽는다. |

> ℹ️ S-221 전체 활동 로그 는 자산 전체를 가로지르는 감사용 화면이다. “지난주에 이관리가 무엇을 바꿨나”, “어제 일괄 변경으로 무엇이 영향받았나”를 답한다. S-220과 같은 테이블을 자산 필터 없이 조회하는 것이므로 추가 개발은 목록 화면 하나뿐 이다.

> ✅ **구현 완료 (2026-09-16)** — S-220·S-221 모두 아래처럼 단순화해 구현했다.
> - **저장 형식**: 설계대로 변경 필드만 JSON `[{field,before,after}]`으로 저장(`asset_history.changed_fields`). 상태변경·배정 2종은 전체 상태 스냅샷을 `snapshot` 컬럼에 함께 저장(Q-23). 등록(REGISTER)도 스냅샷을 남긴다(신규 자산은 스냅샷=전체 필드와 동일하므로).
> - **유형 필터 4종만 실제 생성**: 등록/정보수정/상태변경/배정만 생성된다. 전수조사·대여·확인서·불용은 해당 기능이 아직 구현 전이라 이력 유형 코드(enum)만 미리 만들어두고 실제로는 생성되지 않는다 — 해당 Step(5·6·4-불용) 구현 시 동일한 `AssetHistoryStore`를 그대로 재사용하면 된다.
> - **배치 추적**: 설계대로 엑셀 업서트(S-213)·일괄 변경(S-215)이 batch_id를 공유한다. 자산 복제(S-214)도 같은 이유로 batch_id를 공유하도록 추가 확장했다(설계문서에는 명시 안 됐지만 동일한 "한 번에 여러 건" 작업이라 동일 규칙을 적용).
> - **S-220 화면 위치**: 별도 P-2 탭 페이지 대신, 유형자산 관리 화면에서 선택한 자산의 배정 이력 패널 옆에 "변경 이력" 패널로 나란히 표시(S-218과 동일하게 인라인 패널로 단순화).
> - **S-221 화면 위치**: 별도 메뉴/화면 대신, 유형자산 관리 화면에 "전체 활동 로그" 버튼 → 다이얼로그로 구현. 새 메뉴·프로그램 등록 없이 기존 "유형자산 관리" 메뉴 권한(SELECT)을 그대로 사용한다.
> - **S-221 필터·페이징 (2026-09-16 확장)** — 자산 수가 많아지면 필터 없는 전체 목록은 못 쓴다는 피드백에 따라 확장: 이력유형 외 **자산코드·자산명(포함검색)·로그발생시각(기간)** 필터 추가. 페이지당 200건은 유지하되, **목록을 아래로 스크롤하면 다음 200건을 이어서 불러오는 무한스크롤**로 변경(`GET .../activity-log`에 `assetCode`·`assetName`·`fromDate`·`toDate`·`page` 쿼리 파라미터 추가). 처리자 필터는 여전히 미구현.
> - **PostgreSQL 파라미터 타입 추론 버그 회피**: `(:param is null or ...)` 형태의 JPQL을 `assetCode`/`assetName`/`fromDate`/`toDate`에 그대로 적용하면 `could not determine data type of parameter $N`(Hibernate 5 + pgjdbc 조합) 오류가 난다. 이 4개 파라미터는 "필터 없음"을 null 바인딩이 아니라 **항상 매칭되는 안전한 기본값**(빈 문자열, 1970~2999 넓은 날짜 범위)으로 Java 쪽(`AssetHistoryReaderImpl`)에서 채워 넘기는 방식으로 회피했다. `historyType`은 이 문제가 재현되지 않아 기존 null-check 패턴을 그대로 유지.
> - **취득가액 diff 정규화**: DB에 저장된 값(scale 2, 예: "1500000.00")과 요청으로 새로 들어온 값(scale 0, "1500000")의 표현 차이만으로 실제 변경 없는 필드가 diff에 잡히는 문제가 있어, `BigDecimal.stripTrailingZeros()`로 정규화해 비교한다.
> - 상세는 `TangibleAssetServiceImpl`(도메인 서비스에 diff·기록 로직 포함, 별도 `AssetHistoryRecorder` 클래스로 분리하지 않음), `AssetHistory`/`AssetHistoryInfo` 엔티티, DB 마이그레이션 `V4__step4_asset_history.sql` 참조.

### S-230 · 감가상각 현황

**[도면 S-230] 감가상각 현황**  ·  _회계감사 산출물_

| 설계 포인트 | 내용 |
|---|---|
| **기간 선택** | 연도 + 누적 분기(1~3 / 1~6 / 1~9 / 1~12) 2단 셀렉트. 월 단위 선택지를 만들지 않는다. 확정된 기간은 저장값을, 미확정 기간은 실시간 산출값을 보여주고 어느 쪽인지 칩으로 명시 한다. |
| **총액법 4값** | 취득가액 / 감가상각누계액 / 장부가 / 당기 상각액. 회계팀이 재무제표에 그대로 옮겨 적는 숫자 이므로 상단에 고정한다. 장부가만 보여주는 순액법 표기를 쓰지 않는다. |
| **기초·기말** | 목록 컬럼도 총액법을 따른다 — 기초 누계 → 당기 상각 → 기말 누계 → 장부가 순서로 배치해 증감이 왼쪽에서 오른쪽으로 읽히게 한다. |
| **산출 시각** | 미확정 기간은 산출 기준 시각을 반드시 표기 한다. 같은 화면을 두 번 열어 숫자가 다를 때 원인을 알 수 있어야 한다. |
| **상각 제외 배너** | 취득가액 미입력·기준 미설정 건수를 매번 최상단에 경고로 노출 한다. 이 12건이 자산총계에서 빠지고 있다는 사실을 모른 채 결산하면 나중에 되돌리기 어렵다. |
| **경과** | 30/60 형태로 경과 개월 / 총 개월. 남은 상각 기간이 한눈에 보인다. |
| **상각완료** | 장부가가 비망가액에 도달한 자산은 칩으로 표시하고 당월 상각을 0으로 둔다. 대장에서 사라지지 않게 하는 것이 비망가액의 목적 이다. |
| **엑셀** | 화면 컬럼 그대로 + 합계행. 회계 감사 제출용이므로 기준 연월과 출력 일시를 헤더에 박는다. |

### S-232 · 결산 산출 · 확정 이력

**[도면 S-232] 결산 산출 · 확정 이력**  ·  _배치 없음 · 사람이 확정_

| 설계 포인트 | 내용 |
|---|---|
| **배치 없음** | 스케줄러가 돌지 않으므로 “배치 실패” 상태 자체가 존재하지 않는다. 실행 시각·재실행 컬럼도 필요 없고, 운영 중 새벽 배치를 신경 쓸 일이 사라진다. |
| **확정의 의미** | 결산 자료를 회계에 넘기는 시점에 사람이 누르는 액션. 확정된 기간은 저장값 조회, 미확정 기간은 실시간 산출. S-230 상단 칩이 이 둘을 구분해 보여준다. |
| **확정 전 경고** | 상각 제외 자산이 남아 있으면 확정 직전에 다시 경고 한다. 확정은 되돌리기 번거로운 동작이므로, 누락을 안고 고정하는 것을 막는 마지막 관문이다. |
| **해제** | 최고관리자 + 사유 입력. 해제하면 그 기간은 다시 실시간 산출로 돌아간다. |
| **연간 확정** | 1~12월 확정이 곧 연 결산이다. 이후 연도의 기초 누계는 이 값을 기준으로 잡는다. |

> ✅ Step 2 알림 유형은 16종을 유지한다. 배치를 두지 않기로 하면서 DEPRECIATION_BATCH_FAILED (배치 실패 알림)가 불필요해졌다. 산출은 사용자 요청 시점에 동기적으로 일어나므로, 실패하면 화면에서 즉시 보인다.

|---|---|
| **장부가 노출** | 불용 처리하려는 자산의 현재 장부가를 반드시 보여준다. 장부가 218,400원이 남은 자산을 불용 처리하면 그만큼 처분손실이 발생하므로, 회계 담당자가 알고 눌러야 한다. |

### S-240 · 불용자산 목록 & S-242 처분 처리

**[도면 S-240 / S-242] 불용자산 목록 · 처분 처리**  ·  _상태머신 종단_

|---|---|
| **2단 상태** | 처분대기 (창고 보관) → 처분완료 (매각·폐기·무상기증). 처분대기 상태에서만 수정 가능, 완료 후 잠금. |

| **불용시 장부가** | 불용 처리 시점의 장부가를 disposal_asset 에 복사해 고정 한다. 나중에 감가상각 스냅샷을 뒤져 재계산하면 값이 흔들린다. |
| **일괄 처분** | 폐기는 수십 건을 한 번에 처리하는 것이 정상이다. 같은 처분방법·일자·거래처를 공유 하고 금액만 개별 입력하거나 합계로 배분. |
| **증빙** | 매각 명세서·폐기 확인증을 첨부(C-202 재사용). 세무 조사 때 요구된다. |
| **임시 저장** | 처분은 여러 날에 걸쳐 진행되는 경우가 많다. 완료 전 임시 저장 을 허용해 입력 중간에 잠글 필요가 없게 한다. |
