## §1 짚고 갈 것 — 만료 알림과 Q-21의 관계

> ⚠️ Q-21에서 “배치를 두지 않는다”고 정했는데, 이번 단계에는 배치가 필요하다. 모순이 아니므로 경계를 분명히 해둔다.  
> Q-21은 감가상각 산출에만 적용된 결정 이다. 감가상각은 “요청 시점에 계산하면 되는 값”이라 배치가 불필요했다.  
> 반면 만료·결제일 알림은 “특정 날짜에 사람에게 도달해야 하는 행위” 다. 아무도 화면을 열지 않아도 D-30에 알림이 나가야 하므로, 이건 본질적으로 스케줄이 필요한 작업 이다. Step 2에서 이미 배치 발송 5종(리마인드·연체·만료·결제일)을 확정해 뒀고, 그 결정이 그대로 유효하다.  
> 정리 — 배치가 있는 것: 알림 발송(일 1회 09:00). 배치가 없는 것: 감가상각 산출.

**[도면 S-500] 무형자산 목록 — 만료 중심 설계**  ·  _패턴 P-1_

| 설계 포인트 | 내용 |
|---|---|
| **만료 구간 4칸** | 이 화면의 존재 이유는 만료 사고 예방 이다. 목록 위 4칸을 만료 구간으로 두고 만료됨·30일내를 경고 스타일 로. 유형별 집계는 여기서 필요 없다. |
| **기본 필터** | 기본값을 “90일 내 만료” 로 둔다. 전체 34건을 매번 보는 게 아니라 조치가 필요한 것만 보는 화면이다. |
| **D-day** | 만료일과 D-day를 함께 표시. 날짜만 있으면 관리자가 매번 계산한다. 지난 것은 -10일 로 음수 표기. |
| **알림 컬럼** | 설정된 알림 시점을 30·7·3·1 로 압축 표기. 알림이 설정되지 않은 자산을 한눈에 찾는 것이 목적이다 — 그게 사고 나는 자산이다. |
| **만료 후** | 만료된 자산도 목록에서 지우지 않는다. 갱신 조치가 남아 있으므로 경고 상태로 계속 보여주고, 갱신하면 만료일이 밀려 정상으로 돌아간다. |

**[도면 S-512] 렌탈 상세 — 결제 스케줄**  ·  _패턴 P-2 · 탭 3_

| 설계 포인트 | 내용 |
|---|---|
| **귀속 월 ≠ 결제일** | 8월 사용분이 9월 1일에 결제된다. 두 날짜를 분리해 관리 하지 않으면 월별 비용 집계가 한 달씩 밀린다. 대시보드는 귀속 월 기준 으로 집계한다. |
| **사용량 기반** | 금액이 매월 다른 계약이 실재한다(AWS·Azure). 고정액 가정으로 설계하면 안 된다 — 예상액과 실제액을 구분하고, 자동결제라도 실제 금액은 수기 확정을 허용한다. |
| **지출 테이블 공용** | expense_record 를 렌탈·라이선스가 공용 으로 쓴다(src_type, src_id). 대시보드 비용 집계가 한 쿼리로 끝난다. |
| **해지** | 해지는 삭제가 아니다. 상태를 해지로 바꾸고 지출 이력은 보존 한다. 연간 비용 추이에서 사라지면 안 된다. |

> ℹ️ 라이선스 관리의 실제 어려움은 수량 정합성이다. Adobe CC를 2024년에 5개, 2025년에 3개 사서 총 8개인데 실제 배정은 9명. 이게 시스템에서 조용히 통과되면 라이선스 관리를 하는 의미가 없다. 구매 수량 · 배정 수량 · 잔여를 항상 함께 보여주고, 초과 시 경고 하는 것이 이 모듈의 핵심 요구사항이다.

**[도면 S-530] 라이선스 목록**  ·  _수량 정합성 중심_

| 설계 포인트 | 내용 |
|---|---|
| **보유·배정·잔여** | 3개 컬럼을 항상 나란히. 보유는 구매내역 수량 합계, 배정은 사용자 배정 건수, 잔여는 그 차이. 초과면 음수로 표시하고 경고색. |
| **상단 경고** | 배정 초과 종수를 목록 위에 상시 노출. 이 배너가 없으면 28종 중 2종의 초과를 아무도 발견하지 못한다. |
| **배정률 바** | 95%는 “곧 부족”, 58%는 “과다 구매”. 숫자만으로는 판단이 안 되므로 바를 함께 둔다. 100% 초과 바는 채움색을 경고색으로. |
| **잔여 활용** | 잔여가 많은 라이선스(Figma 5석)는 감축 후보 다. 비용 최적화 기능은 엔터프라이즈 제외 대상이었지만, 이 목록만으로도 담당자가 판단할 근거는 충분하다. |

**[도면 S-532] 라이선스 상세 — 1:N 4개**  ·  _이 단계 최대 화면_

| 설계 포인트 | 내용 |
|---|---|
| **탭 5개** | 사용자배정 / 구매내역 / 포함SW / 지출내역 / 공급사. 기본 탭은 사용자 배정 — 관리자가 가장 자주 하는 일이 배정·해제다. |
| **수량 이중 검증** | 총량 검증(보유 8 vs 배정 9)과 구매내역별 검증 (각 구매내역의 잔여)을 함께 한다. 총량만 보면 “어느 구매분의 초과인지” 알 수 없고, 갱신·해지 시점 판단이 안 된다. |
| **미연결 배정** | 구매내역에 연결되지 않은 배정을 명시적으로 표시 한다. 이게 초과의 실제 원인이며, 시스템이 조용히 넘기면 영원히 발견되지 않는다. |
| **초과 처리** | 차단이 아니라 경고 다(→ Q-47). 실무에서 “먼저 배정하고 나중에 구매 처리”가 흔하므로 막으면 업무가 멈춘다. 대신 목록·상세·대시보드에 계속 노출한다. |
| **포함 SW** | Adobe CC → Photoshop, Illustrator 등. 수기 등록 (벤더 DB 제외, R2). 자산 배정과는 무관한 참조 정보다. |
| **<768** | 탭 5개는 가로 스크롤. 요약 4값은 2×2 그리드로 접는다. |

**[도면 S-550] 내 라이선스 (임직원)**  ·  _회수 요청_

| 설계 포인트 | 내용 |
|---|---|
| **자발적 회수** | 사용량 자동 측정(PC 에이전트)이 제외 범위이므로, 미사용 라이선스 판별은 임직원의 자발적 신고에만 의존 한다. 따라서 “왜 회수해야 하는지”를 화면에 적어 동기를 만든다. |
| **회수 요청 처리** | 요청은 서비스데스크 티켓(회수)으로 자동 생성 된다. 관리자가 티켓을 완료 처리하면 배정이 해제되고 잔여가 늘어난다. |
| **배정일 노출** | 배정일을 보여주면 “2년 전에 받고 안 쓰는 것”을 본인이 자각한다. 최근 사용일이 없으므로 배정일이 유일한 판단 근거다. |

**[도면 S-600 / S-601] 칸반 보드 · 모바일웹 대체**  ·  _C4 · 브레이크포인트 전환_

| 설계 포인트 | 내용 |
|---|---|
| **모바일 전환** | <768에서 칸반 → 상태 탭 + 리스트 (C4). 드래그&드롭을 모바일에서 구현하지 않고, 상태 변경은 상세 화면에서만 허용한다. 좁은 화면에서 드래그는 오조작이 잦다. |
| **드래그** | 데스크톱 칸반의 드래그는 상태 전이 규칙을 검증 한다. 완료 → 처리중 같은 역방향은 거부하고 이유를 알린다. |
| **완료 컬럼** | 완료는 이번 주 것만 보여주고 나머지는 “완료된 티켓” 화면으로. 완료가 수백 건 쌓이면 보드가 무의미해진다. |
| **자산 연결** | 티켓 카드에 연결 자산 코드를 칩으로. 자산 없는 티켓(신규구매)과 있는 티켓(수리)이 한눈에 구분된다. |

**[도면 S-602] 티켓 상세 — 완료 시 자산 자동등록**  ·  _핵심 연계_

| 설계 포인트 | 내용 |
|---|---|
| **자동등록 폼** | 완료 처리 시 자산 등록 폼이 티켓 상세 안에서 열린다. 별도 화면으로 보내면 티켓과의 연결이 끊기고, 관리자가 자산 등록을 잊는다. |
| **필수 5개** | S-212와 동일한 필수 항목(자산명·종류·위치·취득일·취득가액). 예상 금액이 아니라 실제 취득가액 을 입력받는다 — 감가상각 기준이 되므로 정확해야 한다. |
| **연쇄 처리** | 자산 생성 → 요청자 배정 → 수령 확인서 요청까지 한 번에. 이 3단계를 각각 다른 화면에서 하면 반드시 하나를 빠뜨린다. |
| **대상 유형** | 자동등록은 신규구매 티켓에만 적용(→ Q-49). 수리·교체는 기존 자산이 있으므로 상태 변경만, 회수는 배정 해제만. |
| **코멘트** | 요청자 코멘트는 배경색으로 구분. 상태 변경·코멘트 등록 시마다 상대방에게 알림(Step 2 규약). |
| **완료 잠금** | 완료 후 수정 불가. 잘못됐으면 새 티켓으로 처리 하고, 생성된 자산은 자산 화면에서 수정한다. |

| Q-51 | **티켓에 SLA(처리 기한)를 두나** | 기한이 없으면 처리중 상태로 무한정 머문다. | ① 유형별 목표일 + 초과 표시 (권장) ② SLA 없음 ③ 초과 시 에스컬레이션 알림 |
| Q-52 | **지출내역 테이블 통합** | 렌탈·라이선스가 공용으로 쓸지. | ① expense_record 공용 (권장) ② 각각 별도 테이블 ③ 뷰로 통합 |
| Q-53 | **사용량 기반 렌탈의 금액 처리** | AWS처럼 매월 금액이 다른 계약. | ① 예상액 + 실제액 분리 입력 (권장) ② 실제액만 수기 ③ 고정액만 지원 |
