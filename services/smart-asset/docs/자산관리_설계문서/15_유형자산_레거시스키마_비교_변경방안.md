# 15. 유형자산 레거시 스키마(SP001) 비교 및 변경방안

> 작성일 2026-09-23 · 레거시 ERP(WINIERP) `SP001`(자산대장) 테이블을 현재 `tangible_asset` 스키마와
> 비교해 갭을 식별하고 변경방안을 정리한다. Q-13(사용자정의 필드 미채택, 2026-09-16 재확정) 정책에
> 따라 예비 컬럼(`ext_*`) 방식이 아닌 **정식 컬럼 추가**를 전제로 검토했다.
>
> 이 문서는 결정이 아니라 **검토 결과 + 제안**이다. 실제 반영은 §5 실행 순서에 따라
> 항목별로 필요성을 확인한 뒤 별도 마이그레이션으로 진행한다.

---

## 1. 비교 대상

- **레거시**: `WINIERP.SP001` (Oracle, 자산대장) — 컬럼 39개, 단일 테이블
- **현재**: `tangible_asset` + 연관 테이블(`asset_category`, `asset_location`, `asset_assignment`,
  `disposal_asset`) — PostgreSQL, 도메인별 분리 (`V1`~`V2`, `V13` 마이그레이션)
- 참고 문서: `05_화면설계_진행현황_인덱스.md`(Q-1~Q-53 결정 로그), `03_FP분석_개발비견적.md`은 무관

## 2. 구조적 차이

| | SP001 (레거시) | 현재 스키마 |
|---|---|---|
| 구성 | 단일 테이블에 유형자산·도서·PC/모니터 스펙·위치·프로젝트까지 전부 수용 | 도메인별 분리 — `tangible_asset`(마스터) / `asset_category` / `asset_location` / `asset_assignment`(배정 **이력**, SP001엔 없는 개념) / `disposal_asset`(처분 **이력**) / `intangible_asset`(도메인·인증서·상표권, 별도 도메인) / 라이선스·SW는 또 별도 테이블 |
| 상태 모델 | `ASSET_STAT_CD` 단일 코드 | `life_status × assign_type` 2축 분리 (Q-15, 의도적 개선) |
| 식별 | `BARCODE` | QR 기반 `asset_code`(AST-YYYY-NNNN, Q-14/Q-18, 의도적 대체) |
| 등록자·수정자 | `REGER_NO`/`UPTER_NO` **NOT NULL** | **없음** — `AbstractEntity`가 `create_at`/`update_at`만 추적하고 "누가"는 어디에도 없음. `tangible_asset`만의 문제가 아니라 `AbstractEntity`를 상속하는 시스템 전체 엔티티의 공통 이슈 |

| ETC | 비고 | `memo` | 매핑됨 |

| QUANTITY | 수량 | 없음(1자산=1레코드=1QR 고정) | 정책 충돌 — §4-C 참고 |

| DEL_YN | 삭제여부 | `status`(ENABLE/DISABLE) | 매핑됨 |

## 4. 그룹별 정리

### A. 이미 의도적으로 개선/대체 — 손댈 필요 없음

`ASSET_STAT_CD` → 2축분리(Q-15), `BARCODE` → QR(Q-18), `DEL_DATE` → `disposal_asset`,
`USE_DATE` → Q-24 정책, `USER_EMP_NO` → `asset_assignment` 이력.

Q-13 재확정으로 `ext_txt/ext_num/ext_dt` 예비컬럼 자체가 삭제됐으므로(`V3`), 아래 갭들을
"사용자정의필드" 방식으로 메우면 안 되고 **정식 컬럼으로 추가**해야 한다(Q-13 문서에 명시된 정책).

### B. 실제 갭 — 필요성만 확인되면 바로 컬럼 추가 가능

1. 등록자/수정자 추적 — `AbstractEntity`에 `created_by`/`updated_by` 추가하는 시스템 전체
   작업(`tangible_asset`만의 이슈 아님, 감사 요건이면 우선순위 높음)
2. PC/모니터 스펙 6종
3. 위치상세 자유텍스트
4. 사용종료예정일
5. 지역코드(AREA_CD, 위치 상위 그룹핑)

### C. 스키마보다 정책 결정이 먼저인 것

- **수량(QUANTITY)**: 현재 모델은 "1자산=1레코드=1QR"이 구조적 전제(`asset_code` UNIQUE,
  QR 라벨 1개). SP001처럼 수량 필드를 넣으면 이 전제와 충돌한다 — 저가 소모품(마우스 5개 등)을
  묶음 관리할지, 그런 것도 개별 QR로 쪼갤지 결정 필요.
- **부서(DEPT_NO/NM)**: 현재는 `current_member_id`가 있을 때만 `common_user.department_name`으로
  간접 조회 가능한데, `assignType=SHARED`(공용)는 배정 사용자가 구조적으로 null이라 **공용 자산은
  담당 부서를 특정할 방법이 아예 없다.** 부서 단위 자산관리가 필요하면 `tangible_asset`에
  `owner_department_id`류 컬럼이 별도로 필요.
- **도서/SW 통합관리**: SP001은 자산·도서·SW를 한 테이블에 몰아넣었는데(EBOOK_YN, 저자/출판사
  컬럼 재사용), 현재 시스템은 유형자산(tangible)/무형자산(도메인·인증서·상표권)/SW라이선스가
  전부 분리돼 있어 **"도서" 자산이 들어갈 도메인이 명확하지 않다.** category를 "도서"로 만들어
  `tangible_asset`에 욱여넣는 건 가능하지만 EBOOK_YN 같은 전용 필드는 못 쓴다 — 도서를 실제로
  관리할 계획이면 범위 정의부터 필요.
- **프로젝트 연계(PRJ_SN)**: 현재 시스템에 프로젝트 개념 자체가 없다. 실제 업무에서 자산을
  프로젝트별로 집계할 필요가 있는지 확인 필요.
- **배송비여부**: 용도 불명확 — 실사용 이력이 있는 필드인지 확인 필요.

## 5. 권장 변경안 (B그룹, 정책 확정 시 즉시 적용 가능한 스케치)

```sql
-- V26__tangible_asset_legacy_fields.sql (예시, 실제 실행 전 필요 항목만 선별)
ALTER TABLE tangible_asset
    ADD COLUMN area_code            character varying(10),   -- AREA_CD
    ADD COLUMN location_detail      character varying(200),  -- ASSET_POSITION_DESC
    ADD COLUMN pc_cpu               character varying(100),
    ADD COLUMN pc_clock             character varying(100),
    ADD COLUMN pc_memory            character varying(100),
    ADD COLUMN pc_hdd               character varying(100),
    ADD COLUMN pc_ssd               character varying(100),
    ADD COLUMN monitor_type         character varying(100),
    ADD COLUMN monitor_size         character varying(100),
    ADD COLUMN planned_end_use_date date;                    -- END_USE_DATE

-- 등록자/수정자는 tangible_asset 단독이 아니라 AbstractEntity 레벨 변경 필요(별도 작업)
```

부서(`owner_department_id`)·수량·도서 관련은 정책 결정 이후 별도 마이그레이션으로 다뤄야 한다.

## 6. 실행 순서 제안

1. B그룹(PC/모니터 스펙, 위치상세, 사용종료예정일, 지역코드) — 실사용자 확인 후 바로 마이그레이션
2. C그룹(수량/부서/도서/프로젝트) — 정책 결정 먼저
3. 등록자/수정자 — 감사 요건이면 별도 작업으로 우선순위 판단
4. 컬럼이 추가되면 등록·수정 폼(`Editor.jsx`), 상세화면, **엑셀 업서트 양식**(현재 14컬럼)에도
   함께 반영해야 완결된다
